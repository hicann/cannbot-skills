# 批量 Issue 的调查分工

出现多项范围待核查时、分类后准备调查与响应时，由协调者在逐项调查前读取。协调者负责获取、分类、授权、发布与报告；把范围核查、技术调查和草稿按单项或共享实现/证据小组委派。范围为 `pending` 的调查同样适用，不能等它们全部核查完、只剩少量 `need_attention` 才考虑分工。

## 委派时机与复杂度

先复用仍有效的证据，将剩余工作按依赖分组。存在两个以上互不依赖、需实质调查或拟稿的任务组且宿主支持子 agent 时，默认委派并行；单步查询、证据已充分的微小任务或只有一项简单响应时由主会话完成。通常每个任务处理 1–3 条关联 Issue，同时推进 2–3 个任务且不超过宿主可用名额，完成后再补位，不为每条 Issue 都启动一个 agent。调查和拟稿可由同一个子 agent 连续完成，但须先核实范围、响应必要性和拟稿所需证据。

轻量任务优先用具备相应工具能力的轻量模型；宿主无法选择模型时仍用普通子 agent 的独立上下文，不能因此跳过委派。按分析难度选择能力，不按正文长度、PR 文件数或 diff 行数判定：

| 任务 | 适合轻量调查或拟稿 | 升级分析的情形 |
|---|---|---|
| 责任范围核查 | 核对问题版本、明确路径、入口和支持范围 | 版本实现不同、调用链不清、报告平台与实际故障路径矛盾 |
| 简单回复拟稿 | 基于已核实证据整理答疑、最小信息请求或 PR 方案 | 尚需推导根因、评估工程取舍或比较冲突方案 |
| PR 核查 | 作者、状态、关联、base/head 与影响明确的 diff 摘要 | 跨版本覆盖、复杂语义影响、多个修复方向冲突 |
| 知识查询、评论整理、逐算子候选调查 | 查找定向资料、整理响应证据、核查核心补丁及账号 | 资料或评论矛盾、核心贡献难判断、身份映射不明 |

遇到超出当前任务能力的疑点，返回已核实事实、证据和待解决问题，由主会话继续分析或重新委派；不猜测范围、覆盖关系或责任人。主会话在子任务运行时推进其他独立工作并审核已就绪结果，不重复完成已委派的调查。子任务失败或未返回保持待处理，不当作“未找到”，也不阻断其他独立项。

在本轮目录保存简短分工记录，并用现有 `run_state.artifacts` 引用：任务范围、执行者、状态、结果路径，及串行或升级原因。无子 agent 能力时按相同证据与输出要求顺序完成；工具失败、名额不足、依赖未就绪或单步可完成等写具体原因，不新增 Issue 分类或必填状态枚举。

## 给调查者的输入

只传该子任务必要的 Issue 原文/评论、准确 URL、目标版本、源码路径、相关责任配置、共享证据文件引用和独立输出目录；完整草稿任务须提供完整 `description`。优先使用新上下文，不继承主会话历史；复用已验证的公共证据，整批 JSON/PR 快照通过路径按需读取，不全量复制。按任务读取：范围核查用 [responsibility-scope.md](responsibility-scope.md)，拟稿用 [response-writing.md](response-writing.md)，候选调查用 [operator-owner-candidates.md](operator-owner-candidates.md)。只读子任务不加载协调者的获取、发布、授权和状态文档。涉及 PR 时给真实链接并要求读取当前状态和相关 diff。不要把协调者猜测的范围或根因当既定事实。

PR 调查限于平台原生关联或 Issue/PR 正文、评论中的明确互引。无显式关系时不按路径、算子或现象检索潜在修复 PR；回复给出基于已知问题的潜在方案即可。用户明确要求查找修复 PR 或专项审查时再扩大调查。历史显式关联仍须核对当前状态、head 与实际 diff；内部审查发现的不足不直接搬入 Issue 回复。

多 PR 并行核查共用同一组 Issue 诉求标识，逐 PR 返回 [automation.md](automation.md) 要求的 `coverage_review`：覆盖点、证据、版本匹配和已读 `head_sha`。协调者保留全部有效关联 PR，统一复核并交现有执行器选择；自提优先、覆盖面选择、失效 PR 排除及两开关的边界不变。子任务结论不产生外部写授权。

调查者只读源码、Git 历史及 API，只写各自的结果目录，不修改共享分类输入、运行状态或配置，不发布。复用同批快照，必要 API 查询遵守 toolkit 的共享限流。草稿文件只放可直接发布的正文；候选账号、材料清单、缺口及 `response_review` 放独立结果文件，不附在回复正文后。按任务返回适用内容，纯范围调查不拟稿：

- **范围**：建议 level、问题版本、实际故障/文档路径、入口或支持范围证据；kernel 才用 arch35 路径门禁。
- **证据与诉求**：正文已提供什么；实际看过的源码/文档/PR及结论；仍缺什么。证据支持不了结论就保留未知，不能虚构路径或接口结果。
- **完整正文**：每个 Issue 单独一份 Markdown 草稿，复杂问题用小标题；直接回答能从源码查清的问题，不索要已有信息。
- **转交**：本项真正涉及的算子，是否仍有维护工作需要 owner。候选调查可单独委派并跨同实现复用；需要候选时按 [候选输出格式](operator-owner-candidates.md#状态字段) 返回账号对应的算子、简述及可回查的补丁/身份证据，不能只交整单人名列表。

不要求子 agent 加载整个状态 schema 或写完整运行状态；由协调者映射已有字段。返回消息仅概述结论、疑点和文件路径，详细证据留文件。共享根因仍逐项核对原文，不能把一条的现象写进另一条。拟稿者交稿前按 `response-writing.md` 检查实际 `reply.md` 并保存简短 `response_review`；调查笔记不能直接作外部结尾。

## 逐项响应材料

每个 `need_attention` Issue 在 `.cannbot/gitcode-issue-handler/reports/<run_id>/issues/issue-<iid>/` 单独保存 `analysis.md` 和适用的 `reply.md`、`assign.md`。进入响应准备时先保存已知分析，随调查更新；分析简写实际判定依据、相关 PR 与选择理由、计划动作和阻塞。`reply.md` 是完整可发布草稿；只需分配时分析两三行即可，`assign.md` 只写 `/assign @login`，不生成无必要的文字首响。回复和分配都需要时保存两份稿件。

自动响应开启时先落盘再执行，关闭时同样保存材料并列出待用户指令的动作。受阻项也须保存分析和能确定的草稿；尚不能形成稿件时记录具体缺口，不编造回复或分配对象。调查笔记不替代最终材料，由协调者审核并归入上述目录，在本项 `response_artifacts` 记录可读文件路径。

将评论和分配的 `--result-file` 放在该 Issue 目录。两个执行器预览时就会保存分析与草稿，`response-artifacts.json` 汇总路径及正文摘要；若结果文件放在运行根，则自动写到其旁的 `issues/issue-<iid>/`。Agent 在 `analysis.md` 补充实际分析，将分配结果的 artifacts 或 `response-artifacts.json` 的 files 映射到本项 `response_artifacts`，其他执行状态继续写唯一 run_state。分配实际使用原生 PATCH，`assign.md` 是用户可读的分配稿，不重复发布为评论。

response 阶段将首响和 PR 作者分配作为独立 operation，一次准备并按依赖完成；首响已完成而分配失败时只恢复分配，不等下轮重新分类才补动作。写前刷新必要评论、PR 和负责人证据，变化后重算剩余动作；写入结果未知先回查。只需分配的项目在分配回查成功后才完成本阶段，不要求文字回复文件。

## 协调者合并

1. 收到范围证据后写入原始输入的 `responsibility_review`，按 [intake 的快照复用规则](issue-intake.md#步骤-2a固定规则分类) 对受影响项重分类，传同批 PR 快照并合并保留其他结果，不推进全批游标或误报完成；不同意见回到实际文件/版本核验，不能投票决定。
2. 对本轮实际需回复项复核调查者证据和草稿，删掉重复提问、未来调查代替现有答案、PR 内部审查意见和空洞收尾；引用显式关联 PR 时只说明相关方案与必要状态，无关联时不展示潜在 PR。
3. 独立就绪项按 `post_triage_comment.py` 发布并回查，不等全批草稿或 owner 查询完成。
4. 报告前按本轮全部 `need_attention` 清单逐项核对：分析可读，所需稿件存在且与当前证据一致，缺稿有具体原因，`response_artifacts` 指向最终文件。收齐候选调查和剩余项目的明确结果，或记录未完成任务及恢复点；缺少子任务结果不能写成“未找到”或全批完成。范围外仍按责任配置只列举或汇总，不进入回复/候选调查。

委派任务不传旧轮完整回复作为答案，不把“让子 agent 调查”写进对外评论。程序性的 POST/回查仍由协调者统一执行，避免重复发送。

测试仓无法真实覆盖的身份、指派、状态迁移或硬件场景，可委派本地演练：给出模拟输入、预期动作与状态，再核对实际规则或纯函数结果。报告单列演练及未实测部分，不伪造远端成功、首响指标或硬件结果。
