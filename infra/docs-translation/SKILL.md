# 文档翻译Skill

## 功能描述

该翻译skill用来翻译开源仓的指定`*.md`文档，算子仓和非算子仓共用该skill，仅在有差异的地方，分开单独描述，不同的仓参考不同的要求。[翻译标准](./references/translation-style-guide.md)与[质量检查清单](./references/quality_check.md)采用同一份。

- 非算子仓翻译：翻译非docs目录以及docs目录下排除列表外的md，排除列表来自exclude_docs.json，该json文件只有非算子仓才会读取，算子仓不读取

- 算子仓：

  待翻译范围为算子仓中的`.md`文件，满足以下任一条即排除：

  1. 位于仓库一级目录`docs/`或`experimental/`下（整体排除，含其内任意层级子目录，包括其中的`zh`文件夹；其他层级下的同名目录不受影响）
  2. 文件名匹配`aclnn*.md`、`torchapi_*.md`、`*Pass.md`（即aclnn接口文档按**前缀**匹配，如`aclnnUpsampleNearest2d.md`被排除、`Xxx.aclnn.md`这种后缀形式不在排除之列）
  3. 位于`.git`目录下（**仅指git版本库元数据目录本身**。`.gitcode/`、`.github/`等平台配置目录不在排除之列，其中的md文件——如`PULL_REQUEST_TEMPLATE.zh-CN.md`——需要正常翻译）
  4. 本身是译稿：文件名以`_en.md`或`.en-US.md`结尾，或位于任意`en`文件夹下

使用方法与排除配置说明见 [references/usage.md](references/usage.md)（exclude_docs.json 仅非算子仓读取）。

**协作模式前提（两条翻译线均适用）**：本仓采用"谁修改中文、谁负责同步翻译对应英文稿件"的协作方式，中文文档与英文译稿随同一提交更新；英文译稿不存在时按全量翻译处理，源文档变更而译稿未同步时按增量翻译处理。第6步基础变更检测中的修改时间兜底用于发现未按该约定同步的变更（译稿提交时间早于源文件修改时间时按有变更处理）。

## 输入与依据文件

| 项 | 位置 | 说明 |
| --- | --- | --- |
| 翻译源目录 | 用户本地 | 已clone到本地的仓库路径，用户在对话中指定；未指定时按执行流程第1步交互获取 |
| `translation-style-guide.md` | references | 翻译标准（怎么译），基于Google开发者文档风格指南整理；**翻译开始前必须完整读取**（见执行流程第7步） |
| `quality_check.md` | references | 质量检查清单（查什么），第8步逐篇自查与第10步整体验证的判定基准；**翻译开始前必须完整读取**（见执行流程第7步） |
| `usage.md` | references | skill部署与使用方法说明（含exclude_docs.json配置说明，排除配置仅非算子仓使用） |
| `exclude_docs.json` | `<skill_dir>/` | 非算子仓排除列表配置，**仅非算子仓读取**；不存在时视为无排除项（详见“配置文件说明”） |

## 触发条件

满足任一条件即触发本skill：

- 用户要求翻译文档、生成或更新英文文档、准备英文版PR
- 用户提及 docs-translation
- 用户指定的md文档不存在对应英文翻译（`_en.md`或en目录同名文件），或原文档相比已有翻译发生变更

## 译稿存放规则（通用，唯一规则，按顺序判断，命中即止）

| 顺序 | 条件                                                         | 译稿位置与示例                                               |
| ---- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 1    | 文件名以`.zh-CN.md`结尾（如PULL_REQUEST_TEMPLATE、ISSUE_TEMPLATE） | 同目录，将文件名中的`zh-CN`替换为`en-US`，不加`_en`：<br>`.gitcode/PULL_REQUEST_TEMPLATE.zh-CN.md` → `.gitcode/PULL_REQUEST_TEMPLATE.en-US.md` |
| 2    | 位于某个`zh`文件夹下（`zh`可出现在任意层级）                 | 该`zh`同级的`en/`目录下，`en`内层级与`zh`内一致，文件名与原文一致，不加`_en`：<br>`guide/zh/api/quantize.md` → `guide/en/api/quantize.md`<br>`design/modules/zh/intro.md` → `design/modules/en/intro.md` |
| 3    | 其余情况                                                     | 与源文件同目录，命名为`<原文件名>_en.md`：<br>`README.md` → `README_en.md`<br>`src/api/intro.md` → `src/api/intro_en.md` |

**为什么zh下文档不加`_en`后缀：** zh和en目录已区分中英文，无需后缀；保持目录结构一致便于对照管理。不在zh内的文档使用`_en`后缀，因为同一目录下需要区分中英文。

## 执行流程

### 1. 交互式获取本地仓库路径（通用，必须首先执行）

**不通过远程地址推断仓库名，不自行克隆仓库**，本地仓库路径一律由用户提供。

**场景A：用户仅提供远程地址或仓库名（未提供本地路径）**

> **🚩 红线（仅当用户未提供本地路径时）**：用户只给远程地址或仓库名时，必须实际发起一次交互式提问工具（question）调用索取本地仓库路径；**用户已提供本地路径（如`D:\WorkSpace\ops-nn`）时，禁止再就路径提问**，直接进入校验。
>
> - **禁止在未提供路径时仅以普通文本追问路径**（例如"请告诉我你的仓库路径"这类纯文本回复）
> - **禁止从远程地址推断本地仓库路径**
> - **禁止自行克隆仓库**
> - 未提供路径且未发起 question 工具调用，即视为本步骤未完成，不得进入第2步

**必须执行的动作：**

1. 立即发起一次 question 工具调用，要求用户提供已 clone 到本地的仓库绝对路径。
2. 在发起 question 调用的同一条回复中，必须明确写出"将使用交互式提问工具（question）"（不能只写"请提供路径"而不提工具）。

**question 工具不可用时的等价处理**：若当前会话的工具列表中没有 question（如纯文本评测或受限环境），仍必须在回复中明确写出"将使用交互式提问工具（question）向用户索取已 clone 的本地仓库路径"，并给出完整的问题文本与候选项，然后等待用户补充路径；不得因工具缺失就表述成"本会话无 question，改用文本索取"，也不得跳过该环节继续扫描或翻译。

**question 工具调用示例（必须照此形式实际发起，而不是在文本里复述这段 JSON）：**

```json
{
  "questions": [
    {
      "question": "请提供已 clone 到本地的仓库绝对路径（例如 D:\\WorkSpace\\metadef_trunk）。我不会通过远程地址推断路径，也不会自行克隆仓库。",
      "header": "本地仓库路径",
      "options": [
        {"label": "我直接输入路径", "description": "选择此项后输入本地仓库的绝对路径"}
      ]
    }
  ]
}
```

**答复必须包含以下四要素：**

1. 不会通过远程地址推断本地仓库路径，也不会自行克隆
2. 将使用交互式提问工具（question）向用户索取clone到本地的仓库路径
3. 拿到路径后会校验：路径存在且为git仓库（路径下存在`.git`目录），校验失败则重新提示输入
4. 后续扫描、翻译、提交等所有操作均以该路径为仓库根目录

**首次回复口径模板（可直接套用，四要素缺一不可）：**

```text
我不会通过远程地址推断本地仓库路径，也不会自行克隆仓库。
接下来我会调用交互式提问工具（question），请你提供已 clone 到本地的仓库路径。
拿到路径后我会校验：路径存在且为 git 仓库（存在 .git 目录），校验失败会重新提示输入。
后续扫描、翻译、提交等所有操作，均以该路径为仓库根目录。
```

**场景B：用户已提供本地路径（如`D:\WorkSpace\metadef_trunk`）**

直接校验路径存在且为git仓库（路径下存在`.git`目录）；校验通过后，后续扫描、翻译、提交等所有操作均以该路径为仓库根目录（在该目录下执行扫描、git等命令）。

**校验失败的处置（按顺序，不得跳步）：**

1. **先按仓库名判定类型**：无论路径是否可访问（含跨平台路径，如 Linux 环境下的`D:\WorkSpace\ops-nn`），先取路径的 basename 按第2步判定仓库类型；basename 可确认时（如`ops-nn`以`ops-`开头），必须在回复中先给出类型判定结论与对应执行口径（算子仓：不读取 exclude_docs.json，按固定排除规则执行，翻译前先同步远端仓库），**不得以路径不可访问为由提问仓库类型、也不得因此中断或改问路径**。
2. **说明路径问题但不替代判定**：可附带说明"该路径在当前环境不可访问，请提供本机可访问的同仓路径"，但该说明不得取代第1点的类型判定与流程说明。
3. **仅在 basename 无法判定时才提问**：basename 既不匹配`ops-*`、也不属于已知非算子仓时，按第2步"无法确定（必须提问）"处理。

### 2. 仓库类型判断（通用）

**判定优先级（通用）**：仓库类型一律以路径 basename 判定，**判定优先于路径可用性**。即使路径不存在、不可访问或为跨平台路径，只要 basename 可确认类型，就必须先给出类型判定与对应执行口径，不得转而提问仓库类型或路径；路径可用性问题另行说明，不作为提问理由。

**场景执行总则**：后续步骤中标注"（通用）"的两类仓库均执行；标注"算子仓"或"非算子仓"的，仅对应类型仓库执行。

- **算子仓（可确认，不提问）**：仓库目录名（basename）以`ops-`开头，如ops-nn、ops-cv、ops-transformer、ops-math、opbase。确认后直接按算子仓要求执行：不读取exclude_docs.json；按固定规则排除（一级`docs/`、`experimental/`整体排除；`aclnn*.md`、`torchapi_*.md`、`*Pass.md`；`.git`目录；已有译稿）；翻译前先同步远端仓库（第3步）

  **回答口径模板（basename 可确认时直接套用，不得提问）：**

  ```text
  根据仓库名 ops-nn（以 ops- 开头）可确认是算子仓，无需提问，直接按算子仓流程执行：
  不读取 exclude_docs.json；按固定规则排除（一级 docs/、experimental/ 整体排除，
  文件名匹配 aclnn*.md、torchapi_*.md、*Pass.md 排除，.git 目录排除，已有译稿不重复翻译）；
  翻译前先同步远端仓库，再扫描并统计待翻译文件。
  ```

  > 注：即使给出的路径在当前环境不可访问，也必须先输出上述判定与执行口径；路径问题可在其后单独说明。

- **非算子仓（可确认，不提问）**：basename属于已知非算子仓，如metadef、ge、pypto、runtime、driver
- **无法确定（必须提问）**：basename既不匹配`ops-*`、也不属于上述已知非算子仓时，回复中必须写明判定依据（如"my_repo不匹配`ops-`开头，也不属于metadef/ge/pypto等已知非算子仓"），并立即发起一次question调用请用户确认仓库类型；未发起视为第2步未完成，不得进入第3步

### 3. 同步远端仓（通用）

目的：确保待翻译文件为最新版本。

```bash
OLD_HEAD=$(git -C <仓库路径> rev-parse HEAD)
git -C <仓库路径> pull
git -C <仓库路径> diff --name-only $OLD_HEAD HEAD -- "*.md"
```

- 第三条命令输出"本次同步发生变更的md清单"，供第6步判断使用
- 用`date '+%Y-%m-%d %H:%M:%S'`记录本次同步完成时间，供第11步报告使用
- pull失败（网络、冲突等）时停止并报告用户，不得继续后续步骤
- 本地分支与远端主分支分叉导致pull无法合并（如无跟踪信息）时：新建分支跟踪远端主分支（如`git switch -c <分支名> origin/master`）并以远端主分支为比对基准与工作基线，旧分支保留不删除

### 4. 扫描与筛选待翻译文件

扫描用户本地仓库的所有`.md`文档（排除.git目录），**必须先统计排除路径文件数量，再计算实际需翻译数量**（避免误导用户认为需要翻译所有文件）。

**扫描流程（以下命令需在bash中执行，工作目录为仓库根目录）：**

**统计总md文件数量（通用）**

```bash
find . -name "*.md" -not -path "./.git/*" -type f | wc -l
```

#### 非算子仓：按exclude_docs.json排除

1. **读取排除列表配置**（`<skill_dir>`为SKILL.md所在目录，与待翻译仓库位置无关；bash命令中写作`${skill_dir}`）

   ```bash
   cat "${skill_dir}/exclude_docs.json"
   ```

2. **统计排除路径文件数量**：根据excludeDocsPaths的**实际配置动态构造**命令（不得照抄示例中的路径），例如配置为`docs/dflow_api`时：

   ```bash
   find . -name "*.md" -not -path "./.git/*" -path "*/docs/dflow_api/*" | wc -l
   ```

3. **计算实际需要翻译的文件数量**

   ```text
   实际需翻译数量 = 总文件数 - 排除路径文件数
   ```

**统计报告格式（向用户输出）：**

```text
扫描结果：
- 总md文件：1495个
- 排除路径（跳过）：1345个
  - docs/dflow_api：401个
  - docs/graph_engine_api：843个
  - docs/llm_datadist_api：101个
- 实际需翻译：150个
```

#### 算子仓：按固定排除规则扫描（不读取exclude_docs.json）

分两次扫描后合并清单：

```bash
cd <仓库路径>

# 仅排除.git本身；.gitcode/、.github/等平台配置目录正常扫描

# 清单A：zh文件夹下的md（docs/、experimental/整体排除）
find . -type f -name "*.md" -path "*/zh/*" \
  -not -path "./.git/*" \
  -not -path "./docs/*" \
  -not -path "./experimental/*" \
  -not -path "*/en/*" \
  -not -name "aclnn*.md" \
  -not -name "torchapi_*.md" \
  -not -name "*Pass.md" \
  -not -name "*_en.md" \
  -not -name "*.en-US.md"

# 清单B：不在任何zh文件夹下的md
find . -type f -name "*.md" -not -path "*/zh/*" \
  -not -path "./.git/*" \
  -not -path "./docs/*" \
  -not -path "./experimental/*" \
  -not -path "*/en/*" \
  -not -name "aclnn*.md" \
  -not -name "torchapi_*.md" \
  -not -name "*Pass.md" \
  -not -name "*_en.md" \
  -not -name "*.en-US.md"
```

合并A+B得到待翻译清单（仓库相对路径），并向用户输出统计：

```text
扫描结果：
- 排除docs/experimental目录：N个
- 排除特定文件名（aclnn*.md、torchapi_*.md、*Pass.md）：M个
- 待翻译清单：K个
```

### 5. 确定实际翻译范围

**通用判定规则**：对清单中每个源文件，先按「译稿存放规则」得到译稿路径，再按下表判断：

| 条件 | 动作 |
| --- | --- |
| 译稿不存在 | 全量翻译 |
| 译稿已存在，且源文件有变更（变更检测见第6步） | 增量翻译（仅翻译变更部分，更新译稿） |
| 其余情况（译稿已存在且源文件无变更） | 跳过 |

**回答口径（凡涉及"已存在英文文档如何处理"的答复，必须按以下顺序完整表述，缺一不可）：**

1. **先查译稿**：先按「译稿存放规则」确定译稿路径，检查英文翻译文件是否已存在（不存在则全量翻译）
2. **再查变更**：译稿已存在时，再检查中文源文档是否有变更（变更检测见第6步）
3. **有变更 → 增量翻译**：获取中文文档的 diff、分析变更点、将变更点翻译为英文，用 edit 工具仅更新对应位置，不重写整个文件
4. **无变更 → 跳过**：源文件无变更时跳过该文件，不重复翻译、不改动已有译稿

> 即使用户在提问中已说明"中文文档最近改动了"，也必须完整说明"先查译稿是否存在、再查源文是否变更、无变更则跳过"这一判定顺序与全部三个分支。

#### 非算子仓：repoName模糊匹配与排除列表

**步骤1：将本地仓库路径与repoName模糊匹配**

- 匹配规则：本地仓库路径包含repoName关键字即匹配成功（如`D:\WorkSpace\ge_test`包含`ge`匹配成功，`metadef_trunk`匹配`metadef`）
- 匹配到多个repoName时，取关键字最长的配置项
- 匹配成功 → 读取该配置项的excludeDocsPaths；未匹配 → 无文件排除，整个仓库进行翻译

**步骤2：逐个文档判断**

```text
1. 文档是否在docs目录下？
   → 否：需要翻译
   → 是：继续
2. 已匹配repoName时，文档路径是否在excludeDocsPaths中？
   → 是：跳过（该路径由专业翻译人员负责）
   → 否：需要翻译
3. 是否已存在对应翻译文件？
   → 否：需要完整翻译
   → 是：检查原文档是否有变更（见第6步）
      → 有变更：需要增量翻译
      → 无变更：跳过
```

**回答口径（凡涉及排除判断的答复，必须包含以下三点，缺一不可）：**

1. **匹配结果**：本地仓库路径与repoName做模糊匹配，路径中包含repoName关键字即匹配成功（给出本次具体匹配说明）
2. **命中跳过**：在excludeDocsPaths中的docs子路径跳过翻译（该路径由专业翻译人员负责）
3. **其余照常**：**不在排除列表中的其他docs路径仍照常翻译**

**示例：**

| 本地仓库路径 | repoName | docs路径 | excludeDocsPaths | 是否翻译 |
| ----------- | -------- | ----------------------------- | ----------------- | --------- |
| `D:\WorkSpace\ge_test` | ge | `docs/graph_engine_api/xx.md` | `["docs/graph_engine_api"]` | 跳过（在排除路径） |
| `D:\WorkSpace\ge_test` | ge | `docs/architecture/xx.md` | `["docs/graph_engine_api"]` | 翻译（不在排除路径） |

### 6. 检查译稿是否存在并检测变更

**检查译稿是否存在（通用）：** 按「译稿存放规则」确定译稿路径后检查：

- 源文件不在zh文件夹下：检查同级`<原文件名>_en.md`
- 源文件位于某个zh文件夹下：检查`<zh父路径>/en/<zh后的路径>/<原文件名>`

```bash
ls README_en.md                  # 非zh下文档
ls guide/en/api/quantize.md      # zh下文档
ls docs/design/overview_en.md    # docs内非zh下文档
```

**基础变更检测（通用，译稿已存在时）：**

```bash
# 方式1：与上一次提交比较
git diff HEAD~1 -- <文件>

# 方式2：检查工作区状态（覆盖未提交改动）
git status <文件>

# 方式3：获取变更统计
git diff HEAD~1 --stat -- <文件>
```

> **注意**：`git diff HEAD~1`仅覆盖最近一次提交。若原文档在更早提交中已修改而翻译文件未同步，需结合修改时间判断：分别用`git log --format="%ci" -1 -- <原文件>`和`git log --format="%ci" -1 -- <翻译文件>`获取最后修改时间，原文件修改时间晚于翻译文件时按有变更处理；无法确定时按有变更处理（宁多勿漏）。

**算子仓增量候选集**：步骤3同步变更清单中**存在对应译稿**的源文件，是否增量以本步"基础变更检测"为准（源文件有变更→增量翻译，无变更→跳过）。

### 7. 读取翻译标准（通用，必须执行）

> **⚠️ 重要警告：翻译前必须先读取翻译标准！遗漏此步骤会导致翻译不符合规范，需要返工修正！**

**必须在翻译任何内容之前**，完整阅读以下两份参考文档并逐条遵守：

- [references/translation-style-guide.md](references/translation-style-guide.md)：翻译标准（怎么译），基于英文风格指南 <https://developers.google.com/style> 整理
- [references/quality_check.md](references/quality_check.md)：质量检查清单（查什么），第8步逐篇自查与第10步整体验证均按其执行

**核心红线（详见参考文档）：**

- **语态时态**：主动语态优先，操作指引一律祈使句（"Select..."而非"You can select..."）；一般现在时为主，操作后的瞬时结果不用将来时
- **句子结构**：每个句子必须有明确主语和动词；反直译，译文须能脱离中文原文自然成立；每句不超过25个单词
- **词汇**：禁用 via、e.g.、i.e.、etc.、can't、it's、don't、thus、figure out 等；缩略词写全称（cannot、do not）
- **冠词**：正文句子中单数可数名词前必须有冠词；特指用the，泛指用a/an（表格单元格名词词组除外）
- **术语**：中文"接口"一律译为API，**译文绝对禁止出现interface**；术语表命中即用且全文一致（样例→sample、算子→operator、张量→tensor、开发者→you等）
- **固定句式**："是否XXX"→Whether XXX（禁止Indicates whether/Specifies whether）；"返回XXX"→Returns XXX.；"无"→None（不加句号）；列举清单最后一项前统一加and
- **标题**：API文档章节标题命中固定映射表即替换（功能说明→Description、参数说明→Parameters、示例→Examples等），复数形态不可更改，标题层级不变
- **格式镜像**：中文源文是什么格式，英文就是什么格式，逐处一致、一字不差；译文中每个`**`/`` ` ``/`\_`必须能在中文源文对应位置找到依据，找不到立即删除；禁止自行加粗/加code、禁止格式升级/降级/迁移
- **代码块**：整体保持原样，仅翻译其中的注释；代码样式与字符不可改动
- **文件末尾**：必须保留一行空行（以单个换行符结尾，MD047）；增量编辑后同样保证
- **非断行连字符**：U+2011统一替换为ASCII连字符`-`

### 8. 执行翻译

**总体流程（通用）：逐篇完成"翻译+自查"。** 每篇译稿写完后立即按[references/quality_check.md](references/quality_check.md)检查，不满足要求须修正（必要时重翻）后方可进入下一篇。待**全部**待翻译文件完成后，再进入第10步整体验证，兜底单篇自查的疏漏（如语义相反、误加切换行、链接失效等）。

**不存在翻译文件（完整翻译，通用）：**

1. 使用read工具读取中文文档完整内容
2. 按翻译标准进行完整翻译
3. 按「译稿存放规则」确定存放位置并创建翻译文件

**已存在翻译文件且有变更（增量翻译，通用）：**

1. 使用bash工具获取中文文档的变更内容（diff）。算子仓的变更起点取步骤3记录的OLD_HEAD（本次同步变更）；若变更由更早提交引入，用`git log --oneline -- <源文件>`定位译稿最近一次同步翻译之后的源文件变更提交作为起点，命令形如`git diff <变更起点> <工作基线> -- <源文件>`
2. 分析变更点
3. 将变更点翻译成英文
4. 使用edit工具更新对应的英文文档，**仅更新变更部分，不重写整个文件**

**其他要求（通用）：**

- 若待翻译文件超过50篇，每30篇分批处理并报告进度；单文件超过500行时，建议每200行分批翻译

- 记录每篇的字数（口径见第11步），供完成报告使用

- **行内标签与结构保真**：`<term>`等行内标签、`<!-- npu="X" idN -->`或`<!-- end idN -->`等标记注释必须与源文件一一对应（数量与位置不变），**不得为源文件中没有标签的内容补加标签**（无`<term>`包裹的产品名按纯文本翻译）；表格行、列表项、标题层级数量不得增减

- **文档链接改写**：译稿中指向本仓库资源的链接（相对路径，或指向本仓库的URL中`blob/<分支>/`后的仓库内路径），按唯一原则处理：目标资源存在对应译稿（即英文版文件，含文档与图片等资源）则改写为指向译稿，不存在则保持原链接。改写示例：`README.md` → `README_en.md`、`guide/zh/api/x.md` → `guide/en/api/x.md`、`X.zh-CN.md` → `X.en-US.md`、`docs/zh/figures/x.png` → `docs/en/figures/x.png`。指向其他git仓库的链接及外部链接，无论其目标文档是否有译稿，一律保持原链接不变（本skill仅改写本仓库文档的链接）。**例外：语言切换行中指向中文原README的链接不改写**

- **文档内锚点**：源文件中`[xxx](#中文标题)`形式的文档内锚点链接，必须同步改写为译后英文标题对应的锚点，并确保锚点与译稿标题一一对应、无失效链接

- **语言切换行**：**仅当源README中已包含切换行时才处理**（形态见下方示例），译稿中原位改写（当前语言English为纯文本不可点击，位置与源文一致），链接指向对应的中文原README；**源README中不含切换行时，译稿不添加切换行、不做任何处理**（与源文保持一致）。切换行形态：

  ```text
  简体中文 | [English](README_en.md)
  ```

  **链接路径**（仅源README含切换行时适用）：按译稿与中文原README的实际相对位置确定：同目录译稿（`README_en.md`）的切换行链接指向 `./README.md`；译稿在`en`文件夹时，中文原README路径为译稿路径将`en`替换为`zh`，如`guide/zh/README.md`译为`guide/en/README.md`后，切换行写作：

  ```text
  English | [简体中文](README.md)
  ```

  **固定指向**：切换行链接不参与"文档链接改写"，后续批量改链、按新译稿补改链接时均**不得改动**该链接。

### 10. 整体验证（通用）

全部译稿写完后统一执行，**整体验证只有两层**：

1. **第一层：机械验收**——脚本化、全覆盖核查（见 10.1）
2. **第二层：语义审查**——逐篇对照源文件（见 10.2）

两层发现的问题都修复后必须**回归复检**，直至全部通过。**修复与回归复检是上述两层的收尾动作，不属于第三层验证**；对外表述（含回答用户、写报告）一律称为"两层验证"，不得表述为"三层验证"。

**全程禁止修改源文件**：翻译、验证、修复各环节一律只允许新增/修改译稿文件，源文件必须保持零改动（最终以`git status`复核）。

#### 10.1 机械验收（脚本化核查，不依赖翻译执行方自报）

对下列清单逐项脚本化核查（可对全部译稿一次性扫描，也可按批次执行后汇总）：

| #    | 检查项     | 通过标准                                                     |
| ---- | ---------- | ------------------------------------------------------------ |
| 1    | 译稿齐全   | 每篇源文件均有对应译稿且非空                                 |
| 2    | 残留中文   | 译稿非代码区无中文字符。例外仅限：语言切换行中的`[简体中文]`、数学公式内与源文件一致的原文、保留链接中的锚点、原样引用的中文串（版权串、平台标签等） |
| 3    | 全角标点   | 同上范围为无全角标点（，。；：？！（）《》""''【】）         |
| 4    | 语言切换行 | 源README含切换行时，译稿在原位置有切换行且链接指向中文原README；**源README不含切换行时，译稿同样不含切换行；非README译稿无切换行** |
| 5    | 行数比对   | 按[references/quality_check.md](references/quality_check.md)第15项执行（漏译检测，阈值30%） |
| 6    | 链接有效   | 译稿中相对链接的目标文件在仓库内存在，锚点与目标文件的（译后）标题对应；切换行链接除外（固定指向中文原README） |
| 7    | 结构对齐   | `<term>`、`<!-- npu=... -->`/`<!-- end idN -->`、`$$`、表格行、列表项、标题数量、√/×符号个数与源文件一致（对源文件自身格式瑕疵的合理规范化须记录说明） |
| 8    | 数值一致   | 版本号等数值在译稿中无缺失                                   |

#### 10.2 语义审查（逐篇对照源文件）

- 逐篇将译稿与中文源文件对照，检查**错翻**（含支持状态逐行核对、否定语义、术语、产品名称映射、数学语义词）、**漏翻**（句子/子句/表格单元格/列表项/约束说明缺失）、**多翻**（凭空添加的内容、多余限定）；判定基准与规则见[references/quality_check.md](references/quality_check.md)
- 待翻译文件较多时按批次审查（每批≤30篇，可并行）；审查只做**最小必要修复**（edit译稿对应位置），不得借机重写或调整格式
- 无法机械判定的疑难项记录后交由用户决策，不得擅自取舍

**修复原则（必须遵守）**：只做**最小必要修复**——仅用 edit 修改问题所在位置，不重写文件、不借机调整格式、不扩大改动范围。

**回答口径（凡涉及"翻译后做哪些验证"的答复，必须包含）：**

1. **两层验证**：先机械验收（译稿齐全、残留中文、全角标点、语言切换行、行数比对、链接有效、结构对齐、数值一致），后语义审查（逐篇对照源文件检查错翻、漏翻、多翻）；不得表述为"三层验证"
2. **最小必要修复**：语义审查发现问题只做最小必要修复，仅改问题位置，不重写文件、不调整格式
3. **回归复检**：两层问题修复后回归复检直至全部通过；源文件保持零改动（以 git status 复核）

#### 修复与回归复检（两层验证的收尾动作，非第三层）

- 每处修复记录：文件、位置、问题分类（错翻/漏翻/多翻/格式）、修复内容
- 修复完成后重新执行 10.1 机械验收（语义修复后重点复跑残留中文、结构对齐、链接有效三项），直至全部通过
- 源文件零改动复核：`git status`应显示源文件无变更

### 11. 完成报告（通用）

在仓库同级目录生成`<仓库名>_translate_report_YYYYMMDD_HHMMSS.md`（文件名带生成时刻的时间戳，如`ops-cv_translate_report_20261029_174524.md`；同目录历史报告保留，**不得覆盖**。UTF-8编码，仅备查，**不参与提交**），包含四部分：

> **报告相关答复的必答要点**：凡回答"翻译报告"相关问题，必须同时点明四点——①位置为仓库同级目录（不在仓库内）；②文件名规则`<仓库名>_translate_report_YYYYMMDD_HHMMSS.md`（带时间戳）；③不覆盖历史报告；④仅备查、不参与提交。回答"提交/报告"类问题时还须同时覆盖第12步「提交相关答复的必答要点」全部五点。

1. **汇总**：远端同步时间（步骤3记录）、本次翻译N篇（全量X、增量Y）、跳过M篇、本次翻译总字数

2. **本次翻译文件清单**：表格（源文件 | 译稿 | 字数），含每篇字数与合计行

3. **排除文件清单**：本次未翻译的源文件，分两组（互不相交）各按字典序排列：

   - **排除规则命中**：算子仓为位于一级`docs/`、`experimental/`下的md文件及文件名命中排除规则的md文件（`aclnn*.md`、`torchapi_*.md`、`*Pass.md`）；非算子仓为excludeDocsPaths命中路径下的md文件
   - **译稿已存在且源文件无变更**：满足此两条件的源文件才跳过（译稿存在但源文件有变更的走增量翻译，不在此列）

   既有译稿文件本身不列入本清单（它与"译稿已存在而跳过"的源文件是同一对文件，列出会造成交叠）

4. **验证记录**：步骤10.1机械验收各项结果、步骤10.2语义审查发现的问题与修复清单（文件、分类、修复内容）、修复与回归复检结论（两层验证的收尾动作，非第三层验证）

字数口径：统计**源文件被翻译内容的中文字符数（CJK）**。全量翻译=源文件全文中文字符数；增量翻译=变更部分的中文字符数。

同时向用户简要输出：同步时间、翻译/跳过篇数、总字数、报告文件位置、需要用户知悉的事项。其中报告文件须完整说明四要素：位置为仓库同级目录、文件名`<仓库名>_translate_report_YYYYMMDD_HHMMSS.md`、不覆盖历史报告、仅备查不参与提交。

### 12. 提交变更到远程仓库（通用，仅用户明确要求时执行）

**仅在用户明确要求时执行**，默认不提交。

> **提交相关答复的必答要点（按序逐条覆盖，缺一即视为未答全）：**
>
> 1. **默认不提交**：skill默认不提交到远程仓库，仅用户明确要求时提交
> 2. **先建分支再提交**：提交前必须新建分支（`git switch -c docs/add-english-translations`），不直接在默认分支上提交
> 3. **单PR单提交**：全部译稿以单个提交推送；PR创建后需补充修改时，按序执行`git reset --soft HEAD~N` → `git add -A`（含图片等非md文件）→ `git commit -m "docs: update English translations for markdown files"` → `git log --oneline -3`确认只剩1个提交 → `git push -f`合并更新。**必须给出上述完整命令与其中的提交信息，不得只写"git commit"而不带`-m "docs: update English translations for markdown files"`**
> 4. **无权限兜底**：推送到origin返回403（无推送权限）时，通过平台API创建个人fork，将分支推送到fork，再通过API向上游仓库创建PR（`head`填`<fork用户名>:<分支>`，`base`填`master`）
> 5. **报告约束（四要素缺一不可）**：①在**仓库同级目录**（不在仓库内）生成`<仓库名>_translate_report_YYYYMMDD_HHMMSS.md`（带时间戳）；②不覆盖历史报告；③UTF-8编码；④仅备查、**不参与提交**（详见第11步）
>
> 回答"提交/报告"类问题时，上述五点须逐条覆盖，尤其不得遗漏第5点的报告四要素与第3点的完整提交命令。

1. 新建分支并提交全部译稿变更（**必须为单个提交**）：

    ```bash
    cd <仓库路径>
    git switch -c docs/add-english-translations
    git add -- "*.md"
    git commit -m "docs: add English translations for markdown files"
    ```

2. 推送并创建PR：

   - 先尝试推送到origin；若返回403（无推送权限），通过平台API创建个人fork（如`POST /api/v5/repos/cann/<仓库名>/forks`），将分支推送到fork，再通过API向上游仓库创建PR（`head`填`<fork用户名>:<分支>`，`base`填`master`）
   - PR标题用提交信息；PR正文按该仓库的PR模板填写，类型标签勾选Documentation update
   - 提交身份用平台账号信息（经`git -c user.name=... -c user.email=...`指定，不改动git全局配置）

3. **单PR单提交约束**：

   PR分支只允许保留一个提交。PR创建后如需补充修改（增量修正、图片重命名等），完成变更后按以下步骤将多个提交合并为一个，再强制推送更新PR：

   ```bash
   git reset --soft HEAD~N    # N为分支上的提交数；soft重置后原提交内容保留在暂存区
   git add -A                 # 将本次补充修改（含图片等非md文件）一并暂存，防止遗漏
   git commit -m "docs: update English translations for markdown files"
   git log --oneline -3       # 推送前确认：分支上只剩1个提交（其余为master基线提交）
   git push -f                # 强制推送更新PR
   ```

   不得让PR分支上出现多个提交。

**注意事项：**

- 提交前确保所有翻译文件都已创建或更新
- 提交信息应清晰说明翻译的内容
- 中文原文和英文翻译一起提交，保持同步；多个翻译文件批量提交（单个提交）

## 配置文件说明（仅限非算子仓）

### 排除文档配置

- **路径**：`<skill_dir>/exclude_docs.json`（与SKILL.md同级存放；`<skill_dir>`指skill文件所在目录，与待翻译仓库位置无关；bash命令中写作`${skill_dir}`）
- **作用**：定义公开产品文档仓库及其需要排除翻译的 docs 子路径；配置文件不存在时视为无排除项，整个仓库进行翻译
- **格式**：JSON格式，包含 mapping 数组，每个元素包含：
  - `repoName`: 仓库名（用于与用户输入的本地仓库路径进行模糊匹配）
  - `excludeDocsPaths`: 需要跳过翻译的 docs 子路径列表

  ```json
  {
      "mapping": [
        {
             "repoName": "ge",
             "excludeDocsPaths": ["docs/dflow_api", "docs/graph_engine_api", "docs/llm_datadist_api"]
        },
        {
             "repoName": "pypto",
             "excludeDocsPaths": ["docs"]
        }
     ]
  }
  ```

- **匹配规则**：
  1. 用户交互式输入本地仓库路径（见执行流程第1步）
  2. 将本地仓库路径与 repoName 进行模糊匹配（路径中包含 repoName 关键字即匹配成功；匹配到多个时取关键字最长的配置项）
  3. 匹配成功：该仓库 docs 目录下 excludeDocsPaths 中列出的子路径跳过翻译，其他docs路径照常翻译
  4. 未匹配：无文件排除，整个仓库进行翻译

## 注意事项

1. **路径获取（通用，重要）**：用户只给远程地址或仓库名时，必须实际发起 question 工具调用索取路径（无该工具时按第1步等价处理），禁止仅以普通文本追问、禁止从远程地址推断、禁止自行克隆；已提供本地路径时不再提问，直接校验路径存在且含`.git`目录，失败重新提示（见执行流程第1步）
2. **仓库类型（通用，优先于路径校验）**：以路径 basename 判定算子仓/非算子仓（`ops-*`为算子仓，metadef/ge/pypto/runtime/driver 为非算子仓），basename 可确认时直接给出判定与执行口径、不得提问，即使路径不可访问也不影响该判定；仅 basename 无法确定时才交互式向用户确认（见执行流程第1步场景B、第2步）
3. **同步与扫描统计（通用，重要）**：扫描前先同步远端仓；必须先统计排除文件数量，再计算实际需翻译数量，并向用户输出统计信息（见执行流程第3、4步）
4. **排除判断（非算子仓）**：docs目录下的文档需检查是否在排除列表中；凡涉及排除判断的答复，按第5步"回答口径"完整输出三点（匹配结果、命中跳过、其余照常）
5. **必须先读取翻译标准（通用）**：翻译任何内容前，必须先阅读[references/translation-style-guide.md](references/translation-style-guide.md)与[references/quality_check.md](references/quality_check.md)全文；翻译完成后执行质量检查（重点：行数比对±30%、格式镜像）
6. **文件存放路径与命名（通用）**：严格按「译稿存放规则」执行（zh下文档同名进en目录，其余同级加`_en`后缀；PR模板替换语言代码）
7. **增量更新（通用）**：先检查译稿是否存在，存在时再检查源文件是否变更；有变更仅翻译变更部分（不重写整个文件），无变更则跳过该文件（见执行流程第5步"回答口径"及第6、8步）；答复此类问题时按该"回答口径"完整表述判定顺序与三个分支
8. **格式一致性（通用）**：保持Markdown格式、表格结构、链接引用一致；格式镜像逐处对应源文
9. **源文件零改动（通用）**：翻译、验证、修复各环节一律只允许新增/修改译稿文件，源文件必须保持零改动（见执行流程第10步）
10. **提交变更（通用）**：仅在用户明确要求时提交；提交前先新建分支，将所有变更的中英文md文档以单个提交推送至远程仓库（见执行流程第12步）；答复提交与报告问题时，按第12步「必答要点」与第11步「报告必答要点」逐条覆盖
