# 通用API参考质检技能

## 概述

此 SKILL 用于对按《API参考写作模板》编写的 API 参考 Markdown 文档进行全面的质量检查，包括章节结构完整性、写作规范性、完备性与正确性。支持三种输入场景：直接输入 Markdown 内容、单个 Markdown 文档路径、多个 Markdown 文档路径或目录路径。技能按照"数据准备 - 执行分析 - 汇总输出 - 清理"的四步工作流执行检查。

本技能不检查通用 Markdown 语法、链接有效性、拼写等通用项（走 `infra/docs-common-review` 家族），仅聚焦《API参考写作模板》定义的 API 参考写作规则。

## 规则真源

`assets/rules.json` 的规则是《API参考写作模板》（官方真源：https://gitcode.com/cann/docs/blob/master/writing_template/API_reference.md ）写作要求的检查化转写。模板为唯一上游真源：模板更新时以模板为准同步修订规则，禁止在技能内另立标准或复制模板全文（知识依赖单向）。

## 使用场景

1. **一段Markdown内容**：用户输入一段 Markdown 内容
2. **一个Markdown文档**：用户输入一个 Markdown 文档的绝对路径
3. **多个Markdown文档/目录**：用户输入多个 Markdown 文档的绝对路径（用英文逗号分隔）或一个文档目录

## 重要执行原则

- **必须严格按规则描述的检查对象执行，禁止自行推断检查范围，宁可遗漏问题，也不能超出规则定义进行检查**
- **必须严格按照规则的描述检查，禁止将规则发散**
- **带【前提条件】的规则：条件不满足时跳过该规则，既不报告问题，也不视为已通过，禁止在无依据时臆断条件成立**
- **必须严格按照技能步骤执行**
- **步骤必须按顺序执行，严禁跳过任何步骤**
- **每次启动技能都必须按照用户输入重新读取Markdown文档**
- **严格按照文档内容检查，英文大小写必须按照文档中的内容匹配**
- **必须为每个Markdown文档单独分析**
- **只有在所有步骤都完成后才能退出skill**
- **必须严格遵守逐行扫描执行规范，发现问题时记录后继续扫描当前行剩余内容，禁止因发现一个问题而跳过同行后续检查**

## 详细检查工作流程（必须逐个步骤执行）

在执行任何步骤前，先对话中输出当前检查点：[CHECKPOINT: 开始]

**规则**：如果前一个CHECKPOINT未输出，禁止执行后一步骤。

### 步骤1：数据准备

一次性完成所有输入解析、规则筛选和文档列表生成，避免中间文件读写循环。

#### 1.1 解析参数与读取配置

- 获取用户输入中的 `--rules` 参数列表（如果存在）
- 检测用户输入内容是否为文件路径：
    - 如果是 `.md` 文件或者目录路径，则为文件路径模式
    - 如果不是，作为 Markdown 内容模式处理
- **文件路径模式**：直接使用文件路径作为处理文档路径
- **Markdown 内容模式**：
    - 从一级标题或函数原型确认文档对应的接口名；无法唯一确认时不阻塞检查（本技能无代码定位脚本，接口名仅用于临时文件命名），命名为 `auto_temp.md`
    - 将用户输入的 Markdown 内容写入 `output/docs-api-review/temp/<接口名>.md`，例如 `demoQueryDeviceStatus.md`，以便阅读与定位
    - 将该文件的绝对路径作为后续处理的文档路径

**检测是否是Markdown内容的标准**：

- 没有明显文档路径特征（如 `D:/...、/...、./...等`）
- 不包含文件扩展名或路径分隔符
- 极长的内容（超过单行命令行输入长度）

#### 1.2 读取规则并筛选

- 读取当前技能目录下 `assets/rules.json` 的全部规则
- 如果用户提供了 `--rules` 参数，按规则序号筛选对应规则；否则保留全部规则
- 将筛选后的规则按 `rule_item_name` 分组，保留在上下文中直接传递给后续步骤

#### 1.3 生成文档列表

- 读取当前技能目录下 `assets/exclude-files.json` 中的排除文件列表
- 根据文档路径生成待检查文件列表：
    - 单文件：直接加入列表
    - 目录：递归遍历该目录下所有 `.md` 文件，排除白名单中的文件名
- 将文档列表保留在上下文中

#### 1.4 清理历史结果文件

- 检查 `output/api-markdown-check-result.json` 文件是否存在
    - 如果存在，删除该文件，避免历史检查结果影响本次检查
    - 如果不存在，跳过此步骤

完成后必须在对话中输出 [CHECKPOINT: 数据准备完成]

### 步骤2：执行分析

#### 2.1 基础准备

- 确保 `output` 目录存在

完成后必须在对话中输出 [CHECKPOINT: 基础准备完成]

#### 2.2 批量检查文档

从文档列表中逐文件读取文档的完整内容，**必须使用带行号的方式读取**（例如通过脚本为每行添加行号前缀输出），确保每行内容与行号一一对应。

对每个文档（或文档中相互独立的组成部分）先执行**文档类型判定**，再按类型适用范围应用步骤1中已筛选的规则分组：

**文档类型判定（逐文档执行，判定依据按优先级）**：

1. **接口介绍类**：文档（或组成部分）存在"函数原型"章节，或存在"接口名 + 产品支持情况/功能说明/参数说明"结构的接口小节；
2. **自定义数据类型介绍类**：文档（或组成部分）包含"返回码/Enumerations/Structs/Typedefs"等自定义数据类型介绍部分，且不含接口小节；
3. **接口简介/总览类**：其余文档——内容为概述接口的主要功能、使用场景、接口分类、头文件和库文件等信息（如《接口简介.md》、overview 总览文档）。

一份文档同时包含多个部分时（如总览章 + 接口章），按组成部分分别判定与检查，章节结构类规则只作用于接口介绍部分。

**规则适用范围映射**：

| 文档类型 | 适用规则 |
| --- | --- |
| 接口介绍类 | 规则 1-3、5-25（按各规则自身前提条件执行） |
| 接口简介/总览类 | 仅规则 4；**禁止执行规则 1（章节结构）、2（标题层级）及其他接口介绍章节规则——此类文档不是单个接口的介绍，不因缺少功能说明/函数原型/参数说明/返回值说明而报问题** |
| 自定义数据类型介绍类 | 仅规则 26-29 |

判定结果与依据须在上下文中留有记录（如：该文档无函数原型章节、内容为接口分类与库文件概述，判定为接口简介类）。

逐个应用步骤1中已筛选的规则分组：

1. 获取当前规则分组下的所有规则文件列表
2. 对于每个规则：
    - **读取规则描述**：直接从上下文中的规则数据获取
    - **读取参考资料**：读取规则的参考资料（如果该规则有 `reference_doc_path`）；HTTP/HTTPS 链接直接访问对应官方资料（模板真源为 gitcode 上的《API参考写作模板》，本仓不携带模板副本）；网络不可达或链接失效时按 `rule_desc` 执行，不因参考资料缺失而跳过检查
    - **执行检查逻辑**：根据规则的 `rule_desc` 内容严格按照 **逐字逐行** 检查文档内容，不允许根据常识或经验进行扩展性检查
    - **前提条件判定**：规则带【前提条件】时先判定条件是否满足；不满足则跳过该规则，不视为已通过，禁止臆断条件成立
    - **检查结果格式**：检查出来的问题按照 **汇总结果说明** 和 **返回值字段说明** 的要求以及格式输出
    - **检查结果验证**：检查每个问题的描述和建议是否与发现问题的规则相互匹配
        - 如果不匹配，则剔除该问题结果
    - **保留结果到上下文**：将检查结果保留在上下文中，供步骤3直接汇总使用
        - 如果是非问题或者未发现问题，禁止将结果保留在上下文中

完成后必须在对话中输出 [CHECKPOINT: 批量检查文档完成]

### 步骤3：汇总输出

- 直接从上下文中汇总所有检查结果到 `output/api-markdown-check-result.json` 文件
- **禁止读回中间结果文件再写入**，直接从上下文中的分析结果汇总输出

完成后必须在对话中输出 [CHECKPOINT: 汇总输出完成]

### 步骤4：清理临时文件

- 删除`output` 目录下的 `docs-api-review` 文件夹

完成后必须在对话中输出 [CHECKPOINT: 清理临时文件完成]

## 逐行扫描执行规范（强制遵守）

### 1. 逐行扫描顺序

- 对每个文档按行号从小到大逐行检查
- 每行从左到右逐字符/逐词扫描
- 发现问题时记录后必须继续向右扫描当前行剩余内容，不得中断当前行的扫描
- 只有当当前行从左到右完整扫描完毕后，才能进入下一行

### 2. 同行穷举规则

- 当在某行发现规则违规时，必须继续检查该行剩余内容是否还存在同类或其他违规
- 禁止因已发现一个问题而跳过同行后续内容
- 每行必须从头到尾完整扫描后才能进入下一行
- 同一行同一规则可以命中多个问题，每个问题必须单独记录

### 3. 结论验证规则

- 行号必须从步骤 1 读取的带行号文档内容中直接获取，禁止凭记忆、心算、人工计数或估算推算行号
- 对每条检查结论（合规/不合规），必须先在原文中定位到具体字符后再判定，禁止凭对原文的印象或记忆下结论
- 无法在原文中精确定位对应内容时，必须回溯原文重新确认，禁止跳过
- 每条结论的判定依据须在上下文中留有原文对照记录（如：原文此处为XXX，符合/命中规则YYY的ZZZ要求）
- **用户凭印象或记忆给出行号（如"我记得第 N 行附近有问题"）时，禁止直接采用该行号**：正确做法是回到步骤 1 读取的带行号文档内容，定位问题实际所在行（如产品支持情况段落实际所在行），确认该行内容确实命中具体规则（如"产品支持情况未以列表形式呈现"）后再记录真实行号，且判定依据须在上下文中留有原文对照记录
- 被问及"是否可以直接把凭印象得到的行号写进质检结果"时，必须明确回答不可以，并逐条说明本《结论验证规则》纪律，回答须完整包含以下全部要点：
    1. 行号必须从步骤 1 读取的带行号文档内容中直接获取，禁止凭记忆、心算或人工计数推算
    2. 每条结论必须先在原文中定位到具体字符后再判定；无法在原文中精确定位对应内容时，必须回溯原文重新确认，禁止跳过
    3. 正确做法是回到带行号的文档内容，定位问题（如产品支持情况段落）实际所在行，确认该行内容确实命中对应规则后再记录真实行号
    4. 判定依据须在上下文中留有原文对照记录
    5. 说明上述要求来源于本技能 SKILL.md 的《结论验证规则》

## 规则文件说明

规则文件 `assets/rules.json` 包含检查规则的定义，每个规则包含以下字段：

- `rule_no`: 规则编号
- `rule_item_name`: 规则项名称
- `rule_name`: 规则名称
- `rule_type`: 规则类型
- `rule_desc`: 规则描述
- `rule_level`: 规则级别
- `reference_doc_path`: 参考文档路径（真源模板或官方资料）

规则覆盖的模板章节：接口简介、接口介绍（文档组织结构、类介绍、产品支持情况、功能说明、函数原型、参数说明、返回值说明、约束说明、调用示例）、自定义数据类型介绍（返回码、枚举、结构体、Typedefs）。

## 参数说明

用户输入可以包含 `--rules` 参数：

- 格式：`--rules 规则序号列表`
- 示例：`--rules 1,2,3`
- 多个规则序号用英文逗号分隔

## 汇总结果说明

最终的汇总结果只需要汇总步骤2中上下文里的分析结果，不需要按照问题类型、问题行数等合并检查结果，不需要读回中间文件。结果严格按照以下格式输出：

```json
[
  {
    "rule_group": "xxx",
    "rule_item": "xxx",
    "rule_type": "xxx",
    "rule_name": "xxx",
    "snippet": "xxx",
    "description": "xxx",
    "rule_level": "xxx",
    "file_name": "xxx",
    "line_number": "xxx",
    "location": "xxx",
    "suggestion": "xxx"
  }
]
```

### 返回值字段说明

- **rule_group**：问题大类。固定是 **通用API模板规则**；
- **rule_item**：问题类型。必须是发现问题的核心检查规则的**rule_item_name**；
- **rule_type**：问题类型。必须是发现问题的核心检查规则的**rule_type**；
- **rule_name**：问题名称。必须是发现问题的规则的**rule_name**；
- **snippet**：问题内容片段。
- **description**：根据规则的实际检查内容来生成的相应描述信息，不要包含问题行号；
- **rule_level**：问题级别。必须是发现问题的核心检查规则的**rule_level**；
- **file_name**：文档名称。必须是用户输入的Markdown文档的名称；
- **line_number**：问题行号。必须是发现文档的文档里问题所在行号；
- **location**：问题所在的行链接。文档的绝对路径且支持点击跳转，超链接默认支持VS Code。示例为：vscode://file/D:\\8.vs_workspace\\markdown_quality_checker\\bookmap.md:4
- **suggestion**：模型给出的问题修改建议。不要出现问题行号。

## 约束与边界

- **场景约束**：一段内容场景不校验依赖整篇文档结构的规则（API章节结构完整性/顺序、文档标题层级、接口简介、自定义数据类型介绍部分的存在性），仅检查内容中实际出现的结构（表格、代码块、列表、行内文本）对应规则；
- **代码上下文约束**：需要与头文件、软件定义核对的规则（输入/输出一致性、枚举/结构体定义一致性），在用户未提供代码路径或定义内容时跳过，不视为已通过，禁止臆断；
- **顺序约束**：模板明确章节顺序为建议（非强制），顺序偏离仅按提示级别报告；
- **产品知识约束**：产品型号与发布先后顺序仅按规则内参考序判定（真源：《文档写作规范》"产品型号命名规范"），参考序之外的产品跳过比较。

## 禁止行为

- 禁止超出规则描述范围进行检查，即便发现明显错误，遇到规则描述不明确的情况，必须跳过而非自行解读
- 禁止基于常识或经验进行扩展性检查，避免主观推断
- 禁止超出规则定义的检查范围进行检查
- 禁止不按照技能步骤执行
- 禁止不按技能步骤顺序执行
- 禁止跳过任何步骤
- 禁止合并或简化规则分类
- 禁止复制待检查文档到临时文件夹
- 禁止修改或增减规则内容
- 禁止修改文件内容，检查过程中只需要读取文件内容
- 禁止按照问题行号合并检查出的问题
- 禁止生成 CHECKPOINT 文档
- 禁止发现一个问题后跳过同行剩余内容的检查
- 禁止凭印象或记忆对检查结论下判定，必须对照原文精确定位
- 禁止通过心算、人工计数或估算方式确定问题行号，必须从带行号的文档内容中直接获取行号
- 禁止在【前提条件】不满足时臆断条件成立并执行检查

## 注意事项

1. 所有使用的文件路径都应是相对路径，在执行时转换为绝对路径
2. output 目录是在当前项目根目录下
3. 步骤2的分析必须逐个检查用户输入的所有文档
4. 检查完成后需要清理临时文件，仅保留最终结果文件
5. 支持 `.md` 文件扩展名的质量检查
6. 禁止通过中间文件在步骤间传递数据，所有数据在上下文中流转
