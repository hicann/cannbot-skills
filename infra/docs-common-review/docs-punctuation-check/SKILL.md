# 生态资料标点符号质检技能

本 skill 用于对 Markdown 文档进行标点符号和空格使用规范性质检，基于预设规则检测文档中的标点符号、空格间距、路径格式等问题。

## 重要原则（必须严格遵守，防止幻觉）

### 1. 仅使用给定规则

- **只能**使用 `references/rules.md` 中明确定义的规则
- **严禁**创造新规则、修改规则名称或规则级别
- 规则名称必须与规则文件中的完全一致（如"中英文标点混用检查"等）

### 2. 每项检查后追加写入 JSON 文件

- **每项检查完成后**：立即将结果追加写入 JSON 文件
- **质检期间**：禁止输出任何解释性文字、总结、表格
- **最终输出时**：保证输出到文件，无需输出到控制台
- 输出格式**只能**是标准 JSON

### 3. 输出前验证最终质检结果

- **只报告**真实存在问题的检查项
- 无问题的检查项**严禁报告**

### 4. 多子项规则独立报告原则

- 当质检规则包含多个子项（如"中英文标点混用检查"）时，**每个子项的问题必须独立报告**
- **禁止**将同一规则的多个问题合并为一个问题项
- 每个问题位置需要独立的 line_number 和 snippet
- 示例：如果"中英文标点混用检查"在文档中有3处空格问题，应报告独立的问题项，每个指向不同的 line_number

## 输入

1. **待检查的内容**：用户输入需要检查质量的 Markdown 内容，支持以下三种形式：
   - 一段 Markdown 内容（直接输入文本）
   - 一个 Markdown 文档的绝对路径
   - 多个 Markdown 文档路径（英文逗号分隔）或一个文档目录路径

### 示例

```
# 全部检查
/docs-punctuation-check "文档路径"

# 直接检查Markdown内容
/docs-punctuation-check "这是测试 内容。"
```

## 输出

输出一个质检结果JSON文件

- 默认输出目录：当前项目根目录下创建 `/output/` （如果目录不存在则先创建目录）
- 文件命名规则：`punctuation-markdown-check-result.json`

### 质检结果统一 JSON 格式

```json
[
  {
    "rule_group": "xxx",
    "rule_item": "xxx",
    "rule_type": "xxx",
    "rule_name": "xxx",
    "snippet": "xxx",
    "description": "xxx",
    "rule_level": "xxx",
    "file_name": "xxx",
    "line_number": "xxx",
    "location": "xxx",
    "suggestion": "xxx"
  }
]
```

#### 输出字段说明

| 字段名 | 类型 | 描述 | 要求 |
| --- | --- | --- | --- |
| rule_group | string | 问题大类 | 固定为"通用规则" |
| rule_item | string | 规则项名称 | 必须与规则文件中的规则项名称一致 |
| rule_type | string | 规则类型 | 必须与规则文件中的规则类型一致 |
| rule_name | string | 规则名称 | 固定为"punctuation-check" |
| snippet | string | 问题内容片段 | 直接引用文档内容 |
| description | string | 问题的具体描述 | 清晰说明问题，不包含行号 |
| rule_level | string | 级别 | 必须与规则文件中的级别一致 |
| file_name | string | 文档名称 | 必须是用户输入的Markdown文档名称 |
| line_number | string | 问题行号 | 必须从带行号的文档内容中直接获取 |
| location | string | 问题所在的行链接 | vscode://file/绝对路径:行号 |
| suggestion | string | 问题的具体修改建议 | 直接给出正确形式，不包含行号 |

## 执行流程

### 核心原则：按需读取，逐任务执行

- 待检查文档按"逐文件 / 分批"处理，禁止一次性把整个大目录全读入上下文；
- 每个文件可在不同步骤、不同规则下多次按行号回读；
- 仅"同行已不好走内对同一文件同一区域无意义的重复读取"才需避免。

在执行任何步骤前，在对话中先输出当前检查点：[CHECKPOINT: 开始]

**规则**：如果前一个CHECKPOINT未输出，禁止执行后一步骤。

### 第 1 步：数据准备

#### 1.1 解析参数与读取配置

- 检测用户输入内容是否为文件路径：
    - 如果是 `.md` 文件或者目录路径，则为文件路径模式
    - 如果不是，作为 Markdown 内容模式处理
- **文件路径模式**：直接使用文件路径作为处理文档路径
- **Markdown 内容模式**：
    - 创建 `output/punctuation/temp/auto_temp.md` 文件
    - 将用户输入的Markdown内容写入该文件
    - 将该文件的绝对路径作为后续处理的文档路径

**检测是否是Markdown内容的标准**：

- 没有明显文档路径特征（如 `D:/...、/...、./...等`）
- 不包含文件扩展名或路径分隔符
- 极长的内容（超过单行命令行输入长度）

#### 1.2 读取规则并筛选

- **此时读取**规则文件 `references/rules.md`
- 将获取到的规则保留在上下文中直接传递给后续步骤

#### 1.3 生成文档列表

- 读取当前技能目录下 `assets/exclude-files.json` 中的排除文件列表
- 根据文档路径生成待检查文件列表：
    - 单文件：直接加入列表
    - 目录：递归遍历该目录下所有 `.md` 文件，排除白名单中的文件名
- 将文档列表保留在上下文中

#### 1.4 清空历史结果文件

- 检查 `output/punctuation-markdown-check-result.json` 文件是否存在
    - 如果存在，则清空文件内容
    - 如果不存在，则创建该文件

#### 1.5 批量读取待检查文档

- 生成文档列表后步预读全文。步骤 2 在处理每个文件时，按需用带行号方式读取该文件，处理完一个文件再处理下一个。
- 将带行号的文档内容保留在上下文中

完成后必须在对话中输出 [CHECKPOINT: 数据准备完成]

### 第 2 步：执行分析

**严格按任务顺序依次执行，每个任务完整执行完毕（含读取文件、检查、写入结果）后，才进入下一个任务。禁止跨任务并行读取文件。**

#### 2.1 批量检查文档

对于每个待检查文档，执行以下步骤：

##### 2.1.1 使用脚本检查多余空格

- 调用当前技能目录下 `scripts/excess_space_checker.js` 脚本
- 命令格式：`node <技能目录绝对路径>/scripts/excess_space_checker.js <md文件绝对路径> <项目根目录绝对路径>/output/punctuation-markdown-check-result.json`

完成后必须在对话中输出 [CHECKPOINT: 多余空格检查完成]

##### 2.1.2 使用脚本检查缺少空格

- 调用当前技能目录下 `scripts/miss_space_checker.js` 脚本
- 命令格式：`node <技能目录绝对路径>/scripts/miss_space_checker.js <md文件绝对路径> <项目根目录绝对路径>/output/punctuation-markdown-check-result.json`

完成后必须在对话中输出 [CHECKPOINT: 缺少空格检查完成]

##### 2.1.3 使用脚本检查中英文符号混用

1. **执行脚本**：执行`mixed_language_checker.js` 脚本
    - 调用当前技能目录下 `scripts/mixed_language_checker.js` 脚本
    - 命令格式：`node <技能目录绝对路径>/scripts/mixed_language_checker.js <md文件绝对路径> <项目根目录绝对路径>/output`

###### 2.1.3.1 二次校验中英文符号混用检查结果

1. **读取中英文符号混用检查结果**：读取`/output/mix_language_check_result.json`内容
2. **读取规则定义**：从步骤1.2保存在对话上下文中的规则列表中，获取中英文标点混用检查规则的详细定义
3. **逐个验证问题判定是否正确**：
    对于检查结果中的每个问题，执行以下步骤：
    a. **定位问题位置**：根据`line_number`和`snippet`，在原文档中定位到对应行
    b. **查看上下文**：查看问题片段在原文档中的前后文本，确认：
        - 该片段是否真的在中文段落中（或英文段落中）
        - 该片段是否在代码块、命令、参数等例外场景中
        - 该标点符号的使用是否符合上下文语境
    c. **判定问题是否真实存在**：
        - **问题判定正确**：脚本发现的问题是真实存在的（例如：确实在中文段落中使用了英文标点，且不在例外场景中）
        - **问题判定错误**：脚本误判（例如：该片段实际在代码块中，或该标点使用符合上下文要求）
    d. **追加结果**：
        - 如果问题判定正确，将该问题的检查结果追加到`/output/punctuation-markdown-check-result.json`中
        - 如果问题判定错误，跳过该问题，不写入结果文件
4. **验证示例**：
    示例1（判定正确）：
    - 问题：第15行"精度仿真:输出bit级精度结果"中使用了英文冒号
    - 上下文检查：该行是中文段落，不在代码块中，应使用中文冒号"："
    - 判定：问题真实存在，追加到结果文件

    示例2（判定错误）：
    - 问题：第227行"${op_name}"中使用了英文花括号
    - 上下文检查：该片段是代码变量占位符，在代码示例中，属于例外场景
    - 判定：问题判定错误，跳过该问题

  **重要提示**：
  - 必须对照原文档逐个验证，不能直接信任脚本的输出
  - 代码块、命令、参数、变量名等场景属于例外，不应判定为问题
  - 如果无法确定是否为问题，保守处理（跳过该问题）

完成后必须在对话中输出 [CHECKPOINT: 中英文符号混用检查完成]

##### 2.1.4 使用脚本检查多余标点符号

- 调用当前技能目录下 `scripts/excess_punctuation_checker.js` 脚本
- 命令格式：`node <技能目录绝对路径>/scripts/excess_punctuation_checker.js <md文件绝对路径> <项目根目录绝对路径>/output/punctuation-markdown-check-result.json`

## 逐行扫描执行规范（强制遵守）

### 1. 逐行扫描顺序

- 对每个文档按行号从小到大逐行检查
- 每行从左到右逐字符/逐词扫描
- 发现问题时记录后必须继续向右扫描当前行剩余内容，不得中断当前行的扫描
- 只有当当前行从左到右完整扫描完毕后，才能进入下一行

### 2. 同行穷举规则

- 当在某行发现规则违规时，必须继续检查该行剩余内容是否还存在同类或其他违规
- 禁止因已发现一个问题而跳过同行后续内容
- 每行必须从头到尾完整扫描后才能进入下一行
- 同一行同一规则可以命中多个问题，每个问题必须单独记录

### 3. 结论验证规则

- 对每条检查结论（合规/不合规），必须在原文中定位到具体字符后再判定，**行号必须从步骤1带行号的文档内容中直接获取，禁止凭记忆心算或估算行号**
- 禁止凭对原文的印象或记忆下结论
- 特别是标注"合规"时，必须在上下文中明确记录判定依据（如：原文此处为XXX，符合规则YYY的ZZZ要求）
- 如果无法在原文中精确定位对应内容，必须回溯原文重新确认，禁止跳过
- **记录问题行号时，必须从步骤1已读取的带行号文档内容中直接获取行号，禁止通过心算或人工计数推算行号。如果上下文中带行号的文档内容已被截断，必须重新使用带行号方式读取原文档对应区域来确认行号**

## 常见幻觉陷阱（避免！）

| 陷阱 | 错误做法 | 正确做法 |
| --- | --- | --- |
| 创造规则 | 添加规则文件中不存在的检查项 | 仅使用规则文件中明确定义的规则 |
| 规则名称错误 | 使用"chinese-text-spacing-check"代替"中文空格检查" | 使用规则文件中的"中英文标点混用检查" |
| 扩展检查范围 | 根据常识添加规则未描述的检查项 | 严格按照规则描述的检查对象和范围执行 |
| 合并多子项问题 | 将同一规则的多处问题合并为一个问题项 | 每个问题位置独立报告，使用独立的行号 |
| 遗漏其他位置的错误 | 只报告第一处错误，忽略同一规则的后续错误 | 全面检查文档，同一规则的所有问题都要独立报告 |
| 输出多余内容 | 输出总结、表格、解释 | TL;DR, 仅输出 JSON |
| 心算行号 | 凭记忆或计数推算问题行号 | 从带行号的文档内容中直接获取行号 |
| 忽略白名单例外 | 对产品名称白名单中的名称也报空格违规 | 先读取步骤1.4的产品名称白名单（references/product_names_whitelist.json），白名单内名称不判定为空格违规 |
| 凭记忆扫描 | 读一遍文档后凭印象跳跃式扫描，不逐行对照原文 | 必须对照带行号的原文逐行逐字扫描，每条结论必须在原文中精确定位字符后再判定 |
| 跳跃式检查 | 看到哪算哪，跳过行或跳过规则维度 | 按行号从小到大、每行从左到右逐字符扫描，每条规则的每个维度都必须逐一执行 |
| 未验证结论 | 发现问题后不回原文确认空格数量、行号等细节就写入结果 | 每个问题必须回到原文逐字符确认（如确认是1个还是2个空格），行号从带行号文档内容中直接获取 |

## 约束与边界

- **场景约束**：一段内容场景不校验MD专属格式（标题层级、代码块等），仅聚焦基础规范和核心正确性

## 注意事项

1. 所有使用的文件路径都应是相对路径，在执行时转换为绝对路径
2. output 目录是在当前项目根目录下
3. 步骤2的分析必须逐个检查用户输入的所有文档
4. 支持 `.md` 文件扩展名的质量检查
5. **仅使用给定规则文件的范围进行检查，严禁增删改规则条目**
