# 支持性契约与交接证据

新增能力限制、模式分支或显式选路时，在 Spec 适用条件/边界章节填写以下契约；
不需要为无关的日志或命名修改补齐全表。字段、枚举、错误码以目标版本源码为准。

## 1. 状态何时有效

| 能力/条件 | 真实字段与赋值位置 | Selector 消费时是否有效 | 执行路径消费/阻断位置 | 证据或未验证范围 |
|---|---|---|---|---|
| 对称内存等支持性限制 | 文件:符号及初始化/更新顺序 | 值来自哪里、是否仍会变化 | 守卫与失败行为，或上游保证的证明 | 正向/拒绝路径 |
| OpMode | 枚举定义与实际入口 | 模式值如何传递 | 每个可达模式的资源与执行分支 | 已测/不可达/未测 |
| 链路协议 | 按通信域还是按链路判定 | 拓扑过滤依据 | 读写选择与异构链路约束 | 拓扑覆盖 |

沿算子入口 → Selector → Executor → Template 追踪写入与读取。
声明“不支持”必须在所有可达相关路径上有有效阻断；注册属性不是时序正确性的证明。
已有上游保证足够时记录证据，不机械增加重复守卫；错误路径检查资源清理及是否已下发通信。
零数据、单 rank 等早退与能力拒绝的组合按语义说明，不要求空操作一定返回不支持。

来源案例：用户提供的 2026-09-22 Broadcast Ring 报告；在 HCCL `978d01b6` 加未提交 Ring 的
工作树中，`src/ops/broadcast/broadcast.cc` 的 OPBASE 入口在 Selector 后处理对称内存状态。
该案例说明必须核对赋值时序，不推导其他算子都具有同样顺序。

## 2. 枚举、资源与执行分支一致

从目标仓枚举定义列出全部取值，并分别说明可达性、scratch 需求、远端缓冲区和拒绝行为。
“当前测试覆盖两态”不能推导枚举只有两态；第三态不可达也应指向调用链证据。

本次源码 `src/ops/op_common/inc/alg_param.h` 的 `OpMode` 为 OFFLOAD、OPBASE、ACLGRAPH。
具体任务仍须重新核对版本。报告中的 `OFFLOAD ? 0 : 1` 修复只适用于其 executor 的远端直达条件，
不能作为其他算法统一的 scratch 公式。

测试计划按风险选取：支持路径、显式选择但能力不支持的拒绝路径、无/不匹配/禁用配置，
以及新增 DSL token 的解析、正反映射与注册名回归。复用已有测试框架，UT 不替代 Checker；
环境无法覆盖的模式或协议写明源码论证、剩余风险和后续补测条件，不记为 PASS。

## 3. 交接给 Reviewer 的证据索引

在现有任务交接中附索引，不另造阶段或要求角色调度：

- 源码 commit + 工作区快照身份、Spec 路径/哈希、固定评审 base。
- 关键参数赋值与消费符号、支持性契约、wrapper 完成语义、executor 资源消费点。
- 验证矩阵与日志索引、未覆盖项和理由。
- 整改的 finding ID → 受影响分支/依赖文件 → 当前版本证据。

Reviewer 独立核验关键证据。复审复用未变化依赖的定位结果；相关文件、源码身份、模式或拓扑
变化时重新分析受影响范围。保存各阶段开始/结束及等待时间，分别报告墙钟和有效时间；
重叠区间不重复求和。交付文件完整性见 [build-verification.md](build-verification.md#交付文件与-spec-身份)。
