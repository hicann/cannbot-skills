# 错误处理与回退

> 各 CP 不通过时的回退策略、循环最大轮次、恢复规则。

## 回退关系（来自流程表）

| 不通过的 CP | 回退目标 | 重走路径 |
|-------------|---------|---------|
| CP1 | 1.1 需求分析 | — |
| CP2.1 | 2.1 黑盒测试设计 | — |
| CP2.2 | 按语义归属：开发方案 → 2.2 / 需求 → 1.1 | 归属需求时重走 1.1 → CP1 → 2.2 → CP2.2 |
| 3.4 | 按问题归属：代码问题 → 3.1 / 测试问题 → 3.2 | 代码问题：3.3 → 3.4；测试问题：3.2 → 3.3 → 3.4 |
| CP3 | 按语义归属：算子实现 → 3.1 / 测试方案（精度判定口径缺失、不可溯源、与权威源不符）→ 2.1 | 归属算子实现：3.3 → 3.4 → CP3；归属测试方案：2.1 → CP2.1 → 3.2 → 3.3 → 3.4 → CP3 |
| CP4 | 3.1 算子开发 | 3.3 → 3.4 → CP3 → 4.1 → CP4 |
| CP5 | 3.1 算子开发 | 3.3 → 3.4 → CP3 → 4.1 → CP4 → CP5 |

> 可插拔流程插件的内部回退与最大轮次见各插件自身文档。

> CP2.2 的归属分流：无论是 QA 认定问题根因在需求（如需求文档中已由用户拍板的代码架构在目标芯片上不可行），还是用户在确认问卷中对架构选型 / dtype / shape 范围 / 容差 / 性能目标提出异议，均按语义归属回退 1.1 由用户重新拍板，而非回退 2.2。
>
> 开发方案一经用户确认即锁定：**任何后续回退只要改动了开发方案（如 CP4 定位到 Tiling / 切分需调整而回退 2.2），改后的方案必须重走 CP2.2 的用户确认段**，不得跳过。仅回退 3.1 的实现级修改不触发复确认。
>
> **回退派发约定**：回退修改时，PM 复用原执行子 Agent 的会话——在其原会话中追加修改要求与结构化修改意见，保留其对交付件的历史上下文与定位知识，**不新建子 Agent 会话**；仅当原会话不可用（已销毁 / 上下文溢出）时才新建，并在 prompt 中补齐必要的交付件背景。
>
> **回退落地后的文档同步**：修改落地的子 Agent 回传「受影响文档清单」后，PM 按各文档所在目录派发具备该目录写权限的角色刷新（测试目录交测试角色、文档目录交文档角色），**刷新完成后再进入重走路径的下一步**。跳过这一步，代码多轮更新而文档停留在早期快照的不一致会被推迟到代码检视才暴露，届时又是一轮回退。

## 回退最大轮次

所有可循环环节达上限即暂停，禁止无限自动重试。取值如下：

| 循环 | 涉及环节 | state.loop 取值 | 默认最大轮次 | 计数对象 |
|------|---------|-----------------|--------------|----------|
| 设计评审循环 | CP1 / CP2.1 / CP2.2 | `design` | 3 | 单个 CP 的打回-重做；CP2.2 的用户异议返工与 QA 打回共用同一计数 |
| 联调重试循环 | 3.4 → 3.1 / 3.2 | `joint_debug` | 3 | 联调打回-重做的整轮 |
| 验收状态机 | CP3 / CP4 / CP5 → 3.1（CP3 归属测试方案时 → 2.1） | `acceptance` | 3 | 回退后的整轮重走；CP3 归属测试方案的重走沿用本槽 |

- 轮次计数按环节分槽写入 `state.json` 的 `rounds`（见 [state-schema.md](state-schema.md)）；跨环节回退（如 CP2.2 因归属需求回退 1.1）**不清零发起方槽位**，否则往返途中计数被重置，循环将失去边界。
- **超上限处理**：暂停 → 落盘可恢复状态点 → 输出结构化问题清单 → 请求用户决策（继续放宽轮次 / 调整设计 / 停止）。**静默模式（`mode=silent`）下超上限同样暂停并落盘**，问题清单作为中止性总结输出（静默例外清单内），不自动放宽轮次。

## 杠杆评估门（性能未达标时的回退前置）

达上限才暂停是**兜底**，不是唯一出口。性能未达标的回退在**每轮发起前**先过杠杆评估门：本轮之后是否还有与实测瓶颈维度匹配、且未被负结果证伪的实质杠杆？

| 评估结论 | 处理 |
|----------|------|
| 有实质杠杆 | 按归属回退（2.2 或 3.1），计入验收状态机轮次 |
| 无实质杠杆（清单为空 / 仅剩收益趋零的微优化 / 候选方向均已有负结果） | **不回退、不计轮次**，转下方「需求级硬门槛放宽」决策 |

判定依据与清单格式由 CP4 的验收标准给出。杠杆评估门的作用是截断「明知无收益仍重走整条复验链」的空转——回退轮次上限只能限制次数，限制不了单轮的无效消耗。

## 需求级硬门槛放宽

需求文档声明的硬门槛（性能目标、精度标准）**不得由验收环节自行放宽**：验收只能给出「建议按已知限制收口」的结论与完整依据，是否接受属需求级决策。

- **交互模式**：PM 将收口建议与依据交用户决策；用户接受后记入交付结论，不接受则按用户指示继续优化或调整需求。
- **静默模式**：按 [settings.md](settings.md) 的静默默认决策执行，并在 `state.json` 落盘完整收口依据、标记 `pending_user_review`，随任务完成总结上报——**静默下的收口是待复核决策，不是永久定案**。
- 收口依据须含：未达标项与门槛的量化差距、实现级优化穷尽的证据（已落地项 + 负结果项）、设计级方向与实测数据矛盾的证据（若适用）。依据不全时不得收口，按阻断处理。

## 错误类型与判定

| 类型 | 典型场景 | 处理 |
|------|----------|------|
| 交付件不合规 | 文档缺项 | 返回对应生成步骤修复，计入设计评审循环 |
| 方案未获用户认可 | CP2.2 用户在确认问卷中提出异议 | 按条目语义归属回退 2.2 或 1.1，计入设计评审循环 |
| 联调不通过 | 3.4 用例跑不通/精度比对不过 | 按问题归属回退 3.1（代码问题）或 3.2（测试问题），计入联调重试循环 |
| 功能不达标 | CP3 精度/用例不过 | 按语义归属回退 3.1（算子实现）或 2.1（精度判定口径本身有缺陷），均计入验收状态机 |
| 性能不达标 | CP4 未达目标 | 先过杠杆评估门（见本文「杠杆评估门」一节）：有实质杠杆则定位瓶颈——涉及设计（Tiling/切分）回退设计角色（2.2）并重走 CP2.2，否则回退 3.1；无实质杠杆则不回退，转需求级硬门槛放宽决策 |
| 检视不通过 | CP5 规范/一致性/风险问题 | 回退 3.1 按检视意见修复 |
| 环境阻塞 | CP0 环境不满足 | 交用户决定修复或停止 |

## 修改不越权

执行角色发现问题时：允许定位（复现、缩小范围、给根因证据），但**不得自行变更上游设计决策**（架构/Tiling/切分/接口）。定位结论回退给对应上游角色（architect），由其决定是否调整设计。

代码架构是用户在 CP1 拍板的决策，位于 architect 之上：architect 在开发方案中发现该架构不可行时，同样不自行改选，而是把论据回退到需求（1.1），由用户重新拍板。

## 恢复规则

- 暂停/失败落盘到 `.cannbot/<算子名>/state.json`（见 [state-schema.md](state-schema.md)）的可恢复状态点：已完成阶段、当前阻塞点、已产出交付件、当前轮次。
- 恢复时从状态点续跑，不重跑已通过阶段。
