# tip: 加载/编译前隔离并追踪本轮 custom pass 产物

> 📎 导航落点：`references/fusion-troubleshooting.md` §1/§7（pass 是否加载、图与输出是否正确）。本文件仍是加载隔离纪律的**唯一权威定义源**，正文未改动。迁移映射见 `tips/MIGRATION.md`。

**读者**：③ 分析。来源：真实事故——跨用例/跨轮次残留的 custom pass `.so` 仍被 GE 加载，污染下一次编译，导致结果不可信、pass 相互冲突（典型 decompose 类）。

## 症状

- 明明这轮没改/没建对应 pass，dump 里却出现上一轮 pass 的替换效果；或多个 pass 同时生效相互干扰。
- "上一次成功、这次莫名其妙不一样"，且和当前源码对不上。

## 根因

- GE 从自定义 pass 加载目录（C++ 的 custom op/pass `.so`，Python 的 `ASCEND_GE_PY_PASS_PATH`）扫描并加载**当前存在的所有** pass 产物。上一轮 build 出的 `.so`、上一个用例遗留的 pass 文件不会自动消失，会被一并加载。

## 硬性做法

- 把问题当成**加载集合隔离**，不要做共享目录批量清理。只清理当前 case 根目录内、由本轮构建明确拥有的 `build/` 产物。
- C++ 的共享 vendor 加载目录默认只读：先列出其中已有的 pass，并把可能干扰本轮验证的项写进报告；**不得删除“非本次” `.so`**。
- 确需安装、覆盖或移除 C++ pass 时，先记录本轮产物的确切源路径、目标路径和文件名，只允许操作该目标；目标位于 case 根目录外时，须先取得用户明确确认。
- Python 将 `ASCEND_GE_PY_PASS_PATH` 精确设置为本次要验证的 `.py` 文件，不把包含其他 pass 的目录加入路径，也不删除目录里的其他文件。
- 无法确认当前加载集合只有本轮 pass 时，标注“加载基线未确认”，保留盘点结果，不宣称 dump 变化只由本轮代码造成。
- dump 出现“非预期的替换效果”时，先按盘点结果排查残留 pass，再怀疑本次代码。

## 自查

- 当前 case 的旧 `build/` 产物是否已清理，且清理范围没有越出 case 根目录？
- 是否记录了本轮 C++ `.so` 的确切源路径和目标路径，并且只操作了这一项？
- 共享 vendor 目录中是否还有其他 pass？有则是否已盘点并在报告中标注潜在干扰，而不是擅自删除？
- `ASCEND_GE_PY_PASS_PATH` 是否精确指向本次 `.py` 文件？
- dump 里的变化，能不能逐一对应到**当前**源码的逻辑（而非上一轮遗留）？
