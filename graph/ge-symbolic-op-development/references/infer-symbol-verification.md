# InferSymbol 验证参考

## 1. 自定义算子交付结构

推荐把符号化推导作为现有 host 交付件的一部分：

```text
my_op/
├── op_host/
│   ├── my_op_def.cpp
│   ├── my_op_infershape.cpp
│   ├── my_op_tiling.cpp
│   ├── my_op_symbolic.cpp
│   └── CMakeLists.txt
├── op_kernel/
│   └── my_op.cpp
└── op_graph/include/
    └── my_op.h
```

不新增独立 symbolizer so，不新增运行期链接库；把新源文件加入原有 host so 的构建和安装路径。

## 2. 静态检查

提交前检查：

- 发布头来自目标 CANN 安装包，且三个头可以被自定义算子工程直接 include。
- 注册的算子类型与 IR 原型一致。
- 所有输出在成功路径写入 Shape。
- 输入 Shape 的 rank、轴、广播和属性索引与普通 Shape 语义一致。
- 数据依赖声明与 `GetInputSymbolTensor` 定位一致。
- `HasValue()` 和 `GetValueCount()` 的三态判断没有混用。
- 失败路径没有把不确定值强转为整数。
- 组合 Guard 使用 `EXPECT_SYMBOL_AND/OR`，没有依赖 C++ 原生短路来表达完整约束。
- 回调没有保存 `InferSymbolContext`、`SymbolShape` 或 `SymbolTensor` 的地址供后续异步使用。

## 3. 弱符号检查

编译自定义 host so 后，在编译机检查 symbolizer 相关未定义符号：

```bash
nm -D --undefined-only libcust_opapi.so | grep 'ge::'
```

检查目标：

- 表达式、符号、运算和 Guard API 为弱未定义引用。
- 没有不应由运行机提供的强未定义 `ge::` 符号。
- 注册库入口按目标版本的兼容策略解析；不能只凭本机编译成功判断兼容，必须检查目标发布头、注册库入口、弱符号行为和老环境兼容策略。
- 按目标 CANN 版本检查发布头声明、注册库导出和老环境行为；确认入口是强引用还是弱引用，以及未提供注册时是静默跳过还是加载失败。

在仅含 run 包的执行机上，算子 so 应能正常加载。执行期不会调用符号化回调和 symbolizer API；若执行期进入该路径，说明编译/运行职责边界或版本组合有问题。

## 4. 端到端验证

动态 Shape 验证至少覆盖：

1. 自定义算子前的输入动态维被符号化。
2. 自定义算子回调被注册表发现并调用。
3. 输出 Shape 与算子数学定义一致。
4. 后续节点仍能得到符号 Shape。
5. 广播、轴约束或其他条件产生正确 Guard。
6. 自动融合范围扩大或至少不因该算子提前断链。
7. 编译生成的模型可以在执行机运行，并与参考实现比较结果。

启用自动融合的参数和运行命令以目标版本文档为准；常见环境会使用类似下面的配置，但不要把示例参数当作所有版本的固定接口：

```bash
export AUTOFUSE_FLAGS='--enable_autofuse=true'
```

执行任何编译、运行模型、执行机加载或端到端命令前，必须先获得用户确认，并记录完整命令、环境版本和结果；未确认时只做静态检查并标记动态验证为“未运行”。

## 5. 符号化用例设计

本节只描述符号化推导需要增加的测试内容。自定义算子工程的 host so 构建、安装、OPP 配置、模型编译和执行方式沿用该工程已有流程，不在本 skill 重复定义。

### 5.1 最小测试图

在已有自定义算子测试工程中构造一条包含以下节点的图：

```text
动态输入 -> 自定义算子 InferSymbol -> 至少一个后继算子 -> 图输出
```

测试必须能观察自定义算子输出符号是否继续传给后继节点。只调用回调并检查返回码，不能证明整图符号传播成功。

### 5.2 必测场景

| 场景 | 重点断言 |
| --- | --- |
| 静态 Shape | 输出 Shape 与普通 Shape 语义一致，静态输入不引入额外 Guard |
| 动态 Shape、Shape-only | 输出维度表达式正确，后继节点仍可获得符号 Shape |
| 数据依赖值推导 | 输入值存在时输出值数量、输出 Shape 与期望一致、元素顺序正确 |
| 值缺失 | 不解引用空值，不写未经证明的输出值，按契约返回未提供 |
| Guard 为真 | 选择的分支和输出表达式正确 |
| Guard 为假 | 选择其他合法分支、降级或返回错误，行为与算子契约一致 |
| 复合 Guard | 所有子条件都参与约束，不能只验证当前 hint |
| 标量和显式空值 | 零维 Shape、1 个标量元素、无值和显式空值分别正确处理 |
| 非整数常量 | 不做隐式整数转换，按能力边界降级 |
| 负轴/负索引 | 按算子规定的 rank 或轴长度归一化后再计算 |
| optional 输入缺失 | 按 IR index 定位，未连接输入不错误阻断其他输入推导 |

### 5.3 每个用例应记录的内容

每个符号化用例至少记录：

- 输入 Shape、动态维、属性和输入值。
- 哪些输入声明了数据依赖。
- 期望输出 Shape 表达式和符号值数量。
- 期望输出值的元素顺序、索引映射和广播/拼接/规约后的布局。
- 期望的 Guard 条件及其成立/不成立时的行为。
- 期望返回 `GRAPH_SUCCESS`、`GRAPH_NOT_CHANGED` 或错误码。
- 后继节点是否继续获得符号信息。

### 5.4 结果判定

- 回调返回成功不等于用例通过；必须检查输出 Shape 和整图后继传播。
- 输出 Shape 正确不等于符号值正确；需要单独检查值数量、元素顺序和索引映射。
- 值推导用例必须分别检查输入值存在、元素数量、输出 Shape 与期望一致、输出元素顺序；正确构造 N-D 索引表达式不能替代 Shape 或顺序断言。
- 编译成功不等于 Guard 正确；应分别覆盖满足和不满足 Guard 的输入。
- 数值结果正确不等于符号化成功；静态回退也可能产生正确数值，因此需要同时检查符号传播或融合结果证据。
- 只能完成静态检查时，将动态 Shape、Guard 和执行验证标记为“未运行”。

## 6. 兼容性矩阵

| 组合 | 预期检查 |
| --- | --- |
| 旧算子包 + 新环境 | 原有行为不变 |
| 新算子包但不含符号化源文件 + 旧环境 | 不应新增符号化依赖 |
| 含符号化源文件的算子包 + 新环境 | 编译期注册、回调和动态 Shape 链路可用 |
| 含符号化源文件的算子包 + 旧环境 | 以目标版本弱入口和发布头兼容策略为准，确认是静默跳过还是显式加载失败 |
| 新版本编译 OM + 旧执行环境 | 符号信息不参与执行态解析，检查 OM 兼容性 |
| 旧版本编译 OM + 新执行环境 | 检查向后兼容 |
| 编译机有 symbolizer + 执行机只有 run 包 | so 可加载，执行期不调用符号化 API |

OpDef 式和语言无关式接口是否可用，必须通过目标版本的发布头、注册库和最小编译样例确认。不能因为接口文档列出入口，就假设当前安装包已经包含实现。

## 7. 返回值和版本检查

发布接口契约定义：

- `GRAPH_SUCCESS`：采纳完整输出符号。
- `GRAPH_NOT_CHANGED`：丢弃本次写入，按未提供继续降级。
- 其他错误码：中断编译。

如果实际 GE 消费链路与该契约不一致，应把它记录为版本缺陷或组件未同步，而不是在算子回调中伪造成功结果。检查顺序：

1. 检查 `infer_symbol_context.h`、`symbolic_types.h` 和 `symbolic.h` 的版本。
2. 检查注册库是否包含对应入口。
3. 检查 GE 消费组件是否实现三态归并。
4. 检查 graph-autofusion 是否消费回调生成的符号和 Guard。
5. 只有组件版本一致后，才判断算子推导逻辑本身有问题。

## 9. 职责边界

本 skill 只指导自定义算子交付件的接口使用和验证。以下问题应转交相应的组件或技能：

- 发布头、注册表 ABI 或弱符号机制本身有问题：转 metadef 组件维护。
- 编译期逐节点查询、返回值归并或符号回写有问题：转 GE 编译组件维护。
- 融合策略、Lowering、循环轴和 codegen 有问题：转 graph-autofusion 组件维护。
- kernel 计算结果或 tiling 错误：转对应算子开发和调试流程。
