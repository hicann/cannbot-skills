# ArgReduce 范式能力谓词契约

> **层级**：通用知识层（generic/），语言中立。
>
> **这是什么**：通用层文档要讲算法，但不能写死某一种语言的 API（AscendC 的函数名对 DSL 读者无意义）。于是把「算法依赖的硬件/语言能力」抽成一组**带名字的空位**（称为"能力谓词"），通用层只写空位的名字；每种语言在 `adapters/<lang>/capability-mapping.md` 里回答"我们这边这个空位填什么"。
>
> 举例：通用层写「AR 场景需要 `INDEX_TRACKING_REDUCE`」，AscendC 适配层回答「= `ReduceMax(..., calIndex=true)`」，DSL 适配层回答「= `vreduce_min`」。同一句算法描述，两种语言各自成立。

## 1 使用规则

1. **通用层**：算法描述中遇到能力依赖点时只引用谓词名，不写具体数值或 API
2. **适配层**：每种语言逐项回答谓词真值（填什么 API、什么数值、是否支持）
3. **可填性检验**：新语言适配层必须能对每个谓词作答。答不出的说明抽象有问题，应改抽象而不是绕过
4. **冲突处理**：适配层答案与通用层假设冲突时（如某语言归约指令不返回位置），以适配层为准，并标注对设计的影响（如该语言 ARA 场景必须改用向量比较手法）

## 2 谓词定义表（10 个）

> 读法：**「一句话」列**是它到底在说什么；**「什么时候用到」列**是通用层哪些地方依赖它；**「适配层要回答」列**是每种语言必须给出的答案形态。

### 2.1 选择段相关（"怎么比"需要的原料）

| 谓词 | 一句话解释 | 什么时候用到 | 适配层要回答 |
|------|-----------|-------------|-------------|
| `INDEX_TRACKING_REDUCE` | **一条指令同时算出「极值是多少」和「它在第几位」**的归约指令 | AR 场景手法 A；UB 预算里为它预留的临时空间 | 有没有这条指令？位置输出的格式是什么？支持的 dtype 和长度上限？**它的 NaN 行为可信吗（必须实测，不能只看文档）** |
| `VECTOR_COMPARE_SELECT` | **批量比大小 + 按掩码挑赢家**的指令族（比较出掩码→用掩码从两个候选里选） | 主规则（比大小）、平局裁决、NaN 掩码合并；ARA 场景的主手法 | 比较支持哪些模式（大于/小于/等于/不等于）？掩码是逐元素的吗？掩码之间能不能做 OR/AND？"位为 1 选谁"的约定是什么？ |
| `INDEX_ARITH_OP` | **给"位置号码牌"做生成和加法**的算术原语（造 0,1,2,... 序列、加一个块偏移） | 位置流生成（块内 iota 序列）、跨块/跨核合并时加基址偏移 | 怎么造等差数列（常量填充+增量 / 专用 range 指令）？位置和标量怎么相加？ |
| `INDEX_STORAGE_TYPE` | **位置号码牌在片上用什么类型存**。不是随便选：要和值通道**等宽**（同 lane 数、同掩码粒度），否则比较/选择时掩码对不上，两条通道无法同步选择 | 场景能力边界（位置精度）；切分时的块内偏移上界核对；位置→输出类型的转换 | 位置的存储类型是什么？能精确表示多大的整数（决定块内偏移上界）？转换到 int32/int64 输出是否无损？ |
| `VECTOR_LANE_WIDTH` | **向量寄存器一次能装多少个元素**（比如 256 字节寄存器装 fp16 是 128 个） | 判断"R 很小能否一次比完"（RA/Gather 特化的触发条件） | 通道宽度是多少？是否随 dtype 变化？怎么在运行时获取？ |

### 2.2 资源与切分相关（"数据怎么搬、核怎么用"需要的原料）

| 谓词 | 一句话解释 | 什么时候用到 | 适配层要回答 |
|------|-----------|-------------|-------------|
| `ONCHIP_CAPACITY` | **片上缓存总容量**（含单个 buffer 的上限） | UB 三通道预算：值流+位置流+输出/暂存能放多少；反解切块大小 | 总容量多少？单 buffer 上限多少？**必须运行时查询还是可以编译期常量？** |
| `DATA_ALIGNMENT` | **搬运和存储的对齐粒度**（比如 32 字节为一块） | 尾块 padding、workspace 对齐、切块尺寸取整 | 对齐粒度是多少字节？ |
| `MULTICORE_BALANCE` | **多核之间怎么分配工作量才不会有的核闲着、有的核累死**。约定：前 N 个核各多担 1 份，负载差异 ≤ 1 | 多核切分（A1/A0 方向分核）；GroupReduce 的 R 分段 | 用哪套均衡公式？（如 `blkFactor = 总量/核数, blkTailFactor = 总量%核数`）核数字段语义是什么？ |
| `CROSS_CORE_SYNC` | **多个核之间怎么"对齐进度"**：让所有核都做完第一阶段，再开始第二阶段（栅栏），以及怎么告诉框架"要等全部核空闲再启动" | 仅 GroupReduce 两阶段衔接时用到（普通 A 方向切核**不需要**） | 有全核到齐的栅栏原语吗？怎么配置调度模式？ |
| `WORKSPACE_MODEL` | **跨核交换中间结果用的公共内存**怎么申请、怎么布局（每核把局部冠军写进去，第二阶段再读出来合并） | 仅 GroupReduce 的 workspace 布局与大小计算 | 中间存储怎么申请？系统预留和用户部分怎么分？布局约定是什么？ |

## 3 使用示例

通用层 splitting.md 中这样写（只留谓词名）：

> `ubNeed = R_chunk × 值元素宽 + R_chunk × 位置元素宽 + 输出/暂存项 ≤ ONCHIP_CAPACITY`

AscendC 适配层（`adapters/ascendc/capability-mapping.md`）回答：

> `ONCHIP_CAPACITY` = 运行时查询（`GetCoreMemSize(UB)`），950PR 实测 216KB；`INDEX_STORAGE_TYPE` = fp16 配 uint16（等宽，块内偏移 ≤ 65536）

DSL 适配层（`adapters/dsl/capability-mapping.md`）回答：

> `ONCHIP_CAPACITY` = `get_mem_size("ub")`，950PR 实测 253952 B；`INDEX_STORAGE_TYPE` = fp16 配 int16（等宽，实战验证）

## 4 为什么只有 10 个（相比初版的取舍）

初版有 17 个，评审发现"太多且难懂"。合并/删除的依据是**通用层是否真的引用它**——通用层不用的，说明它是适配层的实现细节，不该出现在契约里：

| 初版谓词 | 处置 | 理由 |
|---|---|---|
| `INDEX_CAST_PATH` | 并入 `INDEX_STORAGE_TYPE` | 通用层只有一处提到"位置→输出类型转换"，并入存储类型描述即可 |
| `UNALIGNED_LOAD` | 删除（下沉适配层） | 通用层零引用；非对齐载入是具体语言的搬运细节，归 `adapters/*/highlevel-api` 或实现指引 |
| `GATHER_OP` | 删除（下沉适配层） | 通用层零引用；Gather 转置是某平台的性能特化手段，归 `adapters/ascendc/mode-mapping.md` |
| `UB_CAPACITY` + `SINGLE_BUF_MAX` | 合并为 `ONCHIP_CAPACITY` | 两者回答的是同一类问题（能放多少），且总在同一处使用 |
| `CACHELINE_SIZE` | 删除（下沉适配层） | 初版把它当"切块上界参考"，实际是各平台的调优经验值（如"每 4KB 输入开 1 核"），归 `mode-mapping.md` |
| `SCHEDULE_MODE` | 并入 `CROSS_CORE_SYNC` | 调度模式与栅栏是同一件事的两面（都要"全核到齐"） |
| `BLOCK_DISPATCH_MIN` | 删除（下沉适配层） | 空输出时"至少发几个核"是具体框架的发起约定，归适配层 |
