本文件对应入口 `04-code-analyzer.md` 的步骤 1-3，包含以下环节：

| 环节 | 对应入口步骤 | 说明 |
|------|------------|------|
| 环节 A：Scout 索引 + 执行链路展开 | 步骤 1 | 读 Scout 报告 → 按执行链路逐步展开 Tiling 类内函数 → 分支骨架 + conditions |
| 环节 B：tiling P1 溯源 | 步骤 2（条件执行） | 仅步骤 1 中发现未定义函数时执行；否则跳过 |

## 首要步骤：读取 Scout 侦察报告

读取 Phase 0 产出的 `S2P0_scout_t.md` 和 `S2P0_scout_k.md`。

Scout 报告已经过 Scout-Verify 校验（Phase 0），可直接信任其分支拓扑、行号和 key 计数。

Scout 报告提供：分支追踪路径及行号、tiling_key 值、平台判断函数返回值、kernel 逐条 dispatch 映射和总 key 计数、架构守卫求值结果。

仍需从源码提取（Scout 不提供）：结构化 conditions JSON（逐字抄录源码表达式）、input_variables / caller_options / internal_variables 分类。

### 读取策略

从入口函数出发，按执行链路逐层展开类内各被调用函数。类内函数完整读取，类外函数按需读取，避免读入无关代码。

1. **入口函数**：从 Scout-T 识别 Tiling 类的入口函数，完整读取其实现
2. **Init 链路**：沿入口函数调用链展开 Init 方法及其调用的所有类内子方法，完整读取各子方法的实现
3. **DoTiling 链路**：展开 DoTiling 方法及其调用链上的所有类内函数（策略分发、策略判断、tile factor 计算等），完整读取各函数实现
4. **按需展开**：每个函数读取后，若内部调用了其他类内函数，继续展开读取，直到执行链路上的所有类内函数均已读取为止
5. **行号记录**：读取过程中记录策略判断函数的行号区间
6. **类外函数**：被调用的类外辅助函数（如模板工具函数、外部头文件定义的函数）不在此展开，按「公共函数溯源验证」规则按需单独读取

### 回退条件

按执行链路展开完成后，验证完整性：
- 核对 Scout-T 中入口执行链路上的关键节点（入口函数、Init 链、策略分发、策略判断系列、tile factor 计算系列）是否均已读取；若有遗漏，继续按需展开
- 若发现链路上存在类外函数但按「公共函数溯源验证」规则无法定位实现，在 `completeness_checklist` 中记录，不回退到全量读取

## 公共函数溯源验证

分析源码时，对当前文件未定义的函数调用必须溯源到实现代码，读取实际逻辑后再决定路径走向。溯源范围限定在读取范围文本块列出的文件内；若被调用函数的实现文件不在读取范围，按下方行为约束暂存为内存中间变量，不自行扩展读取。

### 适用范围

需溯源：平台判断函数（返回值决定分支走向）、计算工具函数（返回值参与条件判断）、公共头文件中的 inline 函数。

不需溯源：标准库函数、框架基础设施（`context->GetInputShape()` / `SetBlockDim()` 等确定性接口）、已在当前文件有定义的函数。

### 强制流程

1. **识别**：发现函数调用在当前文件无定义
2. **定位**：通过 `#include` 链和目录结构找到实现文件
3. **读取**：读取实现代码，理解实际判断逻辑
4. **代入**：将目标平台参数值代入实现逻辑，得到确定返回值
5. **记录**：在 `source` 字段引用实现文件路径和行号（格式：`调用文件:行号 → 实现文件:行号`）

溯源深度：到函数实现代码并理解返回值逻辑即可，不需继续溯源更深层调用。

### 行为约束

禁止根据函数名/文件名/平台名推断行为；禁止跳过溯源直接假设函数行为；禁止读取"源码读取范围"之外的文件；发现引用未在读取范围中列出且返回值影响分支判断的外部符号时，禁止自行读取其定义文件，暂存为内存中间变量（记录符号名、调用位置、影响分支），步骤 7 时写入 completeness_checklist，由主 Agent 决定是否补充。

遇到以下想法时必须 STOP，回归源码确认：
- "这个值大概是 N" → 找 `constexpr`/`#define` 确认精确值
- "这个算子应该跟那个类似" → 每个算子独立分析
- "这个约束太复杂了" → 不可跳过，写进未确认项
- "没找到路径" → 记录为"未发现"，不默认没有
- "这个平台应该走这个分支" → 找到分支条件实现，代入目标平台值验证
- "proto.h 说不支持" → 不做可达性判断，kernel 有实现就报告
- "这条路径太边缘了" → 所有路径都报告
- "这个分支跟主干差不多" → conditions 不同就是不同路径
- "这个函数名说明了它的行为" → 函数名≠实现，读代码

所有路径都报告，不做重要性判断；内部变量放入 internal_variables 但不可丢弃。

## Kernel 覆盖策略

kernel 侧分析范围：读取 manifest 列出的 kernel P0 文件（dispatch 入口），提取每个 dispatch 条目的 key 值、模板参数、行号。将这些条目映射为对应 tiling 路径的 `key_instructions`。`source` 字段格式为 `tiling:line → kernel_dispatch:line`。tiling 无法映射的 kernel dispatch 条目由后续「孤儿 Dispatch 回收」步骤处理。
