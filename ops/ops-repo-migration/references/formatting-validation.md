# 目标副本的格式化与源码核验

源包、原 golden、冻结 CSV、输入二进制和原验证证据保持只读。目标仓的格式门禁可能要求
换行、缩进或引号样式与源工程不同；这类必要格式化可以在目标副本中进行，但不能借机
重写实现、调整公式、改变接口、修改预期值或放宽容差。

## 在构建前收敛格式

1. 完成目录和构建适配后，对本次目标文件运行该仓的 pre-commit，保留工具版本、命令、
   退出码和自动修改前后的完整 diff。第一次因自动格式化返回非零不算门禁通过。
2. 逐项审阅自动修改，只保留许可证注释和核验通过的格式变化。Ruff 等检查器的自动修复
   不一定只是排版；不能因为来自 hook 就自动接受。无法确认等价的改动停止并报告。
3. 再跑同一门禁，直到退出 0 且目标文件不再变化，才构建、安装并运行原有回归。
   不以 SKIP、no-verify、格式化屏蔽注释或仓级排除规则规避门禁。

## 按语言核验

- **C/C++/Ascend 源码**：保留 `verify_logic_unchanged.sh` 的完整差异清单，逐文件核对
  词法 token 与预处理语义。标识符、运算符、字面量、include 顺序、条件编译和宏替换内容
  必须保持；注意字符串、宏续行、函数式宏及字符串化的空白敏感性。不能用删除全部空白、
  `git diff -w`、formatter 退出 0 或测试通过代替等价核验。必要时用当前编译器的词法或
  预处理输出辅助检查；行号内建宏等依赖源码布局的情形不能仅凭普通 token 相同放行。
- **Python golden**：必须对原 golden 与目标副本做 AST 比较，使用
  `ast.parse(text, type_comments=True)` 后比较
  `ast.dump(tree, include_attributes=False)`。函数、控制流、调用、常量、字符串值、
  注册映射及类型注释均参与比较，不删除节点或只比较函数名。语法错误或 AST 不同即失败；
  AST 相同仍须审阅 diff，排除依赖源码文本、行号或动态生成代码的行为变化。
  原回归继续使用冻结源 golden，目标副本的等价证据另行归档。
- **测试与数据文件**：保留全部用例、断言和预期值。JSON 等只允许经解析核对的数据不变
  的排版；冻结 CSV、二进制和原套件不能为满足格式门禁而改写。

报告分别列出结构/测试驱动适配与格式化差异，记录核验方法和不确定项；不要把格式化后的
目标写成“与源逐字节相同”。源码核验及功能回归均须通过，两者不能互相替代。

## 提交对应受测内容

构建和回归针对格式收敛后的目标副本。提交前再次执行 pre-commit，核对它没有改动任何
受测输入；若再次改写，重新核验差异，并重跑受影响的构建、安装、UT、example 和冻结回归。
最终 commit 的源码必须与受测版本一致。出现非格式语义差异、无法核验的文件或持续失败的
hook 时，记录失败，不创建“已完成迁移”的提交。
