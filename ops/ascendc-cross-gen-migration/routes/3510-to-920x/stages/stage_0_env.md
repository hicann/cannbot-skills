# 阶段 0：确认 DAV_3510→DAV_9201/DAV_9202 目标、环境与证据目录

本阶段确认执行条件；未通过前不执行目标工程的编译、安装或 NPU 测试。用户只要求调研或当前缺设备时，可给出静态分析和缺口，保持 `GATE-0 BLOCKED`。

## LOADED 检查点

读取本路线 [route.md](../route.md)、[platform-and-api-diff.md](../references/platform-and-api-diff.md)，记录 `[LOADED] 3510-to-920x/platform-and-api-diff`；芯片映射按名称加载 `npu-arch`。

## Step 0.1：记录实际执行环境

优先复用用户已提供的环境和当前环境变量。CANN 路径从 `ASCEND_HOME_PATH` 或用户明确配置读取；无有效路径时询问，不能扫描文件系统猜测。记录：

| 变量/事实 | 取得与核实方式 |
|---|---|
| `OP_DIR`、`OP_NAME`、源码提交/工作差异 | 待迁移工程；区分源 3510 实现与其他未提交修改 |
| `SOURCE_ARCH=3510`、`TARGET_ARCH`、`SOC` | DAV_9201 使用 `9201 / ascend960dt`，DAV_9202 使用 `9202 / ascend960pr`；源配置、目标工具链与实际设备信息相互核对，不能交叉配对 |
| `CANN_SET_ENV`、CANN/编译器版本、host 架构 | 用户给定或环境已声明的路径及版本文件 |
| `PYTHON_PATH`、torch/torch_npu 版本、设备号与健康状态 | 当前 Python 或用户环境；只在确认 CANN 后做最小设备可用性验证 |
| 实际编译用 SDK/devkit 版本与头文件目录；另用源码时记录 `DEVKIT_PATH` 及其版本 | 确认所选 9201 或 9202 的声明、目标分发与实现，不能只查另一份新源码或 9201 分支就认定 9202 工具链支持 |
| 平台注册及其工程依赖 | 核对注册结果覆盖所选目标、依赖版本和链接来源；缺口记录并解决 |
| 资源参数与模板预留 | 按 [平台参数获取与传递](../references/tiling-and-memory-guide.md#平台参数获取与传递) 核对查询接口、返回值、单位及预留来源 |
| 构建与安装方式 | 读该提交的 `build.sh --help`、构建文档、安装包帮助；记录 vendor、安装路径和环境激活方式 |

记录平台接口返回的 `UB_REPORTED_BYTES`、必要的模板预留及计算得到的 `UB_WORK_BUDGET_BYTES`，核对预留是否已在接口返回值中扣除。核数按计算单元分别查询；硬编码或缺少来源的资源参数列入改造清单，不以其他型号或源平台的数值代替。

## Step 0.2：初始化知识与运行记录

1. 优先识别实际 CANN SDK 的目录布局、编译 include 路径和配套文档版本；记录发行版本与文件来源，不要求额外克隆代码仓。若为补充证据使用 devkit 源码，再记录其实际路径与版本。
2. 使用参考源码时，确认其与构建所用 SDK 的版本关系。新 API 必须在实际工具链可用；不支持时采用合法旧路径或先解决依赖，不能以另一个仓库快照替代工具链支持证明。
3. `knowledge-query` 可用时按当前安装说明检索；没有索引则记录 `KNOWLEDGE_INDEX=UNAVAILABLE`，继续使用已核实的官方原文，不能捏造命中卡片。`ops-precision-standard` 或公共精度标准须可读。
4. 按 `route.md` 创建包含所选 `${SOC}` 的独立 `${EVIDENCE_DIR}`，将本节事实写入 `env_info.md`；9201/9202 分别记录，不覆盖其他迁移记录或在日志中写凭证。

所有执行命令使用本阶段记录的 `${CANN_SET_ENV}`、`${PYTHON_PATH}`、`${OP_DIR}` 等变量。预设的构建和安装动作须符合当前任务授权，涉及共享环境时沿用用户已给定的目标。

## 产物与 Gate

`env_info.md` 必须包含可复核的版本/映射、设备验证输出、资源查询及预留依据、路径与构建安装约定；未知值明确标注。

- 执行所需环境、设备、目标 API/资源与依赖均已确认：`[GATE-0] ENV_CONFIRMED`。
- 缺实际设备、工具链或必要资源依据：`[GATE-0] ENV=NOT_VERIFIED BLOCKED`，列出缺项；不据静态文档输出已确认。
