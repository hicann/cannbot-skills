## 现象 / 触发
Level 2/3 NPUKernelBench op references `torch_npu.npu_*` fused op as reference

**SCOPE NARROWED 2026-05-24T19:02Z (owner directive msg DISCORD_ID_REDACTED)**: pure-PyTorch fallback is ONLY acceptable as the **kernel-implementation algorithm specification** (so the harness knows what algorithm to generate) — NOT as the **PASS verification truth source**. Using our own CPU implementation as truth for "kernel matches truth → PASS" verdict is **circular self-validation = cheating** — the customer running our harness independently has no independent ground truth, just our claim that our kernel matches our own CPU code. Anti-cheat rule: PASS verification truth source MUST be **vendor-independent** (e.g. actual A3/V351 CANN binary output, or hand-derived bit-exact reference per spec). When neither is available → case is **FAIL_NO_INDEPENDENT_TRUTH**, ship demotes to PARTIAL. Do NOT auto-substitute Model.forward (our CPU code) for missing vendor reference in pass_a_runner.

## 教训 / 根因
Some `torch_npu.npu_*` fused ops (e.g. `npu_group_norm_swish`) are not registered in binary_info_config.json on Ascend950PR, failing with "does not support opType". **Algorithm-spec usage**: when the NPUKernelBench source uses `torch_npu.npu_X` but the target hardware does not support it, the "Pure PyTorch implementation" given in the source docstring may be referenced AS THE ALGORITHM TO IMPLEMENT (so the worker knows what math to write in the kernel). Upcasting with `.float()` in the algorithm spec for numerical stability is allowed (matching PyTorch nn.functional behavior). **Verification-truth usage (FORBIDDEN per anti-cheat)**: do NOT use pure-PyTorch as PASS verification truth source when vendor reference is broken — the case must instead be marked FAIL_NO_INDEPENDENT_TRUTH.

  - 29_DynamicQuant (2026-05-01): `torch_npu.npu_dynamic_quant` accepts only DT_FLOAT16/DT_BFLOAT16 (rejects fp32 with `aclnnDynamicQuantV2` err 161002 `Tensor not implemented for DT_FLOAT, should be in dtype support list [DT_FLOAT16,DT_BFLOAT16,]`). Combined with `base_shape_filter: lambda s: len(s) >= 2` to filter case_gen's rank-1 typical shapes that npu_dynamic_quant rejects. Path B succeeds 11/11 once SCHEMA is dtype+rank constrained. **Implication for SCHEMA design**: Path B preflight should always confirm the reference accepts the SCHEMA's chosen dtype before generating cases.
  - 3_FusionAttention benchmark on Ascend910_9382 (2026-05-21, fusionattention-kw-2 → kw-5 evidence chain): **counter-evidence to blanket Case A claim for `torch_npu.npu_fusion_attention` on Ascend910 V220** — canonical Pass A evaluator invoked `torch_npu.npu_fusion_attention` directly on case_3 ([4,64,512] BSH head=8 fp16) and it produced numerically reasonable output (mere=2.227e-6, mare=0.0112 vs CPU fp64 truth; deterministic across 3 consecutive runs, bit-identical measurements). Other shapes/dtypes/optional features (SBH/BSND/BNSD layouts, bf16/fp32, pse/atten_mask/sink/sparse_mode) remain un-probed. **Procedural implication**: when an OL-68 Case A claim is broad ("unreliable on all SOCs"), the canonical Pass A evaluator's CANN-on-NPU run is the cheapest empirical probe to scope the claim per-shape per-SOC. That broader per-shape sweep is out of scope of any single kw spawn.
