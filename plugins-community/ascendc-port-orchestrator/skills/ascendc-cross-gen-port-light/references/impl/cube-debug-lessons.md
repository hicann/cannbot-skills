# Cube 类算子迁移：测试与 debug 排查手册

> 定位：迁移过程中测试构造与异常排查——按「错误信号 → 排查手段 → 解决方法」组织。
> 配套：`cube-migration-guide.md` = 迁移指引。

---

## Part 1：死锁 / 卡死（aicore timeout）

### 1.1 错误信号

| 信号 | 判别含义 |
|------|------|
| 精度测试卡死，aicore timeout（如 507014），特定 shape/dtype 组合**全部**触发（如某 dtype 命中某路径卡、另一 dtype 不卡） | 条件触发型死锁——只在特定配置组合的路径上发生，正常组合测不出 |
| AIC 与 AIV 核号**同时**超时，`sc error info: 0xffffffffffff`（全核等待） | 跨核同步死锁特征：等待方永远等不到对端 |
| 批量用例首例 timeout 后大量用例连锁 timeout | 首例堵 stream 污染后续——**必须先定位首个超时用例**，后续多为污染 |
| 不死锁但输出全零/均匀（如 softmax 恒为均匀分布） | 同步 PIPE 选错：只阻塞了错误流水，数据流提前执行读未就绪数据——**不是死锁**，判别方向完全不同 |

### 1.2 排查手段

1. **定位首个超时用例**：批量用例连锁 timeout 时先剥离污染，只复现首例。
2. **无同步路径对照法（首选实验）**：构造一条**不含跨核同步**的同类路径对照运行（如去掉跨核握手走纯串行路径）。对照路径 PASS → 死锁 100% 在同步区，一次实验定界，不用逐行猜。
3. **静态配对推导自洽 ≠ 不死锁**："谁等谁"配对表自洽无环只是必要条件。用 tiling host 打印（coreNum、每核分片、同步区执行次数）抓**真实执行数据**，核对实际参与集合。
4. **插桩不可用约束**：卡在同步点前的核执行不到插桩语句，PRINTF/DumpTensor 无法回传——不得依赖插桩定位。
5. **写法与官方示例一致不能排除问题**：写法一致只排除"写法因素"，问题可能在参与集合执行细节（哪些核没执行 Set）——回到手段 3。

### 1.3 解决方法

1. 逐同步点核对集合粒度：推断"谁等谁" → 对照目标平台该模式的参与集合语义 → 假设粒度 < 文档粒度 → **禁用该路径走标准流程**（决策规则全文见 `cube-migration-guide.md` 改动 6）。
2. 禁用不可行路径后复测：修复成立的判据 = 原超时用例 PASS 且其余用例不回归。
3. PIPE 选错（输出全零）的修复：同步 PIPE 参数必须选**数据流所在流水**，且核对目标平台支持的流水集合。

## Part 2：结果部分/全部错误（mask 与 API 消费粒度）

### 2.1 错误信号

| 信号 | 判别含义 |
|------|------|
| mask 完全未生效（如 causal 位置 0 输出 ≈ 无 mask 参考） | 约定层或消费层问题 |
| 部分输出行正确、其余行全被替换，正确行呈规律性子集（如每 8 行 1 行） | mask 消费粒度与输入布局错位（位图 vs 逐元素） |
| 输出呈均匀分布（数值 ≈ 数据均值） | 全元素替换后 softmax 均匀——数据幅度小时该特征可能被误读为"正确" |
| 同 shape 走某路径正确、不走该路径错误（反之亦然） | 路径级问题——见 Part 3 与 `cube-migration-guide.md` 改动 9 |

### 2.2 排查手段

1. **两端实验判定 mask 约定**（不靠读代码猜）：全 1 mask → 全屏蔽 → 输出 ≈ 均匀/均值；全 0 mask → 无屏蔽 → 输出 = 无 mask 参考。两个端点一秒判定"1"的语义。
2. **判别顺序**：现象 → (a) 输入数据是否符合目标接口约定？(b) API 文档语义是什么？(c) 最后才怀疑平台差异。"行为异常"先怀疑调用约定，再怀疑平台 API 差异。
3. **分层取证打印**：先打"输入侧"（参数值、GM 字节、UB 字节）确认搬运与寻址正确，怀疑面收窄到 API 消费语义后再打消费层——用数据排除变量，不靠猜。注意 AIV 打印约束：元素打印用 `t.GetValue(i)`（`operator[]` 返回子张量视图，不能隐式转标量），多种类型混打用 `(uint64_t)` 显式转换。
4. **精确值判别**：用"判别力强的模式"（半 mask、精确位置值）验证，不用"整体差不多"的模糊判据——均匀输出可能恰好近似正确。
5. **消费粒度随 mask dtype/API 变化**：同一遮罩语义在不同 dtype/API 下可能是逐元素或位图消费（uint8 按位图 8 元素/字节）——以目标平台 API 文档为准，或从错误输出的规律性子集反推消费粒度。

### 2.3 解决方法

1. 按**目标平台接口约定**构造测试 mask：1 的语义以目标平台为准；参考实现与 kernel 约定相反时在一侧取反，不能同一张 mask 直接喂给两侧。
2. mask 消费粒度与布局不匹配时：按消费方式重新排布 mask 数据，或改用逐元素语义的 API。

## Part 3：验证覆盖与结果判定

### 3.1 错误信号

单路径（或少数路径）验证全 PASS，完整套件（全功能路径）仍有大量失败/超时——"验证通过"被定义在路径之外。

### 3.2 排查手段

按**功能路径**拆解套件：每个功能开关/条件分支（有/无、不同模式、特殊对齐形状）各覆盖 ≥1 用例；且覆盖**条件触发路径的命中与不命中两侧**——条件触发型失败只在特定组合暴露，只测正常组合无法发现（与 1.1 条件触发型死锁同因）。

### 3.3 解决方法

"验证通过"必须定义到**路径级别**（哪些路径验证过、哪些没有），不能以单路径 PASS 代表整体。迁移 diff 审查（编译期守卫/初始化调用/host 框架级调用三类"看起来无害"的删除与遗漏）见 `cube-migration-guide.md` 改动 9。
