# a5 Device Constraints

Read when writing any kernel that targets the A5 family (`easyasc.a5` for
`950`, `easyasc.a5pr` for `950pr`).
Do not use in place of the selected workflow and authoring preflight.

## 1. Feature surface

A5 exposes a VF/micro surface (`@vf()` is the normal entrypoint; `micro`
helpers are the lower-level register-side building blocks used inside that
flow), an A5-only `@simt` escape hatch, and on-chip helper surfaces on top of
the standard cube ops:

| Layer | Use it for |
|---|---|
| `@vf()` decorator | default structured entrypoint for regular UB-side vec work: elementwise, row-wise, reduction, normalization, cumsum |
| `micro` helpers | lower-level register/mask/datamove control inside `@vf()` when the structured form needs extra precision (fp8 cast, `pack4`, mask, row-scan) |
| `@simt` decorator | irregular scatter/gather, atomics, branchy control, probes |
| `ub_to_ub` | UB-local copies and layout-preserving handoff steps |
| `ub_to_l1` / `ub_to_l1_*` | Vec-to-cube L1 publish; raw `ub_to_l1` uses 32B block units |
| Sort family | `sort32`, `mergesort4`, `mergesort_2seq` when sort is genuinely needed |

Rule: if you are about to do regular vec math on an a5 UB tensor from the
kernel body, stop and move that logic into `@vf()` first. Treat `@vf()` as the
default way to author A5 micro-side compute. Drop to explicit lower-level
`micro` helpers only when the structured `@vf()` form alone cannot express the
needed register/mask/datamove control.

For `@vf()` scans, cumsums, and row-wise recurrences, keep the running state in
`Reg` / `RegList`. Do not use an in-place UB tensor as both the base-value
source and prefix/reverse-prefix destination inside the same VF loop. A
`vf_barrier(STORE, LOAD)` orders local memory streams, but it does not turn that
UB read/write alias into scalar program order on hardware. Prefer direct
register accumulation for both the base value and recurrence when possible. If
base values must be staged before a scan, stage them in one UB tensor and write
the scan result to another UB tensor, but treat that as a hardware-validated
exception: a separate UB round trip also failed the random-input hardware probe.

a2 does **not** support `@vf()`, `micro`, or `@simt`. Do not copy a2 vec-body
patterns into a5 kernels, or a5 `@vf()` / `@simt` flows into a2.

## 2. Topology priority

A5 SIMT exists, but it is not the normal performance path. Start every a5
implementation by looking for regular hardware structure:

1. Dense dot products, batched matrix products, transpose-matmul chains, and
   GEMM-like reductions go to cube `matmul`.
2. Regular preprocessing/postprocessing around cube work goes to `@vf()` or
   `micro`: casts, elementwise math, masks, row reductions, scans, compact
   publish, and cube-result epilogues.
3. Use `ub_to_l1` / `ub_to_l1_nd2nz` / `ub_to_l1_nz`, `l0c_to_ub`, and
   `l0c_to_l1` to keep cube/VF stages on chip whenever the layout and dtype
   permit it.
4. Use `@simt` only when the algorithm is genuinely irregular: data-dependent
   scatter/gather, atomics, branchy per-element control flow, targeted runtime
   probes, or logic that VF + matmul cannot express cleanly.

Do not introduce a SIMT "correctness baseline" for a subgraph whose dense
contractions and regular elementwise stages are already visible. That creates
the wrong default and usually hides the real layout/sync work until later.

## 3. Device identity and cap lookup

The a5 facade targets device `"950"`. Use
`agent/references/facts-device-runtime.md` for exact caps, core counts, pipe
maps, and quick mutex signatures. This file only records a5-specific authoring
consequences.

## 4. Cross-side handoff consequences

On a5, cube ↔ vec handoffs can stay on chip: cube -> vec can use `l0c_to_ub`,
and vec -> cube can publish through `ub_to_l1` / `ub_to_l1_nd2nz` /
`ub_to_l1_nz`. No GM workspace bridge is required for the handoff, unlike the
a2 model.

See `agent/references/facts-device-runtime.md` for exact mutex signatures and
`constraints/sync.md` for barrier, pipe, and lifetime semantics.

## 5. Cube-side dependency reuse

When a later cube matmul depends on an earlier cube matmul result, prefer the
direct path:

```
mmad → L0C → l0c_to_l1 → l1_to_l0 → mmad
```

Avoid the detour `L0C → UB → L1` unless a genuine vec-side transform (cast,
normalization, `@vf()` stage) is required. The UB detour adds traffic and
synchronization without adding capability.

Fence this path explicitly. `auto_sync()` does not create the `FIX → MTE1`
edge between `l0c_to_l1` and the next `l1_to_l0` / `matmul` consumer. Use
`SEvent(Pipe.FIX, Pipe.MTE1)` for a one-shot dependency, or the ready/valid
pair described in `constraints/sync.md` when the L1 slot is reused across
overlapped iterations.

## 6. MX FP8 / MXFP4 matmul

a5 exposes an MX matmul path through either `DT.e4m3` / `DT.e5m2` L1 inputs
with `DT.mx_e4m3` / `DT.mx_e5m2` L0A/L0B compute views, or packed MXFP4
`DT.fp4_e2m1` / `DT.fp4_e1m2` carrier-backed views. e8m0 scale bytes are carried
as `DT.uint8` in both cases.

Scale storage is the sharp edge. Do not infer it from the logical
`[rows, ceil(K / 32)]` math view:

- external GM scale is `[row_tile, k64_block, 16, 2]` flattened to
  `GMTensor(DT.uint8, [num_blocks, 32])`
- one 32-byte GM block stores one 16-row tile and two K-32 groups, ordered as
  `row0_g0, row0_g1, row1_g0, row1_g1, ...`
- `gm_to_l1_mx_scale(...)` is the GM->L1 scale path; do not use
  `gm_to_l1_nd2nz` for MX scale
- L1 scale is declared as `Tensor(DT.uint8, [16, 2 * k_blocks], Position.L1)`,
  but its bytes keep the same compact K-64 block stream
- `l1_to_l0_mx(...)` moves those bytes into the hidden L0AMX/L0BMX buffer;
  the scale tensor cannot be a transpose view
- for low-level NZ2ZN, scale must already be packed in post-transpose row
  order; `LoadData2DMxParams` does not transpose scale

Current authoring constraints:

- use `matmul_mx(...)` for normal kernel code unless you are testing the
  low-level stubs directly
- `matmul_mx(...)` supports NZ2NZ and A/B-side NZ2ZN through `l1a.T` or
  `l1b.T`; do not pass transposed scale tensors to the shortcut
- low-level `l1_to_l0_mx(...)` supports `src.T` for L0A and L0B NZ2ZN. Keep
  `m_dst/n_dst/m_src/n_src` in physical source order; for an A source
  `[K, M]`, pass `m_dst=K, n_dst=M, m_src=K, n_src=M` and use scale shape
  `[M, 2 * ceil(K / 64)]`; for a B source `[K, N]`, use
  `[N, 2 * ceil(K / 64)]`
- low-level NZ2ZN split-K/split-N must offset the full pre-packed scale tile
  with `src_mx_offset_element`; do not rely on ordinary Tensor slicing for MX
  scale. Use `(subk // 64) * 32` for split-K on any transposed operand and
  `(subn // 16) * ceil(K / 64) * 32` for B-side split-N scale rows
- low-level transposed MX loads (`src.T` / NZ2ZN) require both physical source
  dimensions to be C0-aligned: 32 elements for FP8, 64 elements for FP4
- shortcut `l1b.T` split-N uses 32-column chunks for FP8; FP4 needs 64-element
  physical alignment, so use 64-column static split-N or pad the L1 tile before
  the NZ2ZN load
- static NZ2ZN tiles require both physical source dimensions to be aligned:
  32 elements for FP8, 64 elements for FP4; tail support needs a padded L1 data
  tile
- scale value `127` means multiplier `1.0`; in general scale is
  `2 ** (value - 127)`
- scale is per row and per K-32 group, but all movement follows the K-64 block
  stream above
- host-side reference helpers for FP4 uint8 carriers and e8m0 scale bytes live
  under `easyasc/dtypehelper/` and are exposed through `easyasc/a5.py`
- shortcut `splitk` and `splitn` both exist, but cannot be enabled together
- static `splitk` must be a multiple of 64; static `splitn` must be a multiple
  of 16; for `l1b.T`, static `splitn` must satisfy the transposed load
  alignment (32 for FP8, 64 for FP4)
- `splitn` requires `scale_b.shape[0]` to match the full B logical row count so
  B scale row tiles remain physically addressable. For `l1b.T`, the physical B
  source is `[K, N]` but `scale_b` is `[N, 2 * ceil(K / 64)]`.

Detailed contract and examples: `doc/topics/mxfp.md`.

### 6.1 C310 plain Cast widening must not use the verified-broken ONE parts

The CANN 9.0 C310 header advertises `RegLayout.ONE` for ordinary widening
casts, and the simulator models that ideal slot-selection contract. Real
Ascend950 evidence is stricter: the ONE part is all zero for these exact plain
`MicroAPI::Cast` pairs on the shared `950` / `950pr` C310 family:

- `DT.int8 -> DT.half`;
- `DT.half -> DT.float`;
- `DT.bfloat16 -> DT.float`;
- trait-one `DT.float -> DT.int64`.

The WeightQuantBatchMatmul three-tensor diagnostic matched the first three
failures byte-for-byte by clearing only data fed through ONE parts. The GRU
stage-isolation probe found the trait-one float-to-int64 ZERO half exact and
the ONE half all zero. Its trait-two ZERO replacement passed all 64 lanes and
the complete fixed-point GRU execution.

The public A5 plain `cast()` stub rejects only those four ONE configurations.
Do not extend that guard without hardware contract evidence. In particular,
same-width casts, wide-to-narrow casts, native BF16 <-> FP4 P0-P3 layouts,
`ExpSub` / `MulsCast`, and other unverified widening pairs retain their current
contracts. The simulator keeps ideal slot semantics so direct runtime tests do
not reinterpret the hardware defect as correct math.

Use one of two ZERO-only bridges:

- for `int8 -> half` and `half`/`bfloat16 -> float`, Interleave the contiguous
  source with a zero register. The lower and upper output registers then hold
  their live values in even slots; cast both with `RegLayout.ZERO`. The A5
  SwiGlu packed path is the production reference;
- for full-width 32-bit-to-int64 conversion, use one
  `RegTensor<int64_t, RegTraitNumTwo>`, a matching trait-two mask, one
  `RegLayout.ZERO` cast, and continuous Normal b64 movement. GRU, ArgMax, and
  CumMin contain validated forms.

Full code skeletons and the abstract layout model are in
`doc/api/a5_micro_cast.md`.

### 6.2 Native BF16 <-> FP4 cast constraints

A5 `MicroAPI::Cast` supports register casts between `DT.bfloat16` and
`DT.fp4_e2m1` / `DT.fp4_e1m2`. The source-backed contract is the CANN 9.0
[Cast API](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/900/API/ascendcopapi/atlasascendc_api_07_0398.html)
plus the installed C310 `kernel_reg_compute_vec_vconv_impl.h`.

- BF16 -> FP4 supports `TO_EVEN`, `AWAY_FROM_ZERO`, `FLOOR`, `CEIL`, and
  `TRUNC`; FP4 -> BF16 uses `RoundMode.NONE`.
- Use `MaskMergeMode.ZEROING`. The cast mask follows the wider BF16 element
  width, so use `MaskReg(DT.bfloat16)` (128 lanes).
- Use `RegLayout.ZERO`, `ONE`, `TWO`, or `THREE`. Do not use
  `RegLayout.UNKNOWN`: the C310 compiler rejects it because the underlying
  BF16-to-FP4 `vcvt` requires one of `P0..P3`.
- `RegLayout.ZERO` places carrier bytes in every fourth uint8 register slot;
  dense public carrier output therefore requires an explicit compaction stage.
- C310 preserves signed zero: a negative BF16 input that rounds to zero emits
  FP4 nibble `0x8`, not `0x0`.
- A Reg reinterpret must lower to a C++ reference alias. A value copy taken
  before the cast keeps stale register contents and produces zero carriers.

The complete cast -> live carrier alias -> `pack4()` composition lives in
`agent/references/patterns/a5-fp4-cast-pack.md`.

### 6.3 Exact uint2 carrier constraints

For inputs guaranteed to contain only the exact BF16 values `0`, `1`, `2`,
or `3`, numeric conversion is valid instead of BF16 exponent-bit extraction.

For consecutive values `a,b,c,d`, the carrier byte is
`a | (b << 2) | (c << 4) | (d << 6)`. This path intentionally has no clamp or
range check; adding either changes the contract and instruction sequence.

The inverse packed uint2 -> BF16 path has these layout constraints:

- `DIST_UNPACK4_B8` places each carrier byte in the low byte of a uint32 lane;
- a `uint8 -> half` P0 cast reads the even byte of every uint16 lane, not the
  first 128 contiguous uint8 lanes. Store the 128 dense bytes to UB, issue a
  `VEC_STORE -> VEC_LOAD` local barrier, then reload them with
  `DIST_UNPACK_B8` before casting;
- `DIST_NORM_B8` writes the full 256-byte register even when only a prefix mask
  is active, so the intermediate UB scratch allocation must be 256 bytes.

The complete encode/decode bitfield composition lives in
`agent/references/patterns/a5-uint2-pack-unpack.md`.

## 7. Micro mask row stores

`update_mask(mask, cnt)` is useful for row-width micro register loads/stores,
but do not treat it as an arbitrary per-lane prefix mask for UB memory ops.
The simulator expands `micro_ub2reg` / `micro_reg2ub` masks to C0-sized blocks
(`easyasc/simulator/pipe_micro.py:_expand_mask_c0`), so for fp32 any active
lane in an 8-lane C0 group makes the whole group active. For triangular row
updates, write a compact fixed-width row (for example 16 fp32 lanes) and repair
sparse scalar positions such as the diagonal afterward, instead of using
`update_mask(i)` for `i < 16` and expecting only lanes `0:i` to be stored.

For micro math ops, inactive lanes are not "preserve destination" lanes:
binary/unary/unaryscalar inactive destination lanes are written as zero, while
source registers are left unchanged. Use explicit `select` or a prior load of
the old destination value when preserve-old semantics are required.

`var_assign` inside `call_micro` is supported for integer-category assignments
such as `int -> uint32`, and remains rejected for integer/float conversions. If
the assignment is only a static mask-width setup, a fresh
`Var(value, dtype=DT.uint32)` is still the simplest form.

## 8. CANN-safe micro gather/scatter indices

For A5 micro gather/scatter, keep the CANN index dtype signatures in mind even
when the simulator accepts a broader integer-looking path:

- `DataCopyGather` / `DataCopyScatter` use `uint16` indices for 8-bit and
  16-bit data, `uint32` for 32-bit data, and `uint32` or `uint64` for 64-bit
  data. All combinations are sim + Ascend950 board-validated (2026-07-21) and
  covered by `agent/example/testcases/simulator/micro/test_micro_gather_scatter_ops.py` +
  `agent/example/kernels/a5/vec_only/gather_scatter_onboard.py`.
- `ub_to_reg_gather` for an **8-bit source is a `b8 -> b16` byte zero-extend**:
  the source byte lands in the low 8 bits of a 16-bit `dst`, high 8 bits zeroed
  (`int8` `0xFF` -> `255`, not `-1`). It therefore requires a 16-bit `dst`; the
  8-bit same-width (`b8 -> b8`) case is what is rejected. Same-width gather
  (b16/b32/b64) still requires `dst.dtype == src.dtype`.
- **`reg_to_ub_scatter`'s mask is lane-wise**, unlike the continuous
  `reg_to_ub_*` / `ub_to_reg_*` paths, whose masks are expanded to whole `C0`
  blocks. A scatter writes exactly its active lanes: 5 active lanes of an 8-lane
  b32 block move 5 elements, and an even-lane mask on a b16 register keeps the
  odd lanes from clobbering the `cast` results they share an index with.
  Board-verified 2026-07-29 (`agent/example/kernels/a5/vec_only/scatter_mask_probe.py`); the
  simulator expanded it to `C0` until then and was corrected to match, with
  regression tests in `agent/example/testcases/simulator/micro/test_micro_gather_scatter_ops.py`.
- **`reg_to_ub_scatter` for 8-bit data scatters only the EVEN source lanes**:
  `dst_flat[index[k]] = src[2k]` for the 128 `uint16` indices; the odd source
  bytes are ignored (board-verified; matches the earlier CANNSIM "odd columns
  zeroed" observation). To place a dense FP8 payload, cast even/odd logical rows
  separately, pack each 32-value group, then interleave/scatter through a
  `uint16` carrier view.
- `micro.Arange` does not produce unsigned registers. When CANN requires
  `uint16` or `uint32` indices, generate a signed arange into scratch UB,
  reinterpret that scratch as the required unsigned dtype, then load it into
  the index register. `Reg.reinterpret()` does the same without the UB round
  trip, and `cast(int16_reg, int32_reg)` (NONE rounding) narrows a 32-bit index
  register into the **even** b16 lanes -- exactly where a 16-bit gather index
  belongs (see the next bullet).
- **A 16-bit gather is indexed per b16 lane, and `cast` widens the even ones.**
  `ub_to_reg_gather` into a `Reg(DT.half)` / `Reg(DT.bfloat16)` fills all 128
  lanes, but the `cast` to fp32 that normally follows only consumes lanes `2i`.
  So the index register must hold the wanted element index at lane `2i`; the
  odd lanes may hold anything. Build it as `shiftrs(idx, lane_ramp, 1)` plus
  the row base, which is the same layout `ub_to_reg_unpack` produces. Sim +
  Ascend950 board-validated (2026-07-29,
  `agent/example/kernels/a5/vec_only/gather_cast_b16_probe.py`, and the whole narrow-dtype
  half of `cann_bench/adaptive_avg_pool_3d` in the extension repository).
- `arange(dst, start, increase=False)` **does** produce a decreasing ramp
  `[start, start-1, ..., start-VL+1]` (VL = 256/itemsize) -- `start` is the
  first/max lane, matching `increase=True`. The raw hardware `Arange<DEC>(s)`
  instead ends the ramp at `s` (`[s+VL-1, ..., s]`, s = min/last lane), so the
  codegen shifts the emitted scalar by `-(VL-1)`; sim and board agree
  (board-verified 2026-07-21). Before that fix a decreasing arange diverged
  sim vs board -- if you see an old kernel that hand-compensated with a
  `start+VL-1`, drop the compensation.

## 8b. Register <-> UB continuous access must be 32-byte aligned

`ub_to_reg_*` and `reg_to_ub_*` (`micro_ub2regcont` / `micro_reg2ubcont`, and
the `LoadAlign`-based `ub_to_reg_interleave`) require the **UB address** to be
32-byte aligned. The simulator enforces it:

    RuntimeError: micro_ub2regcont src address base must be 32-byte aligned:
                  _tmp_tensor_13 has base byte offset 10

Only `ub_to_reg_gather` / `reg_to_ub_scatter` reach an arbitrary element
offset, and a gather prices the same as an ordinary load (measured 0.995-1.001x
on the Ascend950). That is what makes a **packed** staging tile practical:
`gm_to_ub_pad` rounds every burst up to 32 bytes in UB, so a row-per-burst
transfer both pads the rows and costs one burst per row. Moving the whole run
as a single burst leaves it packed at the true row width -- rows no longer
start on the 32-byte grid, so the compute gathers instead of loading. On
`cann_bench/adaptive_avg_pool_3d` that took a work item from up to 279 staging
bursts down to one.

Probe: `agent/example/kernels/a5/vec_only/unaligned_reg_probe.py`.

## 9. SIMT body indexing

`@simt` bodies shard work across `simt_thread_id()` / `simt_thread_num()`, and
optionally across an outer block identity. Pick the axis from the argument types
of the SIMT body itself:

- **UB `Tensor` args** — shard with **thread axis only**:
  ```python
  for i in range(simt_thread_id(), n, simt_thread_num()):
      ...
  ```
  Do not multiply by `simt_block_idx()` / `simt_block_num()`. `simt_block_idx()`
  lowers to `Simt::GetBlockIdx()`, whose hardware identity matches
  `GetCubeIdx()`, not kernel-level `GetVecIdx()`. The kernel already partitions
  GM data per vec participant before the UB tile reaches the SIMT body; adding
  block sharding to the index expression skips elements or duplicates the two
  vec subblocks on each core. See `agent/example/kernels/a5/simt/simt_axpy.py`.

- **`GMTensor` args, no UB tiling, one logical SIMT block per cube core** —
  `simt_block_idx()` / `simt_block_num()` are valid:
  ```python
  base   = simt_block_idx() * simt_thread_num() + simt_thread_id()
  stride = simt_block_num() * simt_thread_num()
  for i in range(base, n, stride):
      ...
  ```
  Remember that both vec subblocks of the same core run the call site, so this
  pattern duplicates work unless the outer kernel gates the call to one subblock
  or the duplicate writes are intentional.

- **Lane-local GM scatter/atomic with a small `count` selected by the outer
  kernel** — shard with the SIMT thread axis only:
  ```python
  for i in range(simt_thread_id(), count, simt_thread_num()):
      ...
  ```
  Do not add `simt_block_idx() * simt_thread_num()` to this loop. The outer
  kernel has already selected the local tile or scatter slice; adding block
  identity makes nonzero cores start past a small `count` such as 16 and silently
  skip their contribution.

- **`GMTensor` args, GM-wide sharding across vec participants** — pass the vec
  identity from the outer kernel instead of pretending `simt_block_idx()` is a
  vec id:
  ```python
  @simt()
  def body(x: GMTensor, out: GMTensor, n: Var, vec_idx: Var, vec_num: Var):
      base = vec_idx * simt_thread_num() + simt_thread_id()
      stride = vec_num * simt_thread_num()
      for i in range(base, n, stride):
          ...

  body(x, out, N, GetVecIdx(), GetVecNum())
  ```
  If you want to expose the subblock explicitly, pass `GetSubBlockIdx()` and
  compute `vec_idx = simt_block_idx() * 2 + sub_block_idx` inside SIMT. The
  `agent/example/kernels/a5/simt/simt_atomic_add.py` sample shows both forms.

- **Ascend950 64-bit atomic overloads require board validation.** On the CANN
  9.0 Ascend950 toolchain, signed and unsigned 64-bit `Simt::AtomicMax`
  overloads compile and run without a device error but leave GM unchanged.
  The int32 `AtomicMax` and uint64 `AtomicCas` forms are functional on the same
  board. For a monotone 64-bit maximum, use a uint64 CAS retry loop and launch
  512 SIMT threads; the same packed-winner probe failed to make progress at
  2048 threads despite compiling successfully.

- **A compiling 2048-thread SIMT launch can still exceed a runtime resource
  limit.** A Scatter fallback body with coordinate mapping and a reduction
  chain raised device error 507015 at 2048 threads after one additional
  uniform coordinate branch was introduced. The same body is stable at 512
  threads; for its measured 8192-owner workload, that change retained all
  active parallelism and improved board time. Treat 512 as the conservative
  launch bound for branch-heavy SIMT bodies unless a 2048-thread build has been
  validated with the final body on hardware.

## 10. Host reference helpers in DSL files

`from easyasc.a5 import *` exports the DSL `range`, which shadows Python's
built-in `range` in the whole file. Host-side PyTorch references or list
comprehensions in the same module should use `builtins.range` explicitly;
otherwise non-kernel Python loops can receive `Var` loop indices and fail in
ordinary tensor slicing.

## 11. UB bank conflict on NZ / strided stores (board-only, high impact)

A5 UB is **banked**. A strided/scatter UB store — e.g. `reg_to_ub` packing an NZ
tile one fractal row at a time — whose stride is a **power of two** (32 / 64 /
128) makes every row land in the same bank set and serializes. This is a
**board-only ~30% regression the simulator cannot see** (it models UB as flat
memory, so the kernel is bit-exact in sim and only slow on hardware).

Pad the fractal-row stride to an **odd** number:

```python
FRAC_STRIDE = ROWS_PER_SB + 1          # 64 -> 65: consecutive rows hit different banks
ub_p_nz = DBuff(DT.bfloat16, [FRAC_STRIDE, TILE_N], Position.UB)   # one pad row
reg_to_ub(ub_p_nz[... + r * NZ_C0], p_bf16[c], FRAC_STRIDE)
```

Skip the pad row on the `UB -> L1` copy so the L1 tile stays compact: `ub_to_l1_nz`
/ `UB2L1_NZ` takes a separate source stride `srcStride = src.shape[0] -
src.span[0]` (= `65 - 64 = 1`). Board: **167.67us (stride 64) -> 128.05us (stride
65)**, matching the ND path.

**Always board-validate timing for any NZ / strided UB store; this trap is
invisible in the simulator.** A retained odd-stride implementation lives in
`agent/example/kernels/a5/attention/pfa/qk_softmax_pv_flat.py`; the shape-vs-span source
stride lowering is in `easyasc/resources/tensorutils.h` (`UB2L1_NZ`).

## 12. Per-token scalar bursts need one 32-byte row per token

An isolated micro `.single()` / `.single_value()` address may be unaligned, but
that does not make a repeated one-element GM-to-UB or UB-to-GM burst layout
dense. On A5 hardware, staging one scalar per token with `m > 1`, `n == 1` into
a compact `[1, L]` or `[L, 1]` UB layout can misaddress later rows even when the
Python simulator passes.

Give each token one physical 32-byte UB row and use only its first element:

```python
SCALAR_ROW = DT.bfloat16.C0
scalar_ub = Tensor(DT.bfloat16, [L, SCALAR_ROW], Position.UB)
gm_to_ub_pad(scalar_ub[0:L, 0:1], scalar_gm[...], L, 1, src_gap, 0)
value <<= scalar_ub[row:row + 1, 0:1].single()
```

Use `DT.float.C0` for fp32 scalar rows. Preserve the `[L, C0]` physical backing
on output staging as well, even when the logical output slice is `[L, 1]`.
This is a physical burst-pitch requirement, not a general ban on unaligned
scalar-address micro instructions. The retained hardware-safe examples are
`agent/example/projects/a5/kda_bwd/kernels/finalize_pre.py`, `inverse_epilogue.py`, and
`finalize_post.py`; the project-level hardware gate is documented in

## 13. load3d img2col and the transposing GM -> L1 NZ copy

Three board-confirmed rules govern the `l1_to_l0a_img2col` conv path. All three
were found on Ascend 950 with
`easyasc_cannbench_kernels/kernels/a5/conv/cann_bench/conv_2d/conv_2d_fast.py`.

**`mExtension` fixes the L0A K-fractal stride.** `load3d` lays out consecutive
K fractals at a stride derived from the `m` extent it was given, so the window
must be exactly as tall as the L0A tile even when the live rows are fewer.
Passing a shorter window and a matching shorter `M` to the following `mmad`
still reads the wrong fractals. The hardware also rejects a window that runs
past the img2col matrix (`K_M_EXT_STEP is illegal`), so grow the local bottom
pad until the view is at least one whole `m` tile tall; the extra rows are pure
pad zeros and are simply not stored.

**`gm_to_l1_dn2nz` rounds its NZ C0 stride up to 16 rows.** `GM2L1_DN2NZ` sets
`dstNzC0Stride = align16(M_dst)`, so a single call may only cover several C0
blocks when the destination plane is itself 16-row aligned. With an unaligned
plane the C0 blocks drift apart and every consumer that assumes a packed
`h*w*C0` stride - `img2col` among them - reads the wrong block. Either issue one
call per C0 block or gate the grouping on `(M_dst % 16) == 0`.

**An unaligned source plane collapses that copy's throughput.** When
`H*W*sizeof(dtype)` is not a multiple of 32, the transposing read falls off its
fast path: measured about 40 GB/s versus roughly 1.7 TB/s on an aligned plane,
which turns a MAC-bound conv into an MTE2-bound one (`aic_mte2_ratio` 0.978).
`W = 127` fp16 and `W = 63` fp32 both hit this. Reach for a separate NCHW to
NC1HWC0 transdata pass on that branch only; the aligned branch is faster with
the single fused read.

Read the pipe split from the profiled `op_summary_*.csv` that
`OpExec(profile=True)` copies into `<out_dir>/../csv/` before tuning any of
this - `aic_mac_ratio` versus `aic_mte2_ratio` decides which of the two limits
you are actually against.

## 14. Do not branch inside a `@vf`

`If` / `Elif` / `Else` are accepted inside a micro body, but the vector unit has
no branch: an `if` there lowers to predicated execution, the way a divergent
branch does on a SIMT architecture. Both arms issue, every lane pays for both,
and the loop around them pays for the mask bookkeeping. A `@vf` that branches per
iteration is far slower than one that does not.

Write the alternatives out of the vector function instead:

- **Choose the route in the `@func` body.** Kernel-level `If` is a real branch on
  the scalar unit and is fine. Better still, select by *emptying a loop*: give
  the route that does not apply an empty item range
  (`end = begin + (end - begin) * on`, `on` in `{0, 1}`), so both bodies stay
  straight-line and neither needs a condition.
- **A zero-or-one-iteration loop replaces an `if`.** `for _ in range(Min(n, 1))`
  runs the body only when `n > 0`, costs one loop set-up, and does not
  predicate the lanes.
- **A clamp replaces a conditional value.** The micro pipe has `Min`/`Max`, so
  `Max(0, Min(1, x))` is a branchless 0/1 select, and a masked `mul` by a
  0/1 register zeroes a contribution that should not count.
- **A `select` replaces a conditional store.** `compare` into a `MaskReg` then
  `select` is a data-path operation, not a branch, and mask registers measured
  free (see `agent/references/optimization/levers.md`, L13b).
