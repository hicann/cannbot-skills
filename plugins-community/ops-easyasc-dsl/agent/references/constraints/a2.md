# a2 Device Constraints

Read this file when writing any kernel targeting a2 (`easyasc.a2`, device `b3`).
Covers the a2 device boundary: feature surface, cube↔vec GM bridges, mutex
signatures, sub-block layout, pure-vec entry structure, and a2-specific UB layout
gotchas.

Boundary: vec op semantics live in `constraints/vec.md`; tail-safe local shapes
live in `constraints/tail.md`; online-softmax mask timing lives in
`patterns/online-softmax-tail.md`. Use this file only for the a2 device surface
and the places where that surface constrains buffer layout or cross-side data
movement.

For exact per-device buffer capacities see `agent/references/facts-device-runtime.md`.
For a5 differences see `agent/references/constraints/a5.md`.
For mixed pipeline step-by-step see `agent/references/patterns/a2-mixed-pipeline.md`.

---

## 1. Feature surface

Key `easyasc/a2.py` exports include: `matmul`, `gm_to_l1_nd2nz`, `gm_to_l1`,
`l1_to_l0`, `l1_to_bt`, `mmad`, `l0c_to_gm_nz2nd`, `l0c_to_l1`,
`gm_to_ub_pad`, `ub_to_gm_pad`, `ub_to_ub`, `cast`, `cmax`/`cadd`/`brcb`,
`sort32`/`mergesort4`/`mergesort_2seq`, `CvMutex`/`VcMutex`, `GetSubBlockIdx`,
and the standard vec ops.
It also exposes host-side signed int4/int32 carrier helpers from
`easyasc/dtypehelper/int4_int32.py`, because `DT.int4` is an a2 cube format.

**Not exported on a2** (absent or a5-only):

| Missing | Why it matters |
|---------|---------------|
| `@vf` / `Reg` / `RegList` / `MaskReg` | No register-file abstraction; use UB tensors directly |
| `l0c_to_ub` | Cannot shortcut L0C → UB; must go via GM workspace |
| `ub_to_l1` / `ub_to_l1_nd2nz` / `ub_to_l1_nz` | Cannot publish UB → L1 directly; must go via GM workspace |
| `micro` | Not available |
| `l0c_to_l1(..., dst=float)` | Float destination is blocked on all `b*` devices (`easyasc/stub_functions/cube.py:1297`) |

Tile-size consequence: a5 L0C at 256 KB overflows on a2 (128 KB). Verify
`TILE_M * TILE_N * 4 * 2 ≤ 128 KB` for float L0C double-buffer.

## 2. Data-path bridges

### 2.1 Cube → vec (L0C → GM → UB)

`l0c_to_ub` is absent; `l0c_to_l1(..., dst=float)` is blocked. Mandatory path:

```
Cube  (FIX)   : l0c_to_gm_nz2nd  → GM workspace slot
Vec   (MTE2)  : gm_to_ub_pad     ← GM workspace slot
```

Verified in `agent/example/kernels/a2/attention/flash_attn_score_pv.py:72,76` and `flash_attn_full.py:88,92`.

GM workspace design:
```python
score_ws = split_workspace(DT.float, [GetCubeNum(), 2, TILE_M, TILE_N], name="score_ws")
# cube writes full TILE_M rows into score_ws[cube_idx, slot, 0:TILE_M, :]
# each vec sub-block reads HALF_M rows: score_ws[cube_idx, slot, sb_row:sb_row+HALF_M, :]
```

### 2.2 Vec → cube (UB → GM → L1)

`ub_to_l1`, `ub_to_l1_nd2nz`, and `ub_to_l1_nz` are a5-only. Mandatory path for delayed vec→cube reuse:

```
Vec   (MTE3)  : ub_to_gm_pad     → GM workspace slot
Cube  (MTE2)  : gm_to_l1_nd2nz  ← GM workspace slot → L1 → L0 → mmad
```

Verified in `agent/example/kernels/a2/attention/flash_attn_score_pv.py:91` (vec writes p_ws) and `flash_attn_full.py:116,132`.

### 2.3 Cube-only dependency (L0C → L1 direct)

If an intermediate result only feeds a later cube matmul (no vec stage needed), keep it
on the cube path: `l0c_to_l1` into a supported destination dtype (not float on `b*`
devices), then
`l1_to_l0 → mmad`. Do not route a pure cube dependency through UB.

## 3. Cross-side handoff consequences

Use `agent/references/facts-device-runtime.md` for exact mutex signatures.
This section records why a2 uses different endpoints from a5.

For cube -> vec release, the vec side's first consumer is `gm_to_ub_pad` on
MTE2, not a V-pipe op, because the handoff goes through GM workspace. This
differs from a5, where `l0c_to_ub` makes the tile directly visible to vec-side
compute.

For vec -> cube release, vec ends on `ub_to_gm_pad` through MTE3. The cube side
usually releases conservatively after the full delayed cube stage (MTE2 reload
-> L1 -> L0 -> MMAD -> FIX), which prevents premature workspace reuse.

Multi-stage kernels add a second cube -> vec handoff for the PV stage. Use
`agent/references/patterns/a2-mixed-pipeline.md` for the concrete 2-stage,
3-stage, and 4-stage patterns.

## 4. Sub-block and UB layout

Each cube core has **2 vec sub-blocks** with **independent 192 KB UB** each
(`ub_cap = 192` at `easyasc/globvars.py:23`). Vec instructions in the kernel body execute on both
sub-blocks simultaneously.

Use `GetSubBlockIdx()` to split work between sub-blocks:
```python
sb = GetSubBlockIdx()          # 0 or 1
sb_row = Var(sb * HALF_M)
ub_data <<= workspace[cube_idx, slot, sb_row:sb_row + HALF_M, 0:TILE_N]
# ... vec processing ...
out_row = Var(q_row + sb_row)
output[out_row:out_row + HALF_M, 0:TILE_N] <<= ub_out
```
Verified in `agent/example/kernels/a2/attention/flash_attn_score_pv.py:42-43` and `flash_attn_full.py:54-55`.

Cube-side `wait_vec()` succeeds only after **both** sub-blocks have produced their
tokens, making full-tile cube reload safe after two half-row vec writes.

## 5. a2 vec entry and escalation

### 5.1 Pure vec kernel skeleton

Stable structure for `GM → UB vec ops → GM` kernels with no cube stage:
```python
@kernel()
def vec_kernel(x: GMTensor, y: GMTensor, total: Var):
    data = Tensor(DT.float, [1, TILE], Position.UB)
    work = Tensor(DT.float, [1, TILE], Position.UB)
    flag = Tensor(DT.uint8, [1, TILE], Position.UB)

    n_tiles = CeilDiv(total, TILE)
    tile_per_core = CeilDiv(n_tiles, GetVecNum())
    tile_start = Var(tile_per_core * GetVecIdx())
    tile_end = Min(tile_start + tile_per_core, n_tiles)

    dup(...)   # initialize constants once before the loop

    with auto_sync():
        for t in range(tile_start, tile_end):
            n1 = Var(t * TILE)
            n_valid = Min(total - n1, TILE)
            data <<= x[n1:n1 + n_valid]
            # vec compute on UB
            y[n1:n1 + n_valid] <<= work
```

Reference: `agent/example/kernels/a2/vec_only/to_hif8_torch.py` (TILE=512, DBuff for input/output).

### 5.2 UB initialization and tile defaults

UB contents are undefined at kernel entry. `muls(ub, ub, 0.0)` is unreliable on
uninitialized buffers (`0.0 × NaN = NaN`). Use `dup(tensor, scalar)` for explicit fill.

For score-domain invalidation and running-max identity, use a sufficiently large finite
negative sentinel such as `NEG_LARGE = -1.0e30`. Do not use `float("-inf")`; it is
simulator-convenient but hardware-fragile.

`dup` inside an outer loop but before an inner loop is safe — the extra V→MTE3 autosync
event pair is harmless (dup completes before the inner loop's first MTE3 op).

See `constraints/sync.md` for the full autosync model.

For float vec-only kernels, `TILE = 512` is a good default starting point:
- simple to reason about
- comfortably small for a2 UB (192 KB per sub-block)
- large enough to amortize fixed per-tile work

Tail handling:
- `n_valid = Min(total - n1, TILE)`
- load/store through GM slices using that tail width
- avoid adding a separate tail kernel unless the contract truly needs one

Do not optimize tile size first. Get the contract right with one simple tile,
revisit only if UB pressure or runtime suggests it.

### 5.3 When a pure vec kernel stops being "simple"

Escalate out of section 5 to the focused constraint/pattern files when you hit:
- wide `[M, 128]` interacting with narrow `[M, 8]` → `constraints/vec.md`
- row max / row sum / row-stat broadcast → `constraints/vec.md`
- temporary partial masks or masked writeback → `constraints/vec.md`
- `compare_scalar` / `select` flag flow or `reinterpret` views → `constraints/vec.md`
- exact hif8 rounding or cast placement → `constraints/precision.md`
- generic tile tails → `constraints/tail.md`
- online-softmax mask/update timing → `patterns/online-softmax-tail.md`
- cross-stage workspace reuse or delayed consumer → section 2 above, plus
  `patterns/a2-mixed-pipeline.md`

### 5.4 Split-reduction merge ownership

When multiple A2 cores produce partials for one logical reduction, freeze the
merge owner and kernel mode before coding the split:

- A simulator pass does not compile the device C++ or prove that an atomic
  operation, dtype, or store pipe is legal. Accept an atomic merge only after a
  real hardware compile and run.
- A disjoint GM workspace plus one merge owner is the standard alternative when
  atomic merge is unavailable or fails. Each producer owns its partial region;
  only the merge owner writes the final output.
- If producing and merging cross cube/vec ownership, the launch must include the
  required side. A failure under `@kernel(mode="vec")` does not reject the
  workspace design globally; re-check ownership and use `mode="mix"` when both
  sides are required.
- Make workspace visibility and synchronization explicit. For cube↔vec GM
  bridges, follow `patterns/a2-mixed-pipeline.md` rather than inferring the
  handoff from simulator behavior.

Record the split axis, partial layout, merge owner/mechanism, kernel mode,
visibility/sync edge, precision order, and a hardware stress case. If the same
hardware boundary fails after two focused fixes, switch merge mechanism instead
of accumulating variants around it.

## 6. a2 row-scalar and UB layout gotchas

### 6.1 UB second dimension must be 32-byte aligned

For new UB buffers, keep `shape[1] * dtype.size` 32-byte aligned. For fp32 row
scalars this means `[1, M]`, not `[M, 1]`.

`cmax` / `cadd` row-stat outputs should land in aligned dense scalar buffers such
as `[1, HALF_M]`, then `brcb(..., repeat=local_rows//8, dst_blk_stride=1,
dst_rep_stride=8)` broadcasts them into `[local_rows, 8]` for row-wise `sub` /
`div`. In the active A2 attention kernels, `local_rows` is `HALF_M`.
Primitive reduction and broadcast semantics live in `constraints/vec.md`.
The complete full-row composition lives in
`patterns/vec-row-reduce-broadcast.md`.

Keep the physical scalar width aligned and use a separate valid-row count at GM
boundaries; do not shrink the second dimension to `1` for tail rows.
Do not reintroduce the old `[HALF_M, 1]` scalar-buffer layout when editing
existing kernels; the active A2 attention references use `[1, HALF_M]`.

### 6.2 `ub_to_ub` unsafe for row-scalar state

`ub_to_ub` works in C0-sized blocks and is the wrong primitive for row-scalar
state. Keep the scalar buffer second dimension aligned and copy with an
arithmetic op.

Workaround — use an explicit zero buffer:
```python
ub_zero_s = Tensor(DT.float, [1, HALF_M], Position.UB)
dup(ub_zero_s, 0.0)
add(tmp_scalar, ub_rmax_s, ub_zero_s)   # copies row scalars safely
```

### 6.3 Narrow broadcast views follow vec auto-infer rules

The default stride behavior for narrow broadcast views such as float `[M, 8]`
and half `[M, 16]` is documented in `constraints/vec.md` §1.1 and §2. Keep
row-scalar state in `[1, M]`, and use `brcb(...)` to materialize `[M, 8]` /
`[M, 16]` only when a downstream vec op actually needs the broadcast view.

### 6.4 `dup` + `ub_to_gm_pad` ordering

A `dup` placed inside the outer loop but before the inner loop generates an extra V→MTE3
autosync event because auto_sync sees the V-pipe `dup` and the inner loop's MTE3
`ub_to_gm_pad` as a producer-consumer pair. This event is satisfied immediately (dup
completes before the inner loop starts) and is harmless. No special handling needed.

### 6.5 Integer scalar shifts

A2 exports `shiftls` and `shiftrs` for matching UB tensors with dtype
`int16`, `uint16`, `int32`, or `uint32`. Static shift counts are checked against
the element width (`0..16` or `0..32`); a runtime count must be an integer
`Var`. Both repeat mode and `count` / `count_per_rep` mode are supported.

`shiftrs` is arithmetic for signed tensors and logical for unsigned tensors.
`round_en=True` affects signed right shift only. Board validation showed that
left shift moves the complete fixed-width bit pattern (for example,
`uint16(0xAAAA) << 1 == 0x5554`); do not implement sign-preserving behavior
from a worked documentation example. Parser/codegen and simulator regressions
live in `agent/example/testcases/parser/vec/test_vec_shift_codegen.py` and
`agent/example/testcases/simulator/vec/test_vec_shift.py`.
