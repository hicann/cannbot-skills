# Task 调用契约

> 各步子 Agent 的调用参数、输入/输出、验收标准。编号与 [SKILL.md 统一流程表](../SKILL.md#统一流程表) 一一对应。
>
> **调用原则**：PM 调度子 Agent 时只定义「输入 / 输出 / 验收标准」，**严禁干涉实现细节**（最小信息、最小权限）。交付件模板引用 `workflow-doc-templates` 逻辑名；领域知识引用 `repo-*` 逻辑名。

## 通用约定

- **报告格式**：各步交付的报告/文档统一从 `workflow-doc-templates` 取对应模板作为格式基准。
- **中间产物**：子 Agent 将交付件直接写入下发时约定的 `.cannbot` 路径，并回传结构化摘要（状态 / 交付件路径 / 遗留问题）。`.cannbot` 所有角色均可写。
- **写权限**：各角色写权限由 hook 按角色限定；执行角色遵守「修改不越权」——发现上游设计问题回退给上游，不自行改设计决策。
- **CP 验收**：各 CP 点由 QA 加载对应 `workflow-cp*` Skill 完成验收（验收标准可被子仓 override）；不通过返回结构化修改意见，按流程表「备注」列回退。需用户确认的 CP，QA 生成问卷 json 交 PM 发送给用户。

## 任务恢复映射

中断时按 `.cannbot/state.json` 的 `current_stage` 恢复到对应子 Agent（详见 [state-schema.md](state-schema.md)）。恢复时读取已产出交付件继续，不重跑已通过阶段。

| 中断阶段 | 恢复角色 | 恢复说明 |
|----------|----------|----------|
| 0 / CP0 | developer / PM | 读环境信息文档继续 |
| 1.1 / 1.2 | PM / architect | 读需求文档 / Spec 继续 |
| 2.1 / 2.2 | architect | 读方案文档继续 |
| 3.1 / 3.2 / 3.3 | developer-code / developer-test | 读代码与测试继续 |
| CP3 / CP4 / CP5 | QA | 读对应报告继续；回退则从 3.1 重走 |
| 6.x | developer-doc / developer | 读 PR 状态继续 |
| 7.x | developer-doc | 读交付物继续 |

# 阶段 0：开发准备

## 0 开发准备
- **角色**：developer
- **输入**：无（可复用已有环境信息文档）
- **输出**：环境信息文档（模板 `workflow-doc-templates` 的 `0-环境信息`）
- **动作**：检查 NPU 设备、CANN 环境、编译环境；将环境信息文档写入下发时约定的 `.cannbot` 路径
- **验收标准**：环境信息文档完整，各检查项有明确结论
- **备注**：支持独立触发；交付件可复用

## CP0 环境确认
- **角色**：QA（加载 `workflow-cp0`）
- **输入**：环境信息文档
- **输出**：用户确认问卷 json
- **通过指标**：用户确认环境校验结果满足开发要求
- **动作**：QA 加载 `workflow-cp0` 生成环境确认问卷 json，PM 发送给用户
- **不通过**：由用户决定修复环境或停止开发

# 阶段 1：需求分析

## 1.1 需求分析
- **角色**：PM
- **输入**：对话上下文、仓库设计约束
- **输出**：需求文档（模板 `1.1-需求分析`）
- **动作**：整理数学定义、算子原型、目标芯片、精度/性能要求、其他要求；核对模板确认项，用户未提及的通过问卷补齐
- **验收标准**：确认项无遗漏，用户原始需求逐条记录

## CP1 需求确认
- **角色**：QA（加载 `workflow-cp1`）
- **输入**：需求文档
- **通过指标**：需求完整、明确、可执行，模板确认项齐全且用户原始需求逐条可追溯；硬伤判不通过，开放取舍经用户拍板补齐
- **动作**：QA 加载 `workflow-cp1` 核对需求文档；需用户确认时生成问卷 json 交 PM 发送
- **不通过**：返回结构化修改意见，回退 1.1

## 1.2 Spec 生成
- **角色**：architect
- **输入**：需求文档
- **输出**：`spec.yaml`（**机器可校验 Spec**，规范由共享 skill `ops-spec-gen` 定义，见 `workflow-doc-templates` 的 `1.2-Spec` 指引）
- **动作**：将需求形式化为 L0 数学契约，作为方案设计与测试设计的共同真值源
- **验收标准**：`validate_spec.py` 9-stage 全 PASS；字段与需求文档一致可追溯

## CP1' Spec 确认
- **角色**：QA（加载 `workflow-cp1-prime`）
- **输入**：`spec.yaml`
- **通过指标**：9-stage 校验通过，Spec 准确完整地形式化了需求
- **动作**：QA 加载 `workflow-cp1-prime` 核对 Spec；需用户确认时生成问卷 json 交 PM 发送
- **不通过**：返回结构化修改意见，回退 1.2

# 阶段 2：方案设计（方案线 / 测试线并行）

## 2.1 黑盒测试设计
- **角色**：architect
- **输入**：`spec.yaml`
- **输出**：测试方案文档（模板 `2.1-测试方案设计`）
- **动作**：设计 golden 实现方案、L0/L1/L2 分级用例；测试配置以 spec 为真值源
- **验收标准**：golden 方案可行，分级用例覆盖充分（正常/边界/异常/特殊值）

## CP2.1 测试检查
- **角色**：QA（加载 `workflow-cp2-1`）
- **输入**：测试方案文档
- **通过指标**：golden 方案合理可信、L0/L1/L2 分级与场景覆盖完整、覆盖矩阵对照 spec 全命中、容差依据明确
- **动作**：QA 加载 `workflow-cp2-1` 完成黑盒测试评审
- **不通过**：返回结构化修改意见，回退 2.1

## 2.2 开发方案设计
- **角色**：architect
- **输入**：`spec.yaml`
- **输出**：开发方案文档（模板 `2.2-开发方案设计`）
- **动作**：设计代码架构（MemBase/RegBase/SIMT）、Buffer 规划、Tiling、多核切分、Ascend C 接口验证
- **验收标准**：架构选型合理、Tiling/切分策略可行、关键 API 已验证

## CP2.2 方案检查
- **角色**：QA（加载 `workflow-cp2-2`）
- **输入**：开发方案文档
- **通过指标**：设计可行、与 spec 一致、无明显性能/正确性隐患
- **动作**：QA 加载 `workflow-cp2-2` 完成开发方案评审
- **不通过**：返回结构化修改意见，回退 2.2

## CP2' 方案确认
- **角色**：QA（加载 `workflow-cp2-prime`）
- **输入**：开发方案 + 测试方案
- **通过指标**：CP2.1、CP2.2 均通过，两方案相互吻合无冲突
- **动作**：QA 加载 `workflow-cp2-prime` 做两方案一致性合并确认
- **不通过**：返回结构化修改意见，回退对应步骤

# 阶段 3：代码开发（开发线 / 测试线并行）

## 3.1 算子开发
- **角色**：developer-code
- **输入**：开发方案文档、修改要求（被打回时）
- **输出**：算子代码
- **动作**：按开发方案实现算子代码，编译验证通过；引用 `repo-op-templates`（模板起点）、`repo-coding-rules`（编码规范）、`repo-build-guide`（编译验证）
- **验收标准**：编译通过；按方案实现；被打回时按修改要求调整
- **越权约束**：性能/正确性瓶颈定位后回退给设计角色，不自行改 Tiling/切分/接口

## 3.2 测试工程开发
- **角色**：developer-test
- **输入**：测试方案文档
- **输出**：golden 代码 + 用例表 + 性能采集框架
- **动作**：实现 golden、功能用例表、搭建性能采集框架；引用 `repo-test-develop`（测试框架用法）
- **验收标准**：golden 可产出期望输出，用例表按分级覆盖，性能采集框架可用

## 3.3 白盒测试补全
- **角色**：developer-test
- **输入**：算子代码、测试代码
- **输出**：白盒测试用例
- **动作**：基于算子代码补充白盒用例，覆盖黑盒未涉及的分支
- **验收标准**：分支覆盖达标（具体阈值见配置）

## CP3 功能验收
- **角色**：QA（加载 `workflow-cp3`）
- **输入**：算子代码 + 测试代码
- **输出**：功能验收报告（模板 `CP3-功能验收报告`）
- **通过指标**：全量功能测试通过率 100%，精度比对在容差内（引用 `ops-precision-standard`）
- **动作**：QA 加载 `workflow-cp3` 执行全量功能测试与精度比对，产出报告
- **不通过**：返回结构化修改意见，回退 3.1

# 阶段 4：性能验收

## 4.1 性能采集执行
- **角色**：developer-test
- **输入**：算子代码（CP3 通过后的最终代码）
- **输出**：性能数据
- **动作**：用 3.2 搭建的性能采集框架跑出性能数据（各 shape/dtype 的耗时、带宽、利用率）
- **验收标准**：性能数据完整覆盖需求关注的 shape/dtype

## CP4 性能验收
- **角色**：QA（加载 `workflow-cp4`）
- **输入**：算子代码 + 性能数据（4.1 产出）
- **输出**：性能验收报告（模板 `CP4-性能验收报告`）
- **通过指标**：性能达到目标值（需求文档给定；无明确目标时以瓶颈分析结论判定）
- **动作**：QA 加载 `workflow-cp4` 评估性能是否达标，产出报告
- **不通过**：返回结构化修改意见，回退 3.1（重走 3.3 → CP3 → 4.1 → CP4）

# 阶段 5：代码检视

## CP5 代码检视
- **角色**：QA（加载 `workflow-cp5`）
- **输入**：全部变更文件
- **输出**：检视结论（模板 `CP5-代码检视报告`）
- **通过指标**：多维度检视全过——代码规范（引用 `repo-coding-rules`）、设计一致性、潜在风险、冗余清理
- **动作**：QA 加载 `workflow-cp5` 完成多维度代码检视，产出检视结论
- **不通过**：返回结构化修改意见，回退 3.1（重走至 CP5）

# 阶段 6：上库准备

## 6.1 文档补全
- **角色**：developer-doc
- **输入**：算子代码 + 设计文档
- **输出**：算子文档（模板 `6.1-算子文档`）
- **验收标准**：接口、参数、约束、示例齐全

## 6.2 提交 PR
- **角色**：developer-doc
- **输入**：全部代码 + 文档
- **输出**：PR
- **验收标准**：PR 描述完整，变更范围清晰

## 6.3 CI 流水线
- **角色**：CI（外部流水线，非调度子 Agent）
- **输入**：PR
- **输出**：CI 报告（编译 + UT + ST）

## 6.4 codecheck 修复
- **角色**：developer
- **输入**：CI 报告
- **输出**：修复后代码
- **验收标准**：codecheck 问题清零

## 6.5 检视意见修复
- **角色**：developer
- **输入**：PR 检视意见
- **输出**：修复后代码
- **验收标准**：检视意见逐条闭环

## CP6 CI 通过确认
- **角色**：QA（加载 `workflow-cp6`）
- **输入**：CI 报告 + PR 状态
- **通过指标**：CI（编译 + UT + ST）最终通过、检视意见已闭环
- **动作**：QA 加载 `workflow-cp6` 确认 CI 通过与检视意见闭环
- **不通过**：回退 6.4 / 6.5 修复后重触发 CI（受过程有界约束）
