# 错误处理与回退

> 各 CP 不通过时的回退策略、循环最大轮次、恢复规则。对应设计约束「过程有界」「可恢复性」。
>
> **骨架状态**：结构就位，具体阈值待填充。

## 回退关系（来自流程表）

| 不通过的 CP | 回退目标 | 重走路径 |
|-------------|---------|---------|
| CP1 | 1.1 需求分析 | — |
| CP2.1 | 2.1 黑盒测试设计 | — |
| CP2.2 | 按语义归属：开发方案 → 2.2 / 需求 → 1.1 | 归属需求时重走 1.1 → CP1 → 2.2 → CP2.2 |
| CP3 | 3.1 算子开发 | 3.3 → CP3 |
| CP4 | 3.1 算子开发 | 3.3 → CP3 → 4.1 → CP4 |
| CP5 | 3.1 算子开发 | 3.3 → CP3 → 4.1 → CP4 → CP5 |
| CP6 | 6.4 / 6.5 修复 | 重触发 CI → CP6 |

> CP2.2 的归属分流：无论是 QA 认定问题根因在需求（如需求文档中已由用户拍板的代码架构在目标芯片上不可行），还是用户在确认问卷中对架构选型 / dtype / shape 范围 / 容差 / 性能目标提出异议，均按语义归属回退 1.1 由用户重新拍板，而非回退 2.2。
>
> 开发方案一经用户确认即锁定：**任何后续回退只要改动了开发方案（如 CP4 定位到 Tiling / 切分需调整而回退 2.2），改后的方案必须重走 CP2.2 的用户确认段**，不得跳过。仅回退 3.1 的实现级修改不触发复确认。

## 过程有界（最大轮次，默认值）

所有可循环环节声明最大轮次；达上限即暂停，禁止无限自动重试。默认值如下，子仓可配置覆盖：

| 循环 | 涉及 CP | 默认最大轮次 | 计数对象 |
|------|---------|--------------|----------|
| 设计评审循环 | CP1 / CP2.1 / CP2.2 | 3 | 单个 CP 的打回-重做；CP2.2 的用户异议返工与 QA 打回共用同一计数 |
| 验收状态机 | CP3 / CP4 / CP5 → 3.1 | 3 | 回退到 3.1 的整轮重走 |
| 上库 CI 循环 | CP6 | 3 | CI 触发-修复的往返 |

- 轮次计数按 CP 分槽写入 `state.json` 的 `rounds`（见 [state-schema.md](state-schema.md)）；跨 CP 回退（如 CP2.2 因归属需求回退 1.1）**不清零发起方槽位**，否则往返途中计数被重置，循环将失去边界。
- **超上限处理**：暂停 → 落盘可恢复状态点 → 输出结构化问题清单 → 请求用户决策（继续放宽轮次 / 调整设计 / 停止）。

## 错误类型与判定

| 类型 | 典型场景 | 处理 |
|------|----------|------|
| 交付件不合规 | 文档缺项 | 返回对应生成步骤修复，计入设计评审循环 |
| 方案未获用户认可 | CP2.2 用户在确认问卷中提出异议 | 按条目语义归属回退 2.2 或 1.1，计入设计评审循环 |
| 功能不达标 | CP3 精度/用例不过 | 回退 3.1，计入验收状态机 |
| 性能不达标 | CP4 未达目标 | 定位瓶颈；若涉及设计（Tiling/切分）回退设计角色（2.2）并重走 CP2.2，否则回退 3.1 |
| 检视不通过 | CP5 规范/一致性/风险问题 | 回退 3.1 按检视意见修复 |
| CI 失败 | 编译/UT/ST/codecheck 失败 | 回退 6.4/6.5，计入 CI 循环 |
| 环境阻塞 | CP0 环境不满足 | 交用户决定修复或停止 |

## 修改不越权

执行角色发现问题时：允许定位（复现、缩小范围、给根因证据），但**不得自行变更上游设计决策**（架构/Tiling/切分/接口）。定位结论回退给对应上游角色（architect），由其决定是否调整设计。

代码架构是用户在 CP1 拍板的决策，位于 architect 之上：architect 在开发方案中发现该架构不可行时，同样不自行改选，而是把论据回退到需求（1.1），由用户重新拍板。

## 恢复规则

- 暂停/失败落盘到 `.cannbot/<算子名>/state.json`（见 [state-schema.md](state-schema.md)）的可恢复状态点：已完成阶段、当前阻塞点、已产出交付件、当前轮次。
- 恢复时从状态点续跑，不重跑已通过阶段。
