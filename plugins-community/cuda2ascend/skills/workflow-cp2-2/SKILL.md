# CP2.2 方案检查验收标准

本验收点判定**开发方案是否合理、可行**，即其架构与各项设计决策是否足以指导 direct launch 算子编码落地。本验收点为 **QA 评审 + 用户确认** 两段式——先由 QA 按检查项客观裁定，通过后再将关键决策点交用户逐项确认。

## 验收对象

开发方案文档，应覆盖代码架构（承接需求文档已由用户拍板的选型结果）、direct launch 工程结构（对照 `repo-op-templates` / `repo-build-guide`）、Buffer 规划、Tiling 策略、多核切分策略、Ascend C 接口验证与硬件/编译器能力边界、schema 对齐方案（与评测集 proto.yaml 一致）、瓶颈维度预判与性能优化项等。

## 通过指标

以**检查项清单逐项判定 + 用户逐项确认**，不凭主观印象：

- **架构承接一致**：开发方案的代码架构与需求文档中用户已拍板的选型结果完全一致，未擅自改选；方案只做该架构下的落地细化，且所选模板与该架构匹配（对照 `repo-op-templates` 的模板选择规则）。
- **schema 对齐**：plugin 层 `m.def(...)` 注册的 schema 与评测集算子原型定义（如 cann-bench `tasks/levelN/<op>/proto.yaml`）的 `schema:` 字段逐字一致（参数名、类型、默认值、返回值）。
- **关键设计齐备**：Buffer 规划、Tiling 策略、多核切分策略均有明确设计，无悬空项。
- **接口可行**：所用 Ascend C 接口经过验证、在目标架构上可用（对照 `repo-build-guide`、`repo-knowledge`）。**按实现路径核对验证源**：代码实现涉及 Cube（Blaze/tensor_api 路线）时，接口验证须以 `ascendc-blaze-best-practice` 为权威源（在 skill 文档与 assets/ 中核对参数签名、类型约束与模板参数）；RegBase / MemBase / SIMT 路线须给出 `ascendc-docs-search` 的官方文档验证结果并覆盖同一 API 的所有变体。Blaze 路线下出现未经 `ascendc-blaze-best-practice` 确认的 API，判不通过。
- **承接需求无冲突**：方案中的 dtype/shape/容差等承接自需求文档（= proto.yaml），未另立真值、无相互矛盾。
- **资源约束自洽**：Buffer/Tiling 设计在目标芯片的 UB 大小、AI Core 数等资源约束内自洽。
- **能力边界已核对**：方案依赖的硬件与编译器能力项逐条给出「支持 / 不支持 / 需绕行」结论与核对方式，不支持项已给绕行方案；留「应该可以 / 待定」式空结论者判不通过。
- **瓶颈预判有推导、可证伪**：瓶颈维度预判给出可核对的量化估算依据与证伪条件，并声明校准状态；只写定性断言（如「计算密集度低」）而无推导者判不通过。
- **优化项可核对**：性能优化项逐条标注落地要求（必落地 / 可选）与是否改变数值计算路径，且「必落地」项面向的是预判瓶颈维度。
- **用户确认**：上述检查项全过后，将开发方案的关键决策点整理为问卷直接发送用户逐项确认；全部条目确认无异议方为通过。
- **通过条件**：全部检查项通过，且用户确认无异议。判定形式为"逐项对照检查项清单 + 用户逐项勾选确认"。

## 关键决策点抽取清单

用户确认段的问卷条目从开发方案中抽取。抽取项**锚定 `workflow-doc-templates` 的 `2.2-开发方案设计` 模板章节**（不另立字段，随模板演进自动对齐），默认基线如下：

| 抽取项 | 取自模板章节 |
|--------|-------------|
| 代码架构落地形态 | 「代码架构」节 |
| schema 对齐方案 | 「schema 对齐」节（与 proto.yaml 一致性） |
| Buffer 规划 | 「数据流与 Buffer 规划」节的 Buffer 表 |
| Tiling 策略 | 「Tiling 策略」节 |
| 多核切分策略 | 「多核切分策略」节 |
| 关键 Ascend C 接口选型 | 「Ascend C 接口验证」节的关键 API 表 |
| 硬件与编译器能力边界结论 | 「硬件与编译器能力边界」节（不支持项与绕行方案） |
| 瓶颈维度预判 | 「瓶颈维度预判与校准」节（预判维度 + 估算依据 + 证伪条件） |
| 必落地的性能优化项 | 「性能优化项」节中落地要求为「必落地」的条目 |
| 已识别风险与对策 | 「风险与对策」节 |

抽取项**只取模板已要求 architect 产出的内容**，不得向用户索要模板未定义的字段——否则方案照模板写却过不了确认，会产生无谓返工。

每条问卷条目须带四要素，缺一不可：

1. **决策内容**：可判定取值；凡「适中 / 合理 / 视情况」等定性词均不得作为条目内容。
2. **依据来源**：该决策出自方案文档的哪一节、依据什么约束得出。
3. **语义归属标签**：按下方归属规则标注，决定用户异议时的回退目标。
4. **确认 / 异议** 选项。

问卷附开发方案文档的完整路径，供用户下钻查阅全文。

## 语义归属规则

问题——无论是 QA 判定的缺陷，还是用户提出的异议——其归属为**该决策的真值源所在文档**：

| 决策的真值源 | 归属 |
|--------------|------|
| 开发方案（Buffer 规划 / Tiling / 多核切分 / 接口选型） | 开发方案设计 |
| 需求文档 / 评测集 proto.yaml（代码架构选型 / schema / dtype / shape 范围 / 容差 / 性能目标） | 需求 |

**用户已拍板的代码架构本身在目标芯片上不可行**，以及**用户在确认问卷中对该架构提出异议**，均属后者：须标注归属需求并附论据，由上游回退需求重新拍板，而非在方案侧改选。

## 验收步骤

加载本 skill 时执行：

1. 读取开发方案文档，逐项核对架构承接、schema 对齐、关键设计、接口、承接需求、资源约束、能力边界、瓶颈预判、优化项全部检查项。
2. 对照需求文档（= proto.yaml）核实代码架构与拍板结果一致、schema 逐字对齐；对照 `repo-op-templates`、`repo-build-guide` 核实模板与架构匹配、接口可用性、真值一致性。
3. 检查项存在不通过项时，直接返回结构化修改意见，**不进入用户确认段**。
4. 检查项全过后，按抽取清单生成结构化问卷 json，每条带上述四要素；用会话问卷工具（opencode `question` / claude `AskUserQuestion` / dsh `ask_user_question`）直接发送用户；问卷与回复成对落盘 `.cannbot/<算子名>/questionnaires/`（回复记为问卷同名 `.reply.json`）。
5. 收集用户结论后汇总判定：全部条目确认无异议即通过；存在异议则按条目的语义归属标签返回修改意见。

## 输出

- **通过**：明确结论"开发方案检查通过"，附用户确认记录。
- **不通过**：返回**结构化修改意见**——
  - 问题定位：逐条列出架构承接偏差 / schema 不对齐 / Buffer / Tiling / 切分 / 接口中的缺陷或不可行处，以及能力边界空结论、瓶颈预判无推导、优化项缺落地要求等问题；用户异议则列出异议条目及其异议内容。
  - 问题语义归属：按上方**语义归属规则**标注「开发方案设计」或「需求」，归属需求者附论据，由上游按归属回退。

只判定与给意见，不自行修改开发方案，不编写算子代码，不替上游决定架构 / 切分策略，不代替用户确认。
