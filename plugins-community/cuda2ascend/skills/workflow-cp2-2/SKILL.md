# CP2.2 方案检查验收标准

本验收点判定**开发方案是否合理、可行**，即其架构与各项设计决策是否足以指导算子编码落地。

## 验收对象

开发方案文档，应覆盖代码架构（承接需求文档已由用户拍板的选型结果）、Buffer 规划、Tiling 策略、多核切分策略、Ascend C 接口验证等。

## 通过指标

以**检查项清单逐项判定**，不凭主观印象：

- **架构承接一致**：开发方案的代码架构与需求文档中用户已拍板的选型结果完全一致，未擅自改选；方案只做该架构下的落地细化，且所选模板与该架构匹配（对照 `repo-op-templates` 的模板选择规则）。
- **关键设计齐备**：Buffer 规划、Tiling 策略、多核切分策略均有明确设计，无悬空项。
- **接口可行**：所用 Ascend C 接口经过验证、在目标架构上可用（对照 `repo-build-guide`）。
- **承接需求无冲突**：方案中的 dtype/shape/容差等承接自需求文档，未另立真值、无相互矛盾。
- **资源约束自洽**：Buffer/Tiling 设计在目标芯片的 UB 大小、AI Core 数等资源约束内自洽。
- **通过条件**：全部检查项通过。具体基线（如资源上限）由绑定实现给定，判定形式为"逐项对照检查项清单，全过即通过"。

## 验收步骤

加载本 skill 时执行：

1. 读取开发方案文档，逐项核对架构承接、关键设计、接口、承接需求、资源约束五类检查项。
2. 对照需求文档核实代码架构与拍板结果一致；对照 `repo-op-templates`、`repo-build-guide` 核实模板与架构匹配、接口可用性、真值一致性。
3. 汇总判定，给出通过 / 不通过结论。

## 输出

- **通过**：明确结论"开发方案检查通过"。
- **不通过**：返回**结构化修改意见**——
  - 问题定位：逐条列出架构承接偏差 / Buffer / Tiling / 切分 / 接口中的缺陷或不可行处。
  - 问题语义归属：开发方案设计；若真值冲突根因在需求，标注归属于需求——**用户已拍板的代码架构本身在目标芯片上不可行时属此类**，须标注归属需求并附不可行论据，由上游回退需求重新拍板，而非在方案侧改选。

只判定与给意见，不自行修改开发方案，不编写算子代码，不替上游决定架构 / 切分策略。
