# 设计约束

为保证实现一致性、在方案出现分歧时提供统一指导，约定以下设计约束。

## 1. 结构约束

### 1.1 SOLID 原则

| 条款 | 说明 | 示例 |
|------|------|------|
| **单一职责（S）** | 每个 Skill 只负责一个功能域，只有一种原因引起它需要修改，职责边界清晰 | 例如，`repo-coding-rules` skill 只管理编码规范，不应介绍代码架构的最佳实践 |
| **开闭原则（O）** | 工作流编排对扩展开放，对修改关闭 | 例如，子仓需要扩展特定工作流步骤的约束，应该 override 该步骤用到的 virtual skill，而不是直接改动工作流代码  |
| **里氏替换（L）** | 子仓 override 基类的 virtual 组件后，必须保持相同的输入输出格式，用户和上层工作流不应感知底层实现的替换（基类侧的反向约束见 1.3 基类演进兼容契约） | 例如，子仓用本仓的 `repo-coding-rules` 实现替换了基类的同名默认实现后，工作流仍通过相同的逻辑名、相同的调用方式和参数使用这个 Skill，不会影响工作流的表现 |
| **接口隔离（I）** | 子仓只需 override 自己需要的 virtual Skill，不能要求子仓为了 override 某一个 Skill 而被迫同时实现所有 virtual 组件 | 例如，新仓只想定制编码规范，只需 override coding-rules 一个 Skill，其余组件沿用基类默认实现即可 |
| **依赖倒置（D）** | 上层模块只依赖下层定义的抽象接口，不直接依赖任何具体实现路径 | 例如，工作流只定义 `repo-coding-rules` skill 负责存放编码规范，不要求它分几章，按什么方式编写 |

### 1.2 层级感知原则

层级感知方向：主 Agent -> 工作流 -> 子 Agent -> Skill -> 仓内文档

| 条款 | 说明 | 示例 |
|------|------|------|
| **层级间单向感知** | 下级模块不感知上级模块的存在（不依赖、不引用、不提及） | 例如，子 Agent 不知道自己正在执行工作流的哪一步；Skill 文件不提及自己被哪个 Agent 调用 |
| **层级内黑盒感知** | 同级模块之间互不了解对方的内部逻辑 | 例如，开发角色可以知道测试角色会评测自己的代码，但不了解测试角色的测试流程 |

### 1.3 基类演进兼容契约

里氏替换（L）约束子类 override 时不破坏契约；反过来，基类演进时也不得破坏子仓依赖的契约，否则子仓已有 override 会失效，违背"基类更新后已接入仓无需额外操作"的要求。

| 条款 | 说明 | 示例 |
|------|------|------|
| **契约向后兼容** | 基类 final 编排对外暴露的契约——virtual 组件的逻辑名、各角色的输入输出格式、调用约定——一经发布即视为稳定契约，演进时只能新增、不能破坏性变更；确需破坏性变更时，须提供迁移路径并显式通知已接入仓 | 例如，基类不得随意重命名 `repo-coding-rules` 逻辑名或改变其调用参数，否则各仓针对该逻辑名的 override 会全部失效 |

## 2. 调度约束

| 条款 | 说明 | 示例 |
|------|------|------|
| **职责分离** | 任务的执行方和验收方不能是同一个 Agent 实例（可以是同一类 Agent，但不能是同一个）；当验收方为外部主体（用户、外部 harness agent 等）时，与执行方天然不同，本约束自动满足 | 例如，同一份代码由开发角色实例 A 编写，可以由开发角色实例 B 检视验收；若验收方绑定为用户，则由用户完成验收，同样满足执行方与验收方相互独立 |
| **最小信息** | 调度的每个子 Agent 只获取完成当前任务所需的最小信息集，禁止注入任务无关的全局上下文 | 例如，调度开发角色时只传入当前算子的设计文档，不注入其他算子信息 |
| **最小权限** | 调度的每个子 Agent 只获取完成当前任务所需的最小操作权限，禁止授予超出任务范围的权限 | 例如，调度开发角色时不被授予 test 目录的写权限 |
| **过程有界** | 工作流中所有可能循环或重试的环节必须声明最大执行次数，超过上限后必须暂停并向用户报告问题现状，禁止无限自动重试 | 例如，代码修复-重新检视循环最多 3 轮；3 轮仍未通过则暂停并输出当前问题清单，请求用户决策 |
| **确定性交付** | 调度的每个子环节都有明确的交付件与指标 | 例如，代码检视循环中，建立检视评分机制，当代码检视评分达到阈值后视为循环通过 |
| **状态可观测** | 工作流在每个阶段完成后将状态持久化到外部，不依赖当前会话的上下文记忆 | 例如，每个阶段完成后在 `.cannbot/state.json` 中记录当前阶段和完成时间 |
| **可恢复性** | 任何暂停或失败（含过程有界超限暂停）都必须落盘到一个明确的可恢复状态点，记录已完成阶段、当前阻塞点与已产出交付件；恢复时从该状态点继续，不重跑已通过的阶段 | 例如，代码检视循环超过最大轮次暂停时，将当前阶段、失败原因、问题清单写入 `.cannbot/state.json`；用户决策后，工作流从该状态点续跑，而非从头重来 |
| **修改不越权** | 上游的设计与决策，可能包含本步骤无法考虑到的约束，执行时不质疑、不复核、严格遵循上游设计执行；发现问题时，回退给上游角色修改，禁止自行修正。**定位与修正的边界**：允许在不改变上游设计意图的前提下做问题定位（复现、缩小范围、给出根因与证据），但不得自行变更上游已定的设计决策（如架构、Tiling/切分策略、接口）；定位结论须回退给对应上游角色，由其决定是否调整设计 | 例如，开发角色严格按照设计文档编写代码，出现性能瓶颈时，可定位到是某段循环的切分策略导致，但应把该结论反馈给设计角色，由设计角色决定重构方案，而不是自行改动切分策略 |

## 3. 风格约束

| 条款 | 说明 | 示例 |
|------|------|------|
| **SKILL.md 只做路由** | Skill 入口文件只负责任务意图的识别和路由分发，不包含具体的知识内容或实现逻辑，保持文件轻量 | SKILL.md 中只写"任务匹配到编码规范场景时，加载 references/coding-rules.md"，规范细节放在 references 文件中 |
| **机制优于自然语言** | 能用 hook 拦截、脚本自动执行、agent 权限声明来实现的行为约束，就不要用 prompt 中的自然语言来描述 | "编译前必须检查 API 调用合规性"应实现为 pre-build hook 脚本，而不是在 prompt 中要求 Agent 主动记得去检查 |
| **引用而非硬编码** | Skill 中涉及特定仓库的领域知识时，应通过路径引导 Agent 访问仓库原文获取，而非将知识全文硬编码到 Skill 中 | Skill 引导 Agent 去读取仓库 doc/coding-rules.md 的最新内容，而不是把规范全文复制进 Skill 的 references 目录 |
| **开发者知识外置** | 对开发者同样可见的知识（如测试框架使用方法、编码规范）应该存放在仓库 doc 目录中，保证 Agent 和开发者都能访问，Skill 仅负责引导 Agent 定位到这些文档 | 总结出测试框架的使用方法文档后，优先选择作为仓内文档放在 doc/testing-guide.md 中，而不是放在 skill 的 reference 目录下 |
| **举例不引入外部概念** | 文档与 Skill 中举例时，只使用仓内已有知识或跨领域通用知识，不引入需要额外背景才能理解的外部概念；否则 Agent 为看懂例子还得先去了解该概念，反而间接污染上下文 | 说明领域知识时，用仓内实际存在的算子或通用概念举例，而不是写"例如 BLAS 仓涉及的标准"——Agent 若不了解 BLAS，还需先去查证，偏离当前任务 |
