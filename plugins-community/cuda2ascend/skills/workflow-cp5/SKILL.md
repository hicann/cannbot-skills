# CP5 代码检视验收标准

本验收点判定**代码变更的质量**，即全部变更文件是否达到可提交评测的质量水平。本仓采用 direct launch 工程架构，代码检视须额外核对 **提交反作弊红线**（`repo-coding-rules` A 类条款）——A 类红线是算子实现的通用质量底线（不代算 / 不 CPU fallback / 不路由内置同名算子等），**评测集提交时（模式 A）违反 = 整算子 0 分**；模式 B 下命中 A 类红线同样为阻塞级问题（算子实现不真实）。

## 验收对象

全部变更文件（算子代码、测试代码、相关文档等本次改动涉及的文件）。

## 通过指标

以**多维度检视项 + 评分**判定，不凭主观印象：

- **提交反作弊（评测集提交时为零容忍）**：对照 `repo-coding-rules` A 类条款（A1-A7），无违规项——包装层不调 PyTorch/torch_npu 计算代算、不处理输入输出 tensor、不路由内置同名算子、不 CPU fallback、不缓存输出、不篡改 profiler、不返回 FakeTensor。命中任一 A 类红线 = 阻塞级问题（模式 A 评测集提交时 = 整算子 0 分）。
- **代码规范**：对照 `repo-coding-rules` B 类条款，无违规项（硬件参数硬编码、DataCopy 误用、流水线泄漏、Kernel 内禁止事项、API 未验证）。
- **设计一致性**：实现与开发方案 / 需求文档（= proto.yaml）一致，无偏离既定设计的私自改动；schema 与 proto.yaml 一致。
- **潜在风险**：无越界、精度、并发、资源泄漏等风险项。
- **冗余清理**：无死代码、无调试残留、无无关改动。
- **通过条件**：各维度检视项无阻塞级问题（A 类红线为零容忍——模式 A 评测集提交时违反 = 整算子 0 分，模式 B 同样为阻塞级），且综合检视评分达阈值（默认要求：无"阻塞 / 高"级问题遗留，A 类红线全部通过）。判定形式为"逐条款检视 + 评分达阈值"，不以整体观感裁定。

## 验收步骤

加载本 skill 时执行：

1. 遍历全部变更文件，按提交反作弊（A 类）、代码规范（B 类）、设计一致性、潜在风险、冗余清理五个维度逐条款检视。
2. 对照 `repo-coding-rules` A 类/B 类条款核实反作弊与编码规范；对照开发方案 / 需求文档（proto.yaml）核实规范与一致性。
3. 按评分机制打分，核对是否达阈值、有无阻塞级遗留（A 类红线为零容忍阻塞——模式 A 评测集提交时 = 整算子 0 分）。
4. 汇总检视结果，产出代码检视报告。

## 输出

本验收点产出**代码检视报告 / 检视结论**，引用 `workflow-doc-templates` 的 `CP5-代码检视报告` 模板组织：

- **通过**：报告结论明确为"通过"，附检视摘要（含 A 类反作弊核对结论）与整体质量评价。
- **不通过**：报告结论为"不通过"，并给出**结构化修改意见**——
  - 问题定位：按问题清单逐条列出维度、严重程度、位置（文件:行）、描述与修改建议；A 类红线违规标注为阻塞级（模式 A 评测集提交时 =「提交无效」整算子 0 分）。
  - 问题语义归属：算子实现（规范 / 一致性 / 风险问题 / 反作弊违规）。

报告作为中间交付件随验收结果一并返回。只验收不执行；允许指出问题并给建议，不自行改代码、不变更上游设计决策。
