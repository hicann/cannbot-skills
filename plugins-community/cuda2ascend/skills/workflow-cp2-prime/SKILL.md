# CP2' 方案确认验收标准

本验收点判定**开发方案与测试方案是否相互吻合**，即两者作为一套整体是否一致、无冲突，可共同进入开发阶段。

## 验收对象

开发方案文档（`workflow-doc-templates` 的 `2.2-开发方案设计`）+ 测试方案文档（`workflow-doc-templates` 的 `2.1-测试方案设计`），两份合并确认；二者共同承接同一份 `spec.yaml`（规范见 `ops-spec-gen`）为真值源。

前置约定：两份方案各自的单项检查均已通过，本验收点**只做跨方案一致性核对**，不重复任一方的单项评审（测试方案自身质量归测试方案检查、开发方案自身质量归开发方案检查）；两份文档各自应含内容以对应模板为准（随模板演进或子仓 override 自动对齐），此处不重复罗列。

## 通过指标

以**跨方案一致性对照矩阵**逐维判定，不凭主观印象；凡「大致吻合 / 应该能覆盖 / 视情况」等定性空话均判不达标。对照矩阵形如「开发方案的一项设计决策 ↔ 测试方案中与之呼应的验证手段 / 假设」，逐行核对是否咬合。

### 同源一致（Spec 真值对齐）

- 两份方案对同一份 `spec.yaml` 真值（dtype、shape 范围、精度容差、边界条件等）的引用完全一致，无相互矛盾，无任一方绕过 Spec 另立真值。

### 契约面对齐（接口 / 原型一致）

- 开发方案将实现的算子接口 / 原型（输入输出 tensor 的数量、顺序、dtype、shape 语义、内存格式 / 数据排布（布局，如 ND/NZ、NCHW/NHWC）、标量参数含义、workspace / tiling 等附加入参）与测试方案的 golden 及用例所假设的接口完全一致——否则测试无法驱动实现（如 golden 按 ND 造数而 kernel 按 NZ 读取 GM）。

### 验证闭合（关键路径与边界被覆盖）

- 开发方案关注的关键计算路径，测试方案有对应功能用例验证。
- 开发方案 Tiling / 多核切分策略引入的边界（尾块、对齐边界、切分临界 shape）在测试方案的边界用例中逐一有对应覆盖。

### 精度口径可达（设计精度 ↔ 测试容差）

- 开发方案的数值设计选择（累加 dtype、近似 / 快速算法、中间精度）与测试方案设定的容差及比对方式相互自洽——即按开发方案实现，其可达精度能落在测试方案容差判定之内；若设计天然无法满足所选容差，即为冲突。

### 无缝隙双向（功能点 ↔ 验证手段，含异常 / 边界约定）

- 开发方案声明会实现的每个功能点 / 分支（含空 tensor、空指针、越界等异常输入的约定行为），测试方案均有对应验证手段与预期结果。
- 测试方案假设的每个被测行为，开发方案均会提供，无「测试测了但开发不做」的悬空假设。

### 通过条件

上述各维在对照矩阵中逐行咬合、全命中，即为通过。各维的量化基线（必对齐的接口字段集、必覆盖的边界用例集、容差取值）由绑定实现给定；判定形式为「逐维构建跨方案对照表，逐行匹配，全命中即通过」。

## 验收步骤

加载本 skill 时执行：

1. 抽取两份方案对同一 `spec.yaml` 真值（dtype/shape/容差/边界）的引用，逐项核对完全一致（同源一致）。
2. 对齐两份方案描述的算子接口 / 原型，核对入参出参、tensor 布局与参数语义一致（契约面对齐）。
3. 构建"开发方案关键路径与 Tiling / 切分边界 ↔ 测试用例"的对照矩阵，核对验证闭合。
4. 核对开发方案数值设计与测试方案容差 / 比对方式是否自洽、精度可达（精度口径可达）。
5. 双向核对无缝隙：开发方案功能点 / 异常约定 → 测试有对应验证；测试假设行为 → 开发有对应提供。
6. 汇总各维对照结果，给出通过 / 不通过结论。

## 输出

- **通过**：明确结论"方案确认通过"。
- **不通过**：返回**结构化修改意见**——
  - 问题定位：逐条列出两份方案冲突 / 缺口的具体位置、所属对照维（同源真值 / 契约面 / 验证闭合 / 精度口径 / 无缝隙）与表现（指明哪一方需调整或双方需对齐）。
  - 问题语义归属：开发方案设计 或 测试方案设计（指明哪一方需调整或双方需对齐）；若冲突根因在 Spec（如 Spec 对某字段定义有歧义，导致两方案各自解读而分歧），标注归属于 Spec。

只判定与给意见，不自行修改任一方案，不替上游对齐设计。
