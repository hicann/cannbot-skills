# CP1 需求确认验收标准

本验收点判定**需求文档是否完整、明确、可执行**，即是否足以作为后续方案设计的可靠依据。本仓采用 direct launch 工程架构。需求文档须先确认**评测来源**（第 0 节）：模式 A（有评测集，须对齐算子原型定义 schema）或模式 B（无评测集，下游自建 golden/cases）。判定只做三件事：核对需求文档质量、区分「硬伤」与「待用户拍板项」、给出可判定结论；不改写需求、不臆断补全。本验收点为 **QA 核对 + 用户确认** 两段式——先由 QA 按检查项客观裁定，无硬伤后按问卷模板发用户逐项确认。

## 验收对象

需求文档，由 `workflow-doc-templates` 的 `1.1-需求分析` 模板产出。其应覆盖的确认项以该模板为准，涵盖评测来源（模式 A/B）、数学定义、算子规格（模式 A 须对齐评测集 schema/dtype/attrs）、目标芯片架构、精度要求、性能预期、代码架构选型、其他特殊要求，以及逐条记录的用户原始需求。

## 通过指标

以**检查项清单逐项判定**，不凭主观印象。必填确认项集合**以 `workflow-doc-templates` 的 `1.1-需求分析` 模板为权威**（不在此重复罗列，随模板演进自动对齐），对每一确认项按「存在 / 明确 / 无歧义」三态核对。三态展开为可操作判据：

### 完整性（存在）

- 模板每一确认项均有对应内容，无缺失、**无 `{...}` 占位符残留**。
- 用户原始需求**逐条落表**，未加工、未裁剪。
- **评测来源已确认**：需求文档第 0 节的评测来源模式（A/B）决策状态为「已用户确认」；未确认时并入确认问卷发用户拍板。
- **模式 A 附加**：算子 schema、dtype、attrs 与评测集算子原型定义（如 cann-bench `tasks/levelN/<op>/proto.yaml`）逐字一致——schema 不一致为硬伤（评测注册不上算子）。

### 明确性（可执行、拒绝定性空话）

逐类核对是否给出可判定取值，凡「待定 / 视情况 / 尽量 / 高精度」等悬空表述均判不明确：

- **数据规格**：dtype 为明确枚举；shape 有界，无「任意 / 不限」式开放上界。（模式 A：dtype 须与评测集 proto.yaml 一致）
- **精度要求**：权威源、可核对的出处路径、逐输出张量的判定指标与阈值三者齐备；**只点名标准而不给取值**（如仅写"参考某标准"）判不明确。模式 A 的权威源为评测框架实际执行判定的口径——需求文档若采信了更宽松的其它来源（算子说明的经典容差等）而未标注差异，判不明确。
- **性能预期**：模式 A 以 HAP 阈值表述（如「HAP ≥ 0.5」），模式 B 以耗时/带宽等可量化指标表述；或明确标注「无明确要求」；不接受「越快越好」。
- **目标芯片架构**：具体型号 + 架构版本（ascend910b / ascend910_93 / ascend950），不接受「昇腾系列」这类范围词。
- **代码架构选型**：选定架构为唯一取值且落在模板给定的枚举内，决策状态为「已用户确认」；「待定 / 由开发决定 / 视情况」判不明确，**只给出推荐项而未经用户拍板同样判不明确**。
- **接口与语义**：接口原型、参数方向 / 内存位置、数学公式均无歧义；模式 A 下须与评测集算子原型定义的 schema 一致。

### 一致性（互不矛盾、可追溯）

- 接口原型、数学定义、支持数据类型三者互不冲突（如原型 dtype 与数据类型表一致，且与 proto.yaml 一致）。
- 选定的代码架构与目标芯片架构、算子类别互不冲突：所选架构在可行性评估中被判为「不可行」或目标芯片不支持，即为矛盾。**选定架构与推荐架构不同不视为矛盾**——决策权在用户，只要该架构评估为可行即可。
- 每一确认项均可追溯到用户原始需求或评测集 proto.yaml/desc.md；**我方补充**（用户未提及、为闭合需求所加）须显式标注为待用户确认，不得以「已确认」混入。

### 通过条件

上述三类逐项通过三态核对，且不存在「硬伤」（见下）。确认项集合以模板为权威；判定形式为「逐项对照模板确认项清单 + 交叉一致性核对，客观裁定」。

## 待澄清项的处置

核对中发现的问题按性质分两类，处置不同——这是本验收点的核心判定动作：

| 类型 | 典型表现 | 处置 |
|------|----------|------|
| **硬伤** | 必填确认项缺失、占位符残留、自相矛盾、**模式 A 下 schema 与评测集不一致**、确认项凭空新增（需求无据） | 直接判**不通过**，返回结构化修改意见 |
| **开放取舍** | 只有用户能拍板、无客观对错的取值（评测来源模式、性能目标值、shape 支持范围取舍、**代码架构选型**、其他可选实现方案的选择） | 并入确认问卷发用户拍板，**不计为不通过**；补齐后再判定 |

区分原则：能靠需求文档本身、评测集 proto.yaml 或用户原始需求判定对错的 → 硬伤；只有用户能拍板的 → 开放取舍。

## 验收步骤

加载本 skill 时执行：

1. 以 `workflow-doc-templates` 的 `1.1-需求分析` 模板确认项为清单，逐项读取需求文档核对「存在 / 明确 / 无歧义」三态。
2. **先核对评测来源模式**：第 0 节模式 A/B 决策状态是否「已用户确认」；未确认则记为开放取舍并入确认问卷，步骤 3 的模式 A 附加核对跳过，待拍板后重新验收时执行。
3. **模式 A 附加**：对照评测集算子原型定义（如 cann-bench `tasks/levelN/<op>/proto.yaml`）核对 schema / dtype / attrs 是否逐字一致（不一致为硬伤）。模式 B 跳过此步。
4. 按明确性判据逐类核对取值可判定性；按一致性判据做接口 / 数学 / dtype 交叉核对。
5. 核对用户原始需求逐条落表，且各确认项与其可双向追溯、无遗漏、无越界新增。
6. 将问题按「硬伤 / 开放取舍」归类：存在硬伤直接判不通过，返回结构化修改意见，**不进入用户确认段**。
7. 核对无硬伤后，按下方**问卷模板**生成问卷 json，用会话问卷工具（opencode `question` / claude `AskUserQuestion` / dsh `ask_user_question`）直接发送用户并收集结论；问卷与回复成对落盘 `.cannbot/<算子名>/questionnaires/`（回复记为问卷同名 `.reply.json`）。代码架构选型尚未拍板时，问卷须带上推荐项、推荐依据与各候选架构的可行性评估结论，使用户可依据决策而非盲选。
8. 汇总判定：需求总览无异议、待拍板页均已拍板、待补齐项已补齐，即为通过；用户异议按条目打回需求文档修订。

## 问卷模板

核对无硬伤后，按下列格式用会话问卷工具（opencode `question` / claude `AskUserQuestion` / dsh `ask_user_question`）发送问卷（落盘 `.cannbot/<算子名>/questionnaires/CP1-需求确认.json`）。`{...}` 为占位符，取值自需求文档。「需求总览」页固定发送；「评测来源」「代码架构选型」页仅在决策状态为「待用户确认」时发送；「待补齐项」页仅在存在缺项或我方补充项时发送：

```json
{
  "questions": [
    {
      "question": "需求总览：\n\n| 项目 | 内容 |\n|------|------|\n| 数学定义 | {数学公式} |\n| 算子原型 | {接口原型} |\n| 目标芯片架构 | {芯片型号 + 架构版本} |\n| 数据规格 | {dtype / shape 范围} |\n| 精度要求 | {容差或引用标准} |\n| 性能预期 | {可量化指标或「无明确要求」} |\n\n需求文档完整路径：{.cannbot/<算子名>/1.1-需求分析.md}\n\n对此结果是否有疑问？",
      "header": "需求总览",
      "options": [
        { "label": "已确认，无异议", "description": "需求内容无误，继续开发流程" },
        { "label": "有异议，打回修改", "description": "需求需调整，打回修改" }
      ]
    },
    {
      "question": "评测来源模式（决策状态：待用户确认）：\n\n| 项目 | 内容 |\n|------|------|\n| 模式 A | 有评测集：对齐算子原型定义 schema，golden/cases 由评测集自带 |\n| 模式 B | 无评测集：下游自建 golden/cases（参考 cann-bench 范式） |\n\n请拍板评测来源模式：",
      "header": "评测来源",
      "options": [
        { "label": "模式 A", "description": "有评测集，对齐其算子原型定义 schema" },
        { "label": "模式 B", "description": "无评测集，下游自建 golden/cases" }
      ]
    },
    {
      "question": "代码架构选型（决策状态：待用户确认）：\n\n| 项目 | 内容 |\n|------|------|\n| 推荐架构 | {推荐值} |\n| 推荐依据 | {依据} |\n| 各候选架构可行性 | {各候选在目标芯片上的支持情况与可行性结论} |\n\n请拍板代码架构：",
      "header": "代码架构选型",
      "options": [
        { "label": "接受推荐：{推荐值}", "description": "按推荐架构继续" },
        { "label": "{候选架构2}", "description": "{该候选的可行性结论摘要}" },
        { "label": "{候选架构3}", "description": "{该候选的可行性结论摘要}" }
      ]
    },
    {
      "question": "以下确认项需求文档未覆盖或为我方补充，请逐项补齐或确认：\n\n{逐条列出待补齐项及其建议取值}\n\n如何处理？",
      "header": "待补齐项",
      "options": [
        { "label": "按建议取值补齐", "description": "接受列出的建议取值" },
        { "label": "我来补充", "description": "通过自定义输入逐项给出取值" }
      ]
    }
  ]
}
```

「代码架构选型」页的候选枚举与实现载体按目标芯片确定：ascend950 为 SIMD（RegBase 实现）与 SIMT 两种，其余低版本芯片仅 SIMD（MemBase 实现）一个选项（RegBase 与 MemBase 互斥，支持 RegBase 的芯片不使用 MemBase）；推荐项放 options 首位。

## 判定规则

- **通过**：核对无硬伤，需求总览选「已确认，无异议」，各待拍板页均给出明确结论，待补齐项已补齐。
- **不通过**：核对存在硬伤，或用户对任一条目有异议——返回结构化修改意见（异议条目 + 语义归属：需求），打回需求文档修订。
- 用户通过自定义输入补充的取值，回传需求文档修订后重新验收。

## 输出

- **通过**：明确结论「需求确认通过」，附用户确认记录。
- **不通过**：返回**结构化修改意见**——
  - 问题定位：逐条列出缺失 / 含糊 / 矛盾 / 评测来源未确认 / 模式 A 下 schema 不一致 / 不可追溯 / 凭空新增的具体确认项及其表现；用户异议则列出异议条目及其内容。
  - 问题分类：标注「硬伤」或「开放取舍」。
  - 问题语义归属：需求（需补充或澄清）。

只判定与给意见，不自行补写或改写需求文档，不臆断补全缺项。
