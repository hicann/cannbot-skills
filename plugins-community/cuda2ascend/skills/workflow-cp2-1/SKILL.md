# CP2.1 测试检查验收标准

本验收点判定**测试方案是否合理、覆盖充分**，即 golden 方案与分级用例设计是否足以充分验证算子功能正确性与精度。判定只做三件事：逐项核对测试方案质量、构建覆盖矩阵客观裁定、给出可判定结论；不改写测试方案、不实现 golden 或用例、不臆断补全。

## 验收对象

测试方案文档，由 `workflow-doc-templates` 的 `2.1-测试方案设计` 模板产出。其应覆盖的检查项以该模板为准，涵盖 golden 实现方案（参考框架/API、golden 计算路径、精度比对方式）、测试场景（正常 / 边界 / 异常 / 特殊值）与 L0（门槛）/ L1（功能）/ L2（异常）分级用例设计。

## 通过指标

以**检查项清单 + 覆盖矩阵**逐项判定，不凭主观印象。检查项集合**以 `workflow-doc-templates` 的 `2.1-测试方案设计` 模板为权威**（不在此重复罗列，随模板演进或子仓 override 自动对齐），逐项核对，凡「覆盖充分 / 大致齐全 / 视情况」等定性空话均判不达标：

### golden 可信

- 参考框架/API 明确，对应需求文档的 reference_oracle，无「待定」式悬空。
- golden 计算路径与需求文档的数学定义一致，可作为精度比对基准。
- 精度比对方式（逐元素 / 统计指标）有明确取值。

### 分级与场景完整

- L0 / L1 / L2 三级用例均有设计——L0 覆盖常规 shape/dtype 门槛，L1 覆盖典型 / 竞品 shape 的常用功能，L2 覆盖超大 shape、空指针等异常输入。
- 正常 / 边界 / 异常 / 特殊值四类场景均有对应用例，无空缺场景类别。

### 覆盖对照需求（覆盖矩阵全命中）

- **标准产物前置门**：测试方案须包含覆盖维度分解与覆盖矩阵（模板对应章节）；缺少可核对产物者，直接判不通过——无可核对产物即无从审计。
- **独立重算**：QA 不采信方案自述的覆盖，须**从需求文档独立重算**期望覆盖集（声明的 dtype、shape 范围、边界、特殊值、广播维度），再与用例设计逐维对照——期望以重算为准，非以方案声明为准。
- 需求文档声明的各维度在用例设计中逐维有对应覆盖，无遗漏维度，无「任意 / 不限」式开放上界未被用例约束。
- 覆盖以可核对的**覆盖矩阵**（需求文档声明维度 × 用例设计的逐维对照表，由 QA 复核期独立自建）判定，非凭「看起来覆盖了」；若方案用 `ascendc-st-design` 引擎生成，可将其覆盖报告作为交叉核对物，但不替代独立重算。

### 精度容差明确

- 每类用例的比对方式与容差有可判定取值依据，容差引用 `ops-precision-standard` 对应标准或需求文档容差字段；不接受纯定性词（如「高精度」）。

### 通过条件

上述四类逐项通过 + 覆盖矩阵全命中，即为通过。量化基线（各分级必过用例集、覆盖矩阵门槛、容差取值）由绑定实现给定；判定形式为「逐项对照模板检查项 + 覆盖矩阵核对，客观裁定」。

## 验收步骤

加载本 skill 时执行：

1. 以 `workflow-doc-templates` 的 `2.1-测试方案设计` 模板检查项为清单，读取测试方案文档逐项核对。
2. 核对 golden 参考框架/API 与计算路径同需求文档数学定义的一致性。
3. 逐级核对 L0/L1/L2 用例与正常 / 边界 / 异常 / 特殊值四类场景是否齐备。
4. 先核对方案是否含覆盖维度分解与覆盖矩阵（缺则不通过）；再**从需求文档独立重算**期望覆盖集，与用例设计逐维对照核对全命中，不采信方案自述覆盖。
5. 核对各类用例的容差依据（`ops-precision-standard` 或需求文档字段）是否明确。
6. 汇总各项判定，给出通过 / 不通过结论。

## 输出

- **通过**：明确结论「测试方案检查通过」。
- **不通过**：返回**结构化修改意见**——
  - 问题定位：逐条列出 golden 缺陷、缺失的用例分级 / 场景类别 / 覆盖维度、容差依据不足处及其表现。
  - 问题语义归属：测试方案设计；若真值冲突根因在需求（如需求未声明某维度导致无从覆盖），标注归属于需求。

只判定与给意见，不自行修改测试方案，不实现 golden 或用例，不替上游决定用例取舍。
