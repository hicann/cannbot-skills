# CP2.1 测试检查验收标准

本验收点判定**测试方案是否合理、覆盖充分**，即对评测集评测用例的覆盖核对与补充设计是否足以充分验证算子功能正确性与精度。评测集自带 `golden.py` + `cases.yaml`（如 cann-bench），测试方案的职责是**核对评测集 cases 对 proto 声明维度的覆盖完整性**并**补充未覆盖场景**，而非从零设计。判定只做三件事：逐项核对测试方案质量、构建覆盖矩阵客观裁定、给出可判定结论；不改写测试方案、不实现 golden 或用例、不臆断补全。

## 验收对象

测试方案文档，由 `workflow-doc-templates` 的 `2.1-测试方案设计` 模板产出。其应覆盖的检查项以该模板为准，涵盖 golden 对齐方案（评测集 golden.py 引用、计算路径核对）、评测集 cases 覆盖核对（覆盖矩阵）、补充用例设计（评测集 cases 未覆盖的场景）与 L0/L1/L2 分级。

## 通过指标

以**检查项清单 + 覆盖矩阵**逐项判定，不凭主观印象。检查项集合**以 `workflow-doc-templates` 的 `2.1-测试方案设计` 模板为权威**（不在此重复罗列，随模板演进自动对齐），逐项核对，凡「覆盖充分 / 大致齐全 / 视情况」等定性空话均判不达标：

### golden 对齐可信

- golden 引用评测集 golden（如 cann-bench `tasks/levelN/<op>/golden.py`，评测集自带，提交方不重写），无「自建 golden」式悬空。
- golden 计算路径与需求文档（= proto.yaml + desc.md）的数学定义一致，可作为精度比对基准。
- 精度比对方式（逐元素 / 统计指标）有明确取值，具体判定指标与阈值见下方「精度口径权威且可执行」。

### 评测集 cases 覆盖核对

- **覆盖矩阵全命中**：测试方案须含覆盖维度分解与覆盖矩阵（proto 声明 dtype × shape 范围 × attrs × 评测集 cases 逐维对照表）；缺少可核对产物者，直接判不通过。
- **独立重算**：QA 不采信方案自述的覆盖，须**从 proto.yaml 独立重算**期望覆盖集（声明的 dtype、shape 范围、边界、特殊值、广播维度），再与评测集 cases 逐维对照——期望以重算为准，非以 cases 声明为准。
- proto.yaml 声明的各维度在评测集 cases 中逐维有对应覆盖，无遗漏维度，无「任意 / 不限」式开放上界未被 cases 约束。
- 覆盖以可核对的**覆盖矩阵**（proto 声明维度 × 评测集 cases 逐维对照表，由 QA 复核期独立自建）判定，非凭「看起来覆盖了」；若用 `ascendc-st-design` 引擎生成，可将其覆盖报告作为交叉核对物，但不替代独立重算。

### 补充用例合理

- 评测集 cases 未覆盖的场景（如特定尾块/非对齐/多核边界）有补充用例设计，补充用例不与评测集 cases 重复。
- 补充用例仅供开发期自测，不替换评测集 cases。

### 精度口径权威且可执行

- **逐输出张量成表**：测试方案含精度判定口径表，逐输出张量列「dtype → 判定指标 → 阈值 → 权威源出处 → 本地断言实现位置」；缺表、合并输出、或留「参考 XXX 标准 / 高精度 / 容差内」式定性引用者，直接判不通过。
- **权威源可溯源**：每条阈值都给出可核对的出处路径（评测框架实际执行判定的实现 / 评测集精度标准规范 / 算子原型定义与算子说明；模式 B 为需求文档声明或 `ops-precision-standard` 对应条目）。
- **QA 独立核对权威源**：不采信方案自述的口径，QA 按出处路径读原文重新确认判定指标与阈值——出处不存在、字段对不上、或方案取值与原文不符，判不通过。多处来源冲突时以**评测框架实际执行判定的口径**为准。
- **可执行**：口径已指明本地断言的实现位置（哪个测试环节、以何种方式产出指标实测值与阈值对照），而非只声明"由框架最终裁定"。
- **差异必须显式**：本地口径与权威口径存在差异（指标不同 / 阈值更宽）时，方案须逐条列出差异项、原因与风险，并标注该差异须提请确认；辅助容差只能标注为交叉核对项，不得作为通过依据。未显式记录的宽松化，判不通过。

### 通过条件

上述四类逐项通过 + 覆盖矩阵全命中，即为通过。判定形式为「逐项对照模板检查项 + 覆盖矩阵核对，客观裁定」。

## 验收步骤

加载本 skill 时执行：

1. 以 `workflow-doc-templates` 的 `2.1-测试方案设计` 模板检查项为清单，读取测试方案文档逐项核对。
2. 核对 golden 引用评测集 golden.py，计算路径同 proto.yaml 数学定义一致。
3. 逐级核对 L0/L1/L2 用例与评测集 cases 的覆盖对照是否齐备。
4. 先核对方案是否含覆盖维度分解与覆盖矩阵（缺则不通过）；再**从 proto.yaml 独立重算**期望覆盖集，与评测集 cases 逐维对照核对全命中，不采信方案自述覆盖。
5. 核对精度判定口径表：逐输出张量的判定指标与阈值是否齐备；再**按出处路径读原文独立核对**权威源取值（模式 A 优先核对评测框架实际执行判定的实现），核对方案取值与原文一致；本地口径与权威口径的差异是否已逐条显式记录。
6. 核对口径已指明本地断言的实现位置，可在开发期执行并产出指标实测值。
7. 汇总各项判定，给出通过 / 不通过结论。

## 输出

- **通过**：明确结论「测试方案检查通过」。
- **不通过**：返回**结构化修改意见**——
  - 问题定位：逐条列出 golden 对齐缺陷、覆盖矩阵缺失维度、补充用例不合理处，以及精度口径缺表 / 不可溯源 / 与权威源不符 / 无本地断言实现位置 / 宽松化未显式记录等问题及其表现。
  - 问题语义归属：测试方案设计；若真值冲突根因在需求（如 proto.yaml 未声明某维度导致无从覆盖），标注归属于需求。

只判定与给意见，不自行修改测试方案，不实现 golden 或用例，不替上游决定用例取舍。
