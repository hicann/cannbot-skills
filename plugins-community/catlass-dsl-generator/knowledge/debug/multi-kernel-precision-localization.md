# 接口与概念

多 kernel 链的精度问题通常不是“某个 kernel 完全算错”，而是跨 kernel 边的数值契约没有
对齐：dtype、内部累加 dtype、舍入位置、归约/重复索引/分段顺序、有效区/padding 或消费
分支发生变化。全局 matched ratio 会掩盖少量大偏差；只看最终输出也无法判断偏差是在哪条
边产生的。

定位顺序固定为：**阶段契约 → 局部检查 → 真实链路 → 双向替换 → 首个偏差边 → 单因素
修复 → 原判据复测**。不要用下游“给定候选中间量算得对”来推断上游正确，也不要用下游
局部通过来关闭整链问题。

最好的做法是在设计期就把契约钉死：读 reference 的每一步 dtype、舍入和归约顺序，写成
阶段契约，并用机制探针验证不确定的 API 行为。阶段 oracle 和双向替换主要用于“契约已
写清但仍有偏差”或“设计期无法确定”的情况。

## 通用规则（任何多 kernel 链都适用）

1. **中间量 dtype 与标杆一致**：每条跨 kernel 边的存储 dtype、内部累加 dtype 和转换时机
   必须与标杆在该点的语义一致。标杆在更高精度保留的中间量，候选不能提前窄化；标杆在
   低精度的地方，也不能默默用高精度一路算完再转，除非有实测误差证据并记录。
2. **layout / shape / stride / 有效区一致**：逻辑坐标、padding、转置视图和无效 lane 的
   处理必须能一一对应；padding 值不得参与归约或散写。
3. **舍入位置一致**：缩放、归一化、激活和 cast 的先后顺序必须与标杆一致；代数等价不等于
   数值等价。
4. **归约与顺序一致**：重复索引的累加顺序、分段/分块累加顺序、部分和合并顺序、原子累加
   的顺序语义都要与标杆对齐；不确定时用固定输入做顺序实验。
5. **每个中间量都有独立 oracle**：oracle 来自 reference 中间量或独立实现，不能是候选
   自己产生的输出；下游用候选输入算得对，不能证明上游正确。
6. **先定位首个偏差边，再改代码**：逐边比较候选/标杆中间量，找到第一条不满足契约的边；
   在定位前不要同时改多个 kernel、dtype 或容差。

# 用法

## 1. 固定每条跨 kernel 边的精度契约

每条边记录：

- 数学含义与缩放/广播/激活等代数变换的位置；
- shape、stride、有效区、padding 和无效值的处理；
- 输入/输出 dtype、内部累加 dtype、舍入发生的位置；
- 重复索引/散写、归约、分段/分块累加的顺序；
- 哪些分支共同消费该中间量；
- 对应的 oracle：reference 中间量、独立 Torch 实现，或明确写出的替代验证。

选择 kernel 划分前，先检查该划分是否新增舍入、改变归约顺序或丢失高精度中间量。若改变，
必须用实测误差证据说明可接受，不能仅凭代数等价判定。

## 2. 三类检查分开做

| 检查 | 输入来源 | 回答的问题 |
|---|---|---|
| 局部 kernel 检查 | 标杆中间量或明确受控输入 | 给定正确输入，该段是否正确？ |
| 真实链路检查 | 候选真实上游输出 | 第一次偏离标杆发生在哪条边？ |
| 误差传播检查 | 标杆/候选中间量互换 | 上游误差是否足以导致最终失败？ |

局部检查用候选自己生成的输入，只能回答“下游对候选输入是否自洽”，不能回答“候选输入
是否正确”。已有分段探针可以保留，但要补齐后两类检查。

## 3. 双向替换矩阵

对每个关键中间量：

| 实验 | 前半段 / 后半段 | 解释边界 |
|---|---|---|
| A | 标杆 + 标杆 | 验证拆分后的 oracle 能重现原 reference |
| B | 标杆中间量 + 候选后半段 | 仍失败则后半段有独立问题 |
| C | 候选中间量 + 标杆后半段 | 失败说明上游误差经标杆后半段传播已足以致错 |
| D | 候选 + 候选 | 与实际交付链路对照 |

所有输出分支分别记录；替换后半段时保留标杆原来的 dtype、舍入位置和累加顺序，否则替换
实验改变了验收对象。大中间量可以按段导出、比较和重放，不必一次完整保存。

## 4. 找首个偏差边

建议检查点：每个跨 kernel 边的输入、输出、内部累加结果、转换前后，以及各消费者的输入。

每个检查点记录：首错坐标、期望值、实际值、最大绝对误差、匹配比例、错误数量，以及
tile/row/lane 分布。相对误差在接近零处要结合绝对误差解释；高匹配比例下要单独看最大
绝对误差和参考值幅度桶。

固定输入重复运行：若匹配比例或最大误差变化，优先查初始化、覆盖、布局、同步和运行配置；
若稳定，再做舍入、归约和误差传播的受控实验。两类问题可能并存。

## 5. 先分类失败，再谈精度

读结构化结果 JSON，按数值不匹配、输入生成失败、预期报错验证、空输入、info、确定性
用例分别统计；不要只 grep 日志，也不要把总失败数全部归为 kernel 精度。`deterministic=true`
只表示重复运行一致，不证明算法正确。

诊断可以扫不同阈值、加高精度对照和中间量检查；正式验收仍回到冻结的 reference、workload
和容差。需要修改契约时单独记录原因，并保留旧判据结果。

# 代码模式

以下为阶段 oracle 的伪代码，API 名称按实际实现替换：

```python
stages = ["stage_1", "stage_2", "shared_intermediate", "out_branch_1", "out_branch_2"]
ref = run_reference(inputs, collect=stages)
cand = run_candidate(inputs, collect=stages)
for name in stages:
    report(name, ref[name], cand[name])   # matched_ratio, max_abs, first_error, tile/lane

# 双向替换：只替换一个中间量，保持后半段的 dtype/顺序与 reference 一致
run_candidate_with(ref["shared_intermediate"], from_stage="downstream")
run_reference_with(cand["shared_intermediate"], from_stage="downstream")
```

每次 run 记录：源码 SHA、输入 seed/摘要、DSL/CANN/设备版本、tile/配置、容差、命令、
进程和退出码。不要反复读取同一份日志当作新进展。

# 约束

- 容差只吸收完全对齐标杆实现后的浮点尾差；dtype、舍入位置/模式、累加 dtype 或归约顺序
  不一致属于精度 bug，不能靠容差通过。
- 局部下游正确不证明上游中间量正确；必须直接比较中间量。
- 不能用候选自身产生的中间量作为该阶段自己的 oracle。
- 不得通过修改 reference、workload 或正式容差来“通过”；诊断阈值扫描与正式验收分开。
- 替换实验必须保留标杆后半段的 dtype、舍入位置和累加顺序。
- 高匹配比例下仍要检查最大绝对误差、首错坐标和参考值幅度；少量大偏差可能被比例掩盖。
- 输出不稳定时先排除初始化、覆盖、布局、同步和配置，不要直接归因于舍入。
- 单例与整轮表现不同，不能唯一指向某个同步或状态问题；需要 fresh process、B→B、A→B、
  A→B→A 的顺序实验，并单变量改变初始化/同步。
- 最终验收必须覆盖所有输出分支、分段边界、重复索引、抵消/极值和空输入。

# 失败表现

- 局部下游用候选中间量算得对，但整链失败：上游中间量已偏离，先建参考中间量 oracle。
- 只有部分用例失败，重复运行匹配比例变化：初始化/覆盖/布局/同步/配置问题。
- 一个输出分支通过、另一个不匹配：先固定同一份标杆共享中间量，分离输入差异与累加/
  归约顺序差异。
- 匹配比例很高但最大绝对误差很大：少量元素严重错误，查首错坐标、幅度桶和尾块。
- 单例通过、整轮失败：跨用例状态污染或配置漂移，做顺序实验而不是继续调参。
- 提高容差后通过：契约漂移，不是修复；保留原判据结果并记录变更依据。

# 验证方法

修复后回到冻结的 reference、workload 和容差复测；保留修复前的中间量证据和失败列表。
至少覆盖：重复索引、正负抵消、极值、不同缩放/参数、分段边界、空输入和所有输出分支。
对不稳定用例固定输入重复 N 次，分别记录匹配比例和最大绝对误差；若仍不稳定，继续按
初始化/覆盖/布局/同步排查，不把“重复运行一致”当成正确性证明。

具体到某个机制时，再查 `knowledge/debug` 与 `knowledge/dsl` 中对应的条目。
