# CANNBotDSL 探针调试法

CANNBotDSL 里最贵的 bug 不会报错。编译干净、不 crash、`torch.npu.synchronize()` 正常返回，只是数字不对。这类 bug 读代码找不到（代码「看起来」是对的，否则你不会那么写），加 print 也找不到（device 侧的中间量拿不出来）。

**唯一可靠的手段是最小探针 + 参数扫描。** 这个 skill 讲怎么用好它们，以及几个反直觉的坑。

## 何时用

- kernel 编译通过、跑完了，但精度不达标
- 一部分 shape 对、另一部分错
- 不确定某个框架 API 的语义（**开发前就该用**，不用等出 bug）
- 隔离测试全绿但整体仍错 ← 这条最容易走错方向，见 §3

编译报错走 `../../debug-skills/cannbotdsl-runtime-debug/SKILL.md`；crash/hang 走 `../../debug-skills/cannbotdsl-crash-debug/SKILL.md`。本 skill 只管「跑通了但结果错」。

## 1. 探针先行：不要等出 bug

写 kernel 之前，把设计里**拿不准的 API 语义**先用探针钉死。成本极低（一个探针 20~60 行、几分钟），收益极高：同样的错误在 1000 行 kernel 里可能要查几小时。

判断标准：如果你在心里说「这个参数应该是……吧」，那就是一个探针。

真实例子——MLA 开发前写了两个探针验证两种 matmul 形状，当场抓到两个语义错误：

| 探针发现 | 如果留到 kernel 里 |
|---|---|
| `tile_view` 的 coord 是 **tile 索引**不是元素偏移 | 静默算错 rel=0.93，且和其他 bug 混在一起 |
| PV 的 L1→L0B 要 `transpose=True`，QK 不要 | 静默算错 rel=1.36 |

两个都是「编译通过、结果错」，都在 20 行探针里 5 分钟定位。

## 2. 一个合格的探针

三条要求，缺一条结论就不可信：

**最小** —— 只包含被验证的那一件事。要验证 matmul 形状，就不要带 softmax。每多一个组件，结论就多一分歧义。

**上板** —— 必须在真机跑出数值并和 torch 对比。只做编译验证只能证明「能编译」，对静默数值错误零信息量。这类 bug 的定义就是编译得过。

**单一变量** —— 探针之间只差一个因素。想知道是不是 transpose 的问题，就跑 `transpose=True` 和 `transpose=False` 两版，其余完全相同。

另外：**探针自己挂了不是探针结论**。如果探针因为 harness 写错而编译失败（channel 协议不完整、GM→UB 走了不支持的路径等），那只说明探针没写对，不能推出被测组件的任何结论。修探针，或者换个角度验证。

### 2.1 探针会骗你的两种方式（都返回 PASS，都是假结论）

探针挂掉很好办 —— 你会看到报错。**危险的是探针"跑通了"但结论无效**：它给你绿灯，而你据此改了 kernel。实战踩到两次，两次都差点定案：

**坑 A：一个 region 里连写同一 buffer 的多个偏移。** 想省事把 N 个问题写进一个 buffer 的 N 个偏移一次跑完，结果前几个对、后几个错 —— **包括一个逻辑上平凡正确的对照组也错了**。根因是 `../cannbotdsl-vf-fusion/SKILL.md` §6 陷阱 4（融合时桥接到陈旧 store）**反噬探针本身**，与被测 op 无关。

> 症状识别：**对照组都错了，先怀疑探针结构，别怀疑硬件。**
> 规避：**每个问题一个独立 `@jit` region、一个独立 buffer。** 多跑几次的成本远低于一个假结论。

**坑 B：用了让两种假设无法区分的输入。** 验证 `vmadd(acc,lhs,rhs)` 是 `acc + lhs*rhs` 还是 `acc*lhs + rhs` 时，第一版探针写的是 `vmadd(a, b, a)` —— 而 `a + b*a == a*b + a`（交换律），**两种读法数值完全相同**。探针返回 PASS，"证实"你原本相信的那个，你无从察觉。

> 症状识别：这类探针**永远 PASS**，无论真相如何 —— 所以它的 PASS 不携带任何信息。
> 规避：设计输入时先自问「**如果我的假设是反的，这个输入会给出不同的数吗？**」答案是"不会"就换输入。测操作数序要用**三个互不相同、不满足任何对称性**的值（如 2.0 / 3.0 / 5.0）。

**通用判据**：一个探针的 PASS 只有在**它的 FAIL 是可能的**时才有意义。写完先问一句：**什么情况下这个探针会失败？** 答不出来，它测的就不是你以为的东西。

## 3. 最贵的坑：隔离探针全绿，kernel 仍然错

这是本方法论里唯一反直觉的一条，也是实战中代价最大的一条。

真实案例：MLA 在 `d_nope=448` 时静默算错（MERE 8e-2），而 512/384/256 全对。为了定位，写了四个隔离探针：

| 探针 | 验证内容 | 结果 |
|---|---|---|
| P4 | QK 在 448 的尾块 | ✅ 精确 |
| P5 | 尾块的零填充语义 | ✅ 精确 |
| P6 | PV + UB 存储在 448 | ✅ 精确 |
| P8 | 448 + strided(BSND) 视图 | ✅ 精确 |

**四个全绿，kernel 照错不误。** 继续往单个组件里挖是错的方向——它们真的都没问题。

真正的原因是**交互**：QK 和 PV 的 L0 操作数形状本来就不同，

```
QK:  S[M,tile_n]  = Q[M,d_chunk] @ K^T[d_chunk,tile_n]
PV:  O[M,d_chunk] = P[M,tile_n]  @ V [tile_n,d_chunk]
```

只在 `d_chunk == tile_n == 128` 时**偶然重合**，所以共用一对 L0 channel 在 512 下毫无问题；`d_chunk=64` 时形状不同，复用就喂给 mmad 一个错形状的操作数。每个探针单独测时用的都是同一种形状，自然测不出来。

**规律**：
> 隔离探针通过，只证明该组件**在那个配置下**是对的，不证明组件本身没问题，更不证明组件之间的假设一致。
>
> 探针全绿而整体仍错 → **立刻转向找组件间的共享假设**（共用的 buffer、共用的 channel、共用的常量），不要再往单个组件里挖。

排查共享假设的具体动作：列出被多个组件共用的每一个资源，对每个资源写出**每个使用者对它的形状/布局/生命周期假设**，然后找哪两条假设只在当前参数下碰巧一致。

## 4. 参数扫描找边界（最高效的单一手段）

比起在一个失败 case 上反复挖，**扫描参数找边界**几乎总是更快。一个落在已知常量上的锐利边界会直接点名机制。

三个真实战例：

```
扫 S（query 长度）:  S≤16 全错, S=17 全对
  → 边界正好是 tile_vec_m=16 → split-M 的空分区

扫 d_nope:  256 ✅  384 ✅  448 ❌  512 ✅
  → 只有非 128 倍数的错 → 尾块 / chunk 划分

扫 S_kv:  128 ✅  129 ❌  130 ❌  160 ❌  192 ❌  255 ✅  256 ✅
  → 误差随「被 padding 的列数」增长，不是随尾块大小
  → 补 1 列(255)能过、补 64 列(192)错得最凶 → padding 列污染了归约
```

第三例尤其说明问题：如果只测 129/130，会以为「尾块小就错」；加上 255 才看出真正的自变量是**填充列数**，机制随之明确（零填充列的 score=0，`exp(0-rowmax)` 是非零权重，撑大 softmax 分母）。

**怎么选扫描点**：在怀疑的常量（tile 尺寸、向量宽度、fractal 对齐）两侧各取几个点，务必包含 `边界-1 / 边界 / 边界+1`，并且**两端都要取到「应该对」的点**——只扫失败区间看不出边界。

## 5. 误差形态定位法

拿到错误结果先别改代码，先看**错在哪里**。形态直接指向机制：

| 误差形态 | 指向 |
|---|---|
| 所有行、所有列**均匀**偏差 | 共享状态被污染（softmax 的 running max/sum、跨核 channel），**不是**几何/寻址问题 |
| 只错某个连续行段 | m-tile 划分、split-M 分区 |
| 只错某个连续列带 | 输出轴分块、L0C 列带偏移 |
| 错行恰好是最后 k 行 | 尾块处理 |
| 误差随某参数单调增长 | 该参数直接参与错误机制（见 §4 第三例） |
| 只有个别元素误差巨大，其余正常 | 大概率是**判据**问题不是 kernel 问题（见 §6） |

具体做法：把 `(got - golden).abs()` 按行、按列、按 tile 边界分别 reduce 打印出来。

真实例子：MLA 短序列 bug 的误差是**均匀**的，一度被误判为 softmax 权重算错；按上表它其实指向「共享状态被污染」，最终确认是空分区的 AIV 在 padding 上算 rowmax/rowsum 并写了共享的 running max/sum，把**另一个** AIV 的行也带偏了。形态表能省掉这一轮弯路。

## 6. 精度基准：别让判据骗了你

**绝不要拿同 dtype 的 torch golden 当基准。** 低精度参考实现自身的误差可能比被测 kernel 还大。

实测数据（MLA，fp16 输入）：

| 对比 | MERE |
|---|---|
| golden@fp16 vs golden@fp64 | **2.10e-3** ← 参考实现自身的误差 |
| 我们的 kernel vs golden@fp64 | 1.64e-3 ← 比参考还小 |

用同 dtype golden 当基准，会得到「kernel 不达标」的错误结论，进而去改一份本来正确的代码。

**正确做法**：
1. golden 用 **fp64 计算后截断到目标 dtype**
2. 用项目的**官方 checker**（如 `cann-bench` 的 `compare_tensors`），它还带小值域/相消兜底——`|golden|` 接近 0 的元素上相对误差本来就没有意义，朴素公式会炸出 MARE=1074 这种数字

**区分「实现 bug」和「设计固有精度」**：用 torch 复刻 kernel 的数值路径（fp32 累加、P cast fp16、fp32 rescale……），对 fp64 打分。如果模拟值和实测值吻合，**实现就是对的**，误差来自设计选择：

```
模拟数值路径 vs fp64 : 1.641e-3
实测 kernel  vs fp64 : 1.639e-3   ← 吻合到 3 位有效数字 → 实现无 bug
```

这一步能避免在正确的代码上浪费时间，也能量化「换设计能换回多少精度」（该例中 P 保持 fp32 可到 1.0e-6）。

## 7. 修复后的验证纪律

**改完必须重跑全量，不能只跑目标 case。** 两个真实教训：

**教训一：修复可能打到无关路径。** 尝试给 causal 加 head folding，目标 case 仍错，而**本来正确的 prefill case 反而崩了**（MERE 1.11）。原因是判据写成 `N_q % TILE_CUBE_M == 0`，128 % 64 == 0，所以 prefill 也被折了。只跑目标 case 会以为「没修好」，跑全量才看到「还弄坏了别的」。

**教训二：验证维度要覆盖修复的语义。** 短序列（S=1/2）的 bug 修完后，所有定向验证都是 `is_causal=False`，全绿。但 padding 方向的错误只在 causal 下暴露——causal mask 是右下角对齐的，追加 padding 会让每个真实行少看 `pad` 个 key。**非 causal 全绿给了虚假的安全感**，直到跑完整 sweep 才发现。

规律：修复涉及哪个语义维度（mask / layout / dtype / 尾块），验证就必须在那个维度上变化，不能只在「最容易构造的那一档」上验证。

## 8. 把结论写下来

每个探针的结论——包括**失败的尝试**——都记进一个 `FINDINGS.md`。理由很实际：这类 bug 的结论无法从代码反推（代码里只剩正确的那个写法，看不出为什么），下次遇到同类问题会从头再查一遍。

每条记：**现象 → 排查路径（含被排除的假设）→ 根因 → 修法 → 教训**。被排除的假设和根因一样有价值，它能让下一个人不必重走。

## 外部依赖

本 skill 的方法论本身无依赖，但**执行**探针需要：

| 依赖 | 为什么必需 | 缺失后果 |
|---|---|---|
| **NPU 设备** | 静默数值错误的定义就是编译得过，必须真机跑出数值 | 整个方法失效——只做编译验证对这类 bug 零信息量 |
