# 文件检视场景（轻量流程）

## 触发
检视 DSL 算子、审核代码、代码审查、帮我检视 xxx、检查有没有问题、
复核算子实现

---

## 编排

### 阶段1：派发可读性检视子 Agent

Read `steps/clause-review.md` 获取 prompt 模板，派发 1 个检视子 Agent
（`subagent_type: "Explore"`，只读代码，文本返回结构化发现），传入：

- 算子文件路径（多文件/目录输入时每个文件各派 1 个，单消息并行）
- 规则文档路径：`references/readability-rules.md`
- 方法论路径：`core/methodology.md`

子 Agent 按十条原则的识别规程逐一检测，按置信度打分举证、判定，
返回 YAML 结构化发现。

### 阶段2：撰写报告

按 `steps/report-write.md` 输出 `./{算子名}_review_report.md`。

**撰写要求（三原则：清晰、可读、简洁）**：

- **结论先行**：开头 2-3 句话说清命中了哪几条原则、问题集中在什么
  段落、建议的整改优先级——读者看完结论就知道要不要继续往下读
- **一张表**：全部问题一张表，一行一条，问题和修复各一句话；
  超过一行说明没抓住重点，重写
- **证据链一行压缩**：`+40 规范违反@1234 +30 防御缺失@549 -15 上游
  校验@213 → 85%`，不逐条列证据
- **片段非必要不给**：只有"一句话说不清、必须看代码才懂"的问题才
  附最短真实片段（≤6 行，原文禁止改写），表格该行标注 `[见下]`
- **待确认写明确认什么**："需要作者确认 X"而不是罗列问题
- **不写元信息**：检视过程、规则介绍、统计口径说明都不写——读者
  是算子作者，不是技能用户
- **全零也出报告**：结论写"未发现可读性问题" + 豁免说明一句

---

## 约束

- 严格按阶段顺序执行；子 Agent 必须实际 Read 算子代码，禁止仅凭规则
  文档示例下结论
- 每个 FAIL 必须引用真实行号和最短足以证明的代码片段（≤6 行）
- 待确认是一等结论，禁止为凑结论强行判 FAIL
