# 可读性规则（DSL-R01 ~ R10）

语料来源：191 个人工检视问题中的 A 命名（~35%）、B 魔鬼数字（~15%）、
D 结构风格（~20%）。本文档不是判定清单，而是**判定框架**：每条原则给出
意图、识别规程（问什么、读什么）、举证要点、豁免思路、修复方向。

**使用方法**：逐条原则对算子文件执行识别规程 → 对发现的候选按方法论
置信度打分举证 → 判定。文档中的"常见形态"是语料中反复出现的例子，
**用于帮助理解原则，不是穷举，更不是检测词表**——命中形态不必然违规，
不命中形态也不必然合规；判定永远以原则和证据为准。

---

### DSL-R01 命名自注释

**意图**：名字是读者理解代码的第一入口。当读者必须跳转到赋值/声明处
才能理解一个名字时，阅读成本随跳转次数指数上升——这是语料中占比
最高的问题。

**识别**：通读代码，对每个变量/参数/函数名问：
> "只看使用处，我能说出它是什么轴/哪个阶段/什么结构/什么单位吗？"

答不上来即候选。常见形态（举例，非穷举）：
- 过短缩写，语义全靠注释或上下文反推
- 无领域限定的通用词（表位置/表状态/表结果的泛泛之词单独使用）
- 用类型或容器当名字（dtype 缩写、buffer 直称）
- 成组的单字母前缀别名，前缀本身无含义

**举证**：引用使用处与赋值处，说明"理解使用处必须回看赋值"这一
跳转真实存在。名字存活范围很小且语义就是右值本身时降级。

**豁免思路**：读者群有共享约定的惯用名——判断依据是同仓/文档有
明确约定或全文一致使用，而不是"看着眼熟"。

**修复**：名字承载轴/阶段/结构/单位限定；统计量、奇偶半区、延迟线
等用完整语义词；函数名预告返回内容的领域语义。

### DSL-R02 名实一致（不误导）

**意图**：缩写名只是读不懂，误导名会让读者建立**错误**心智模型，
顺着错误假设改代码——比 R01 危险得多。

**识别**：对名字中含有的领域词（模式/结构/单位/状态词），核实变量
真实语义是否与之相符。问：
> "按名字理解，我会对这个变量的语义产生什么预期？实际语义符合吗？"

常见形态：名含某领域词但语义是另一回事；名为布尔前缀但用整数
赋值与判断（整数伪布尔）；函数名是"处理/解析/执行 + 泛词"，与函数
体实际职责对不上。

**举证**：给出名字的预期语义（依据领域常识）与代码实际语义的
对照，两者冲突成立即 high。

**豁免思路**：名字虽简但有就近注释消歧——降为 R01 low。

**修复**：换真实语义的自注释名；布尔语义用真布尔；模式/状态用
枚举而非裸值。

### DSL-R03 一名一义，一义一名

**意图**：同一概念多种写法，读者要维护"它们是不是一回事"的映射；
同一名字多种含义，读者每见一次都要重新消歧。

**识别**：双向检查：
1. 对核心领域概念（统计量/缩放/延迟线/分核结果等），收集文件内
   所有指代它的名字——多于一个即候选（词序变体、缩写全词并存、
   不同函数签名中同一缓冲的形参名不同）
2. 对复用频率高的短名，核实各处的语义是否一致——一名多义同样
   是问题

**举证**：列出同概念的全部写法及其位置；或同一名字的多个语义
及各自位置。

**豁免思路**：跨层边界处故意的改名，且有注释给出映射（host 元
数据字段 vs kernel 形参）。

**修复**：每概念定一个标准名全文件统一；同仓算子间共用概念对齐。

### DSL-R04 字面量单一事实来源

**意图**：会随设计调整联动的数，裸写 N 处就埋下 N 处漏改的雷
（"散弹式修改"）。这条原则管的不是"字面量"本身，而是"改动时
要同步改多处"这一事实。

**识别**：对代码中的数值字面量，问两个问题（不预设数值范围）：
1. **它会随设计调整而变吗？**（块宽、轮数、系数、格式参数会；
   数学/硬件恒真不会）
2. **它有多处联动吗？**（同一数值出现在多处；或改一处必须同步
   改他处——深度、取模底数、循环步长的联动最典型）

两问有一为是 → 必须命名。另查：常量区已命名的值，代码中仍裸写
同值字面量且语义相关——这是"定义了却不用"，同一表达式两种写法
并存是最有说服力的证据。

**举证**：指出字面量的全部出现位置及联动关系；说明改值时需要
改几处。错误消息字符串中嵌的数值也要查——常量改值后消息说谎。

**豁免思路**：不随设计变化的恒真量（数学常数、硬件定值且有注释）、
公开契约的一部分（有文档的枚举值）、语义自足的小局部量。

**修复**：模块级命名常量，派生量用表达式（`HALF = BASE // 2`），
关键常量带推导注释；联动参数单一来源——一处定义，深度/取模/
循环全部引用；错误消息用 f-string 引用常量。注意"同值异义"：
同一数值承担两种语义时应拆成两个常量，而不是共用一个。

### DSL-R05 无重复

**意图**：重复不是"看着像"，是"改一处要同步改多处"的维护地雷；
也是读码时的噪音。

**识别**：结构同构判定——把标识符/常量换成占位符后仍相同的
代码块即同构。常见形态（举例）：
- 多个同构块散布（仅变量名/偏移不同）
- 同一循环骨架反复出现，仅最内层操作不同
- 仅以编号区分的手工展开（常伴随写死偏移与"展开数 == N"断言）
- 仅按一个布尔转发给下划线同名函数的透传 wrapper

判定**是否该抽象**：差异能否用参数/循环/分发表表达？抽象后是否
损害硬件并发意图？

**举证**：给出各同构实例的位置与占位符化后的相同骨架；说明
差异可参数化。若展开是性能意图（ILP/bank 冲突避免），要求有
注释说明——无注释的性能展开仍报。

**豁免思路**：硬件布局/并发语义要求的对称写法，且有注释说明意图。

**修复**：可参数化的差异提函数/提循环；编号展开改列表+循环；
透传 wrapper 合并、差异进参数或进函数名。

### DSL-R06 规模可审阅

**意图**：超出读者一次能建立心智模型的规模，检视和修改都会
失真。规模问题的实质不是行数，是**职责堆积**。

**识别**：问三个问题：
1. 这个函数能用一句话说清职责吗？（函数体内同时做校验、推导、
   分配、launch 编排等多种职责 → 该拆，无论行数）
2. 这个类/文件有清晰的分段结构吗？（helper/kernel/校验/接口
   边界）
3. 量级是否明显越界？（参考量级，非硬阈值：函数百行级、公开
   接口函数应短到只剩编排、文件数千行级、单类数百行级）

**举证**：给出函数/类/文件的跨度与其内部职责清单——职责种类
比行数更有说服力。

**豁免思路**：无（规模问题总是真的，只是优先级不同）。

**修复**：按职责分段/拆文件；校验段独立成文件；接口函数只留
编排（校验调用→派生→分配→launch）。

### DSL-R07 无死代码与冗余操作

**意图**：不改变行为的代码让读者为其虚构目的（"这段存在必有
原因"），浪费理解成本。

**识别**：对每段代码问"删掉它，行为会变吗？"不会变即候选。
常见形态：恒等运算（加零/乘一/零乘项，常为编号对称性保留）；
纯别名搬家（连续字段复制，直接引用原字段即可）；恒真/恒假的
编译期断言；被后续无条件覆盖的赋值；与算子无关的历史注释/
引用。

**举证**：证明删除不改变数据流/控制流。覆盖性赋值要给出覆盖
点的行号。

**豁免思路**：有注释说明的 ABI 占位/防御性兜底；为对齐意图
保留的恒等项且有注释。

**修复**：删除已证实的冗余；别名改直接引用；复述实现的伪代码
注释直接删除，必要的契约或非显然约束在相关代码附近简述。

### DSL-R08 注释即意图

**意图**：注释解释代码未表达的原因和约束。`#` 注释及模块、类、
函数 docstring 都属于检查范围，精简后仍能理解正确使用和修改代码
必须遵守的条件。

**识别**：
1. 完整阅读模块说明、函数 docstring 和相关注释块。逐行翻译、
   参数或类型复述、实验记录、临时日志路径、测试数量与修改历史
   均为冗余候选；搬入 docstring 后仍按同一标准判断。
2. 同一事实是否在模块、函数和调用处重复展开？区分重复叙述与
   不同使用点确有必要的局部前提。
3. 注释与当前代码是否一致，引用是否可核实？外部论文和稳定
   接口文档可作为来源；过期符号与临时取证位置不能替代当前约束。
4. 同步完成条件、资源复用时机、偏移单位、对齐及数值边界等
   非显然原因是否在相关位置说明？明显的分支或阶段无需补注释。
5. 自然语言说明是否遵循当前项目语言约定？API 名称、公式、
   许可证文本与必要术语保留原样。

**举证**：冗余给出具体行段及其重复的代码或说明；过期给出与当前
实现的矛盾；缺失说明删去该约束可能导致的具体误用。行数和占比
只能帮助定位，不能单独判为缺陷。

**豁免思路**：许可证、公开接口契约和代码无法表达的正确性约束
应保留；复杂约束确需多句时，以必要性判断，不机械限行。

**修复**：删除复述与过期内容；将长篇说明收敛为当前契约和必要
原因，并放在最相关的位置。详细推导及实验记录归入调用方提供的
设计或验证资料，不要求额外文档路径。保持计算、同步、签名和
执行语句不变；docstring 若被运行时或工具读取，先核实其用途。

### DSL-R09 风格以多数派为基线

**意图**：风格的价值在于一致——同一文件/仓库内风格跳变处，
往往是外部粘贴或多人拼合的痕迹，也是缺陷高发处。

**识别**：不预设具体风格标准，先建立文件的"多数派基线"
（空格、空行、换行对齐、错误消息格式），再找**系统性偏离**
基线的区域：
- 成片运算符/逗号无空格的区域（与全文风格断裂）
- 连续空行、多余换行的聚集
- 错误消息格式不一：首字母大小写、语言、前缀风格在同文件
  内并存

**举证**：给出基线形态与偏离形态的对照实例——证明偏离是
"区域性的"而非个别笔误。

**豁免思路**：无（偏离多数派基线本身即证据）。

**修复**：以多数派为基线统一；错误消息统一首字母、语言与
前缀风格。

### DSL-R10 用 Python 的方式写

**意图**：语料的总体结论之一是 AI 生成代码带明显"C++ 翻译成
Python"痕迹——同样的逻辑，用 Python 表达力写更短、更清楚、
更少错。

**识别**：找"用 C 思路写 Python"的模式（常见形态举例）：
- 锯齿校验：成串单条件 if/raise，每对只查一个变量的一个
  属性——表驱动（dict/元组列表 + 循环一次查多维）或多条件
  合并是 Python 化写法
- camelCase 标识符、单字母形参
- 整数伪布尔（=1/=0 配合 !=0 判断）
- 位运算代替除法对齐，且移位量与对齐常量是两个独立事实
  来源（应整除引用常量，单一来源）
- 手工索引循环搬运本可用切片/生成器/any/all 表达的逻辑

**举证**：给出 C 思路写法与对应 Python 化写法的对照（可用
同仓已有范例佐证——语料中的表驱动校验就是好例子）。

**豁免思路**：性能/硬件语义要求的写法，有注释说明。

**修复**：表驱动替代锯齿；snake_case；真布尔；除法对齐引用
常量；善用生成器表达式与多条件合并。
