# CANNbot DSL 代码检视方法论

检视代码并逐条核实候选时使用。执行角色和报告位置由调用方安排。

## 三步法：检测 → 核实 → 判定

**1. 检测**：按规则文档各原则的识别规程（提问/阅读规程）在算子文件里
定位候选。

**2. 核实（举证）**：Read 候选行上下文（前后 ≥10 行），对照原则的
「举证要点」和「豁免思路」收集证据，按下方打分表累计置信度。判断
涉及变量来源、跨层语义时，Grep/Read 相关定义与调用处综合判断。

**3. 判定**：按置信度区间给出结论，附证据与代码片段。

## 置信度打分

对每个候选建立假设：
- **原假设 H0**：该代码段无问题
- **备择假设 H1**：该代码段存在规则所述问题
- 置信度初始 0%

### 正向证据（支持 H1，加分）

| 证据类型 | 分值 | 分析动作 |
|---------|------|---------|
| 规范违反 | +40% | 对照规则条款识别到明确的违规模式 |
| 上下文防御缺失 | +30% | 作用域内无防御代码（无注释说明意图/无常量化/无保护） |
| 调用链风险 | +15% | Grep 分析被调函数内部逻辑后确认风险传导 |
| 数据流风险 | +15% | 变量来源不明确、运算路径不可控 |
| 领域关联 | +10% | 代码命中规则的 DSL 领域触发特征 |

### 负向证据（支持 H0，减分）

| 证据类型 | 分值 | 分析动作 |
|---------|------|---------|
| 防御存在 | -20% | 作用域内有显式防御：边界判断 / 非空校验 / const_expr 编译期保证 / 常量区已定义且注释充分 |
| 上游校验 | -15% | 作用域外已有校验，且校验变量与风险变量相同或可证等价 |

**设计原则**：负向证据单项分值低于正向证据——防止找到一条模糊防御就
大幅扣分。真正充分的防御需要**多条负向证据叠加**才能将置信度降至安全
区间，单条负向证据不应单独决定判定。

### ⚠️ 证据强制引用要求

每条正向/负向证据必须附可验证的代码引用，否则该条证据计 0 分：

```
格式: [文件路径]:[行号] [具体代码行内容]
示例: quant_block_sparse_attn.py:69 DMA_BLOCK_BYTES = 32
```

- 声称"上游已校验" → 必须 Grep 找到校验语句，且确认校验变量与风险变量
  是同一个（或经赋值链可证等价）；校验了"某个相关变量"不算数
- 声称"编译期常量" → 必须引用 const_expr / 常量区定义行
- 声称"Channel 自动同步" → 必须引用该 buffer 的 Channel(...) 声明行
- **找不到对应代码 → 该证据计 0 分，禁止虚构举证**

### 证据有效性校验（排除误报，满足任一即降级）

- 负向证据累加 ≤ -50% → 不进入 FAIL
- 上下文可证明不可能触发风险（如 const_expr 编译期已排除该分支）→ 排除

## 结论分级

置信度 = Σ 正向 + Σ 负向（负向为负数）

| 结论 | 置信度 | 含义 |
|------|--------|------|
| FAIL | ≥80% (HIGH) | 明确违规 |
| SUSPICIOUS | 70-80% (MED) | 可疑，需人工确认 |
| 待确认 | 证据显示问题存在但修复方向依赖作者意图 | 语料中约 10% 属此类 |
| PASS | <70% (LOW) | 证据不足，不判定违规（报告中只汇总） |

## 严重度

| severity | 适用 |
|----------|------|
| high | 误导性命名（名实冲突）、跨处联动的魔数（改动需散弹式多处修改） |
| medium | 同概念多名、重复代码、职责堆积的规模问题、关键流程注释缺失、C++ 翻译痕迹 |
| low | 缩写命名、死代码、注释语言混杂、风格偏离基线 |

## 常见豁免（命中即重点收集负向证据，细则见规则文档各原则的豁免思路）

- 读者群有共享约定的惯用名（同仓/文档有约定或全文一致）→ 非坏命名
- 不随设计变化的恒真量（数学常数、有注释的硬件定值、公开枚举）→ 非魔数
- 硬件布局/并发意图要求的对称写法或手工展开，且有注释说明 → 非重复
- 有注释说明的 ABI 占位、防御性兜底 → 非死代码
- 以文件/仓库多数派为基线的风格 → 非风格问题

豁免判断按规则文档各原则的"豁免思路"（理由类别）执行，禁止靠背实例过关。

## 代码片段格式要求

FAIL / SUSPICIOUS / 待确认 必须附：
- 准确行号（写入 findings 前重新核对）
- **最短足以证明问题的真实代码片段**（通常 ≤6 行；复制原文，禁止改写）
- 一句话问题描述 + 一句话修复建议
- 证据清单压缩为一行：`+40 规范违反@1234 +30 防御缺失@549 -15 上游校验@213`

## 条款边界

每条规则有明确适用范围。对不上问题模式的候选 → PASS 并注明；语料外的
新问题模式 → 报告中标注"语料外发现"，不强行归入现有规则。
