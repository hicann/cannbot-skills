# Broadcast 范式同步模型（RAW/WAR 依赖 → 同步点推导）

> **层级**：通用知识层（generic/），语言中立。
>
> 来源：adapters/ascendc/kernel-template.md §7（原 broadcast-standard-kernel-template.md）、dag-buffers.md 持有法则。同步原语实体（AscendC: SetFlag/WaitFlag/HardEvent/eventID）在适配层。

## 1 同步的本质

同步 = **跨执行单元的数据依赖**。同一个 buffer，执行单元 A 写、执行单元 B 读（RAW），或执行单元 A 读、执行单元 B 写（WAR）——就必须同步。

- 同一执行单元内自动串行（同单元的读后读/写后写不需同步），由编译器/硬件保证
- 不同 buffer 互不干扰
- 无跨执行单元数据依赖时，不需要任何显式同步

## 2 执行单元与事件对

执行单元划分由谓词 `EXEC_UNITS` 定义。本范式涉及三个单元：

| 单元（中立名） | AscendC 实例 | 职责 |
|------|------|------|
| 搬入单元 | MTE2 | GM → 片上 |
| 计算单元 | V | 片上计算 |
| 搬出单元 | MTE3 | 片上 → GM |

依赖类型与事件对：

| 依赖类型 | 含义 | 事件对（源→目标） | 方向 |
|---------|------|------|------|
| RAW | 生产者写 buffer → 消费者读 buffer | 搬入→计算、计算→搬出 | 正向 |
| WAR | 消费者在读 buffer → 生产者要覆盖 buffer | 计算→搬入（覆盖）、搬出→搬入（跨迭代覆盖） | 反向 |

## 3 四种同步场景

1. **RAW → 搬入_计算**：搬入写完片上 → 计算要读该片上
2. **WAR → 计算_搬入**：计算正在读片上 → 搬入要覆盖该片上
3. **RAW → 计算_搬出**：计算写完片上 → 搬出要读该片上
4. **跨迭代 WAR → 搬出_搬入**：上轮搬出读片上 → 下轮搬入要覆盖该片上

不是每条搬入后都插一对同步——同步点必须由依赖推导而来，不是模板化插入。

## 4 同步点推导方法

**持有法则 → 同步点**（持有法则见 [liveness-fusion.md](liveness-fusion.md) §2）：

1. 遍历每个 buffer 的生命周期，逐步标注三态持有
2. 标记每一次跨执行单元的 RAW/WAR——持有注释中"上一动作写、本动作读（跨单元）"即 RAW，"上一动作读、本动作写（跨单元）"即 WAR
3. 每个标记点即一个同步点：正向同步在生产者操作后 Set、消费者操作前 Wait；反向同步在覆盖者操作前 Wait、被覆盖读完成后 Set

**循环间的反向同步**：
- 末轮迭代跳过 Set（后面没有下一轮消费者）
- 首轮迭代跳过 Wait（前面没有上一轮生产者）

## 5 多输出同步原则

- 所有计算完成后、**第一次搬出之前**，插入一次 计算→搬出 的正向同步
- 后续各搬出之间不需要额外同步（搬出单元顺序执行）
- 若某输出 buffer 在下一轮迭代中被覆写，需确保该次搬出在 跨迭代反向同步（搬出→搬入）完成之前结束

## 6 退出前屏障

Kernel 退出前必须排空所有执行单元（屏障/等待全部流水线），防止搬出未完成即退出。

## 7 事件管理通用约束

（由谓词 `SYNC_PRIMITIVE` 承载，各适配层填值）

- 同步原语必须**成对使用**：一次 Set 必须有对应的一次 Wait
- 同类型事件可共用一个事件 ID（前一个 Wait 清零后可复用）；不同类型事件必须用不同事件 ID
- 事件 ID 通过框架接口获取，不可硬编码；部分事件 ID 可能被内部占用而不可用
- 在 Init 或 Process 开头统一获取事件 ID
