# Runtime LLT 生成覆盖率政策

## 适用范围

本政策用于 `runtime-llt-generator` 新增或修改 LLT 时的完成判定，不替代仓库 UT 规范。

- 开始前记录工作区已有修改，作为本次任务的基线。
- 覆盖率只统计用户指定范围或本次 LLT 涉及的生产代码改动，不包含基线中的无关修改。
- 仅修改测试时，默认统计目标函数全部可执行行；用户或缺陷已明确范围时，才按分支或代码区间统计。
- 声明、注释、空行和当前产品未编译的代码不计入分母。
- 排除代码时逐行说明原因，可由配置启用的代码不得排除。

## 门槛入参与解析

- 可选入参 `coverage_threshold` 表示百分比数值，接受 `80`、`80%`、`87.5%` 等写法；用户用自然语言明确指定“覆盖率达到 90%”时视为同一入参。数值单位始终是百分点，必须是 `0` 到 `100` 之间的有限值。
- 用户未指定 `coverage_threshold` 时，请求门槛默认为 **80%**。80% 是本 Runtime Skill 的默认值，不是通用行业标准。
- 需求、目标仓库 workflow 或其他强制规则规定最低覆盖率时，实际生效门槛取“请求门槛”和“强制最低值”中的较高者。用户值与强制值冲突时不得静默降级。
- 参数缺失时直接采用默认值；参数越界、无法解析或同一请求给出互相冲突的值时，只询问会影响门槛判定的歧义。
- 开始生成前记录请求门槛及其来源（用户输入或默认值）、仓库强制最低值和实际生效门槛；交付时同时报告这些值。

## 完成门槛

- 按“适用范围”统计行覆盖率，结果必须达到实际生效门槛。
- 所有可达的新建或修改判断结果、错误返回、边界和资源清理路径必须有直接用例，不能用行覆盖率门槛替代分支与行为验证。
- 覆盖率只说明代码被执行，不能证明断言有效或行为正确。

## 采集与判定

1. 先检查当前 workflow、`tests/build_ut.sh --help`、准确 CMake target 和覆盖工具，不复用可能已过期的命令。
2. 使用与被测源码、测试源码同一工作区快照构建并运行目标用例。筛选结果必须实际执行大于 0 个用例。
3. 从 LCOV、LLVM coverage 或仓库等价工具的明细数据读取目标行；不得从控制台总体 `PASS` 推断覆盖率达标。
4. 记录 commit/工作树状态、覆盖口径（生产 diff 或 test-only 目标范围）、构建 target、测试 binary、筛选条件、报告路径、可执行总行、命中行、未命中行、未知行和百分比。
5. 同一目标具有平台实现时，分别采集受影响平台的结果；一个平台的覆盖率不能外推到另一个平台。
6. 可执行代码未插桩、未构建、未进入报告、无法映射到当前二进制或统计范围不能解释时，必须记为 unknown，并阻止“达到实际生效门槛”的结论。报告缺失或源码与二进制快照不一致时，结论只能是“覆盖率未验证”。

计算口径：

```text
scope_line_coverage = 已命中的目标范围可执行生产代码行 / 目标范围可执行生产代码总行
```

- 分子、分母、未覆盖行和 unknown 行必须能从报告明细中核对。
- unknown 不为 0 时不能判定达标。
- 分母为 0 时记为 `N/A`，不算达标。
- 没有判断分支的函数，分支覆盖率记为 `N/A`，但仍需测试调用方可触发的边界情况。

## 质量检查

- 对返回码、出参、对象状态、副作用、回调、资源和依赖交互使用有效断言。
- 检查成功、非法输入、边界、依赖失败、重复调用、失败清理和适用的平台分支。
- 检查未覆盖代码是否暴露遗漏场景、不可达代码、错误挂载或错误 target。
- 使用独立、可重复、顺序无关的用例；恢复 mock、全局状态、环境变量和临时资源。
